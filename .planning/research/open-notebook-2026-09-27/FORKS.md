# Open Notebook forks and companion variants

**Checked:** 2026-09-27. **Evidence level:** pinned source, compare API, and test inspection. No fork was built, installed, or exercised with learner data. This is a bounded variant audit, not a complete census of Open Notebook's thousands of public forks.

## Scope and baseline

I inspected [upstream Open Notebook at `3127f14`](https://github.com/lfnovo/open-notebook/tree/3127f14ea9dbb519f0e4ddc64a0742ca644ba6ef), the first 100 public forks returned by GitHub's stargazer sort, targeted compare views for fourteen named forks, and the current trees of the three forks with relevant divergent code: [eryabyshev/open-notebook-app at `f7a7f78`](https://github.com/eryabyshev/open-notebook-app/tree/f7a7f7806d7e7e3b3ca8983c42f3f8ee9ed38b59), [POWERFULMOVES/PMOVES-Open-Notebook at `c73faa9`](https://github.com/POWERFULMOVES/PMOVES-Open-Notebook/tree/c73faa9a71df85350f0fe5f5b6742667d2bd40eb), and [Danejw/construction-os at `ff1011a`](https://github.com/Danejw/construction-os/tree/ff1011afb4e99b1435332974993b66c011d63690). I also sampled [AdamCage/open-notebook-with-ldap at `368c062`](https://github.com/AdamCage/open-notebook-with-ldap/tree/368c062cba47bfe4ab05afa0d2529e4bdfbaa5ea). Independent implementations checked were [Epochal-dev/open-notebook-mcp at `a2cddbf`](https://github.com/Epochal-dev/open-notebook-mcp/tree/a2cddbf65cba8c4c8de7be16566781b7612a9545) and [sergeesteves/open-notebook-mcp-skill at `98833f9`](https://github.com/sergeesteves/open-notebook-mcp-skill/tree/98833f9606c6ab12e8c0bb8f7d268ba0b219b1c3).

The prior [integration research](INTEGRATION.md) has no feature row IDs. Each `ON-F` row below is **new** and points to its relevant integration section. Itembank's current baseline is [the local companion](../../../surfaces/open_notebook.py), [course Sources route](../../../surfaces/daemon.py), `model_adapter.py` for hosted CLI and OpenAI-compatible operations, `notes.py` for private learner notes, and its course source/journal protocol. The companion is source-only and has not been verified against a running Open Notebook instance. The research plan requests a later `CAP-` mapping; this report does not edit that shared inventory.

## Screened variants and limits

- [Construction OS at `ff1011a`](https://github.com/Danejw/construction-os/tree/ff1011afb4e99b1435332974993b66c011d63690) is a substantial MIT domain fork. Its [artifact template router](https://github.com/Danejw/construction-os/blob/ff1011afb4e99b1435332974993b66c011d63690/api/routers/artifact_templates.py) and project UI add repeatable domain extractions, but the project is rebranded for construction workflows and changes hundreds of files. Itembank already has course artifacts, operations, and review authority. **Defer** direct code absorption; revisit only if a specific repeated authoring job lacks a current itembank owner and passes a synthetic course test.
- [AdamCage's LDAP fork at `368c062`](https://github.com/AdamCage/open-notebook-with-ldap/tree/368c062cba47bfe4ab05afa0d2529e4bdfbaa5ea) adds user and LDAP authentication paths while 364 commits behind upstream. Its tree has no named auth test alongside the new auth modules. This is outside the current local-only companion job. **Defer** pending an explicit remote multi-user product decision and a current security review.
- The checked `mvanhorn`, `geraldhoong`, `PayPerQ`, `NimaMan`, `techserv`, `Guan-Y`, `azimRR`, `BSCConsulting`, `phong711`, and `mehdikiani` branch comparisons were behind or identical to current upstream. A stale or identical branch supplies no unique feature at the checked revision. This does not judge unpublished branches or earlier ideas that upstream absorbed.
- The 100-fork listing was one sort page, with follow-up comparisons chosen for relevant names, recency, and source paths. Private, deleted, and unsearched forks, tags, and non-default branches are not covered. GitHub ahead/behind counts only describe ancestry. No test in a donor repo was executed here, no live instance was available, and no accessibility or learning outcome was observed. A future `CAP-` inventory pass should link ON-F1 to ON-F5 or mark any row that duplicates an existing capability.

**Priority:** repair ON-F1 before any live companion claim; then exercise ON-F2 against a pinned instance. ON-F3 needs a real provider trial, while ON-F4 and ON-F5 remain bounded prototypes. A full fork has no demonstrated advantage for the first course-companion job.
