Reconsider the presentation shell, storage implementation, the number of

## Candidate gate before retirement

**G1, working baseline:** exercise each requested study mode, editor and saved
session. Identify which advantage is visual, interaction quality, speed,
feedback or content. The old and new apps need not have identical breadth for
the candidate to be worth adopting for daily studying.

**G2, ownership:** restore a complete backup into a fresh profile and verify
images, cards, notes, sessions, results and review schedules. Browser storage
is origin-scoped and best-effort by default; persistent storage is an additional
protection, not a replacement for recoverable exports. [MDN storage guide](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

**G3, genuine offline return:** test cached application reload while offline,
then an application update without learner-data loss. A database alone is not
the app-shell offline mechanism; service-worker cache handling needs its own
journey. [MDN service-worker guide](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers).

**G4, real learning:** try representative factual, numerical/production and
explanation tasks. Card-derived recognition and deterministic term checking
do not exhaust the course vision. Verify at least one joined source-to-review
course loop before declaring the candidate the full Itembank replacement.

**G5, recoverable retirement:** after choosing the candidate, preserve the
current checkout, uncommitted changes and learner data. Establish which
automations and writers should stop, what remains read-only reference and
which learner data actually needs migration. A clean Git branch by itself
cannot preserve the current uncommitted files. Do not infer authorization to
archive a chat or stop an automation from this recommendation.
