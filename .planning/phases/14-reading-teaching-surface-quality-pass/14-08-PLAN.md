<objective>
Bring the two in-scope surfaces down to one announcing region each, without
making any failure silent — and then write down what this phase can and cannot
prove without a browser.

The accessibility gate says exactly one `role=status` per rendered page. Today a
served quiz page can hold **three** concurrent polite regions on a visual item
and a runnable lesson **five**. The gate was being restated as a slogan in two
places and neither statement had been checked against the code.

Two things make this more than a cleanup. First, `surfaces/lesson.py` documents
in a comment that run-request errors are announced with an alert role, and the
code has never set it — the string appears in that module only inside that
comment — so today a failed run is announced only because its status element
happens to be polite, and de-living it under the readout rule would make **every
run failure silent**. Second, an explicit `aria-live="off"` overrides the
implicit live value an alert role would otherwise carry, so the obvious fix is
self-silencing: the ORDER of the attribute writes is the specification.

This plan is also the phase's verification close-out. All four of the defects
this phase fixes were invisible to a green test suite, so the honest split
between what a fixture proves and what a human must look at is itself a
deliverable.

Purpose: ROADMAP criterion 6, the inherited accessibility gates holding unchanged.

Output: one announcing region per page with two named transient exceptions, two
failure paths that provably announce, the additive-format floor re-proven, and a
gates document that says plainly which gates a machine closed.
</objective>

  <action>
Five rules govern every element below. They are the single authority on live
regions in this phase and are not restated anywhere else.

  **Rule 1** — one *announcing* region per activity canvas: the reserved
  `.feedback` region inside the active card on the quiz, and the `.status`
  region on the reader, which has no activity canvas of its own. It announces
  verdicts, held state, duplicate and empty notices, and tier arrival, and it is
  the only element whose content changes are spoken without the learner asking.
  **Rule 2** — an alert role is reserved for a change that BLOCKS the learner's
  next action.
  **Rule 3** — a result the learner explicitly requested is not an announcement:
  text that appears only as the direct outcome of a control they just pressed,
  inside the container they just opened, is static text with no live region. The
  press is the event.
  **Rule 4** — a persistent state *readout* is not a live region: it is a visible
  readout associated with its control by `aria-describedby`, at `aria-live="off"`,
  read on demand rather than pushed.
  **Rule 5** — Rule 3 covers *synchronous* results only. A result that arrives
  seconds later while focus is still on the button gets a live region that exists
  **only for the duration of the request the learner initiated**.

**Dispositions, element by element.**

  `.feedback` on the quiz — the boot placeholder and the per-card region in both
  clients: **survives unchanged**, as exactly one at a time. Only the active card
  exists in the host, and the fixture asserts a page never holds two. The two
  clients are mutually exclusive at runtime, so their two implementations are
  never both live.

  `.status` on the reader — the degraded-lesson and style-warning notice:
  **survives**, and gains `aria-live="polite"` for parity with its role. Exactly
  one per reader page.

  `#assist-status` on the quiz — **static text by default, live only while a
  request is in flight.** Drop the permanent status role. On press: set
  `aria-live="polite"`, THEN write the waiting copy. On arrival: write the result
  — generated support, unavailable, policy-blocked or cancelled — into the same
  region, one announcement, no focus movement. After it has rendered: **remove
  `aria-live`**, so re-opening the disclosure later re-announces nothing. Every
  locked string is unchanged. Moving focus to the result on arrival was the other
  candidate and is rejected: the inherited focus gate says status is announced
  without a focus jump, and an arriving hint is not an error.

  `.visual-status` in the five visual-item renderers — **keeps its persistent
  polite region.** `06.1-UI-SPEC.md` owns the visual-interaction contract and
  requires "one persistent polite live region announces committed state,
  validation, and runtime observation once; use role=alert only for
  action-blocking failure", so 06.1 wins and this is a **recorded exception**,
  not a silent divergence. Add a comment at each site naming 06.1 as the
  authority. A visual item therefore holds two announcing regions, and Task 2's
  count fixture is written against two on visual items specifically — never
  against some unexplained number.

  `.run-status` per runnable code block — **de-lived to an `aria-live="off"`
  readout under Rule 4**, wired by `aria-describedby` from the run control, with
  the failure path made real. A lesson with four runnable blocks ships four
  polite regions today; after this it ships none, and the reader's one `.status`
  region is its Rule 1 region.

**The binding sequence, and it is the specification.** `setStatus(block, text,
isError)` performs, in this order:

  when `isError`: set the element's role to alert, then set `aria-live` to
  `assertive` — never `off`, and removing the attribute entirely is equivalent;
  otherwise: remove the role, then set `aria-live` to `off`;
  and only then write the text.

Three portability rules that make it work in practice: the live attributes are
set **before** the text is written, never after; `aria-live` is never left at
`off` while the alert role is present; and the success path restores both, so a
later idle update does not re-announce. A failed run blocks the learner's next
action, which is exactly Rule 2's condition, so this is the role the comment
always claimed and the code never had. Update that comment so it becomes true
rather than aspirational.

**Housekeeping.** `session.do_hint`'s legacy `stumped` keyword branch has no
caller left once plan 14-03's route and plan 14-07's client have landed. Confirm
that by search, then delete the branch and the keyword, leaving `do_hint` as the
model-orchestration entry point its docstring describes.
