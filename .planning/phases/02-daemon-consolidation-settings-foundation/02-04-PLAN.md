<objective>
Give the daemon the JSON API D-04 scopes — the same four session commands an agent already drives from
the shell — over the same runtime calls, addressed by opaque identifiers rather than by paths, and wrapped
so that a routine error cannot take the whole daemon down with it.

**User story (MVP framing):** **As an** AI tutor driving a sitting, **I want to** start, fetch, answer and
summarise a session over HTTP against the same runtime the CLI uses, **so that** I am a client of the one
runtime rather than a scraper of a page.

Purpose: SURF-04's proof. Two of RESEARCH.md's findings are load-bearing here and both are the reason this
is its own plan rather than three lines in the tracer. `surfaces/session.py`'s command bodies call
`sys.exit()` on error conditions that are routine in normal use, and `SystemExit` is not a subclass of
`Exception` — so the `except Exception` pattern every existing handler uses does not catch it, and one
learner's stale session would kill the daemon for every other bank in the house. And `read_session` /
`write_session` take a raw filesystem path with no allowlist at all, so a literal reading of D-04 would
reopen under a different field exactly the class of bug D-03's stem allowlist was written to close.
Output: four JSON routes that are safe to leave running.
</objective>

Add the session lookup, then the four routes, then the containment.

**`session_index(root)`** — scan `<root>/_attempts/` for `session_*.json`, read each one's `session_id`
field, and return `{session_id: abspath}`. Build it lazily per request rather than once at startup, so a
session created by `POST /api/start` (or by an `itembank start` run in another terminal) is addressable
immediately; a single directory listing per API request is cheap next to the file reads the request is
about to do anyway. Skip any file that will not parse rather than raising — a half-written session file in
the directory must not break addressing for every other session. This is D-03's allowlist principle
extended to session identifiers, which is the gap RESEARCH.md Pitfall #5 found between D-03 and D-04.

**The four handlers.** Each one follows the same four steps and nothing else:

1. Resolve the identifier. `handle_api_start` takes `bank` and resolves it through the same `banks` stem
   allowlist the GET routes use — a value that is not a key in that dict is a 404, full stop; it is never
   joined to a path, never normalised, never checked for traversal segments, because it is never treated
   as a path at all. The other three take `session_id` and resolve it through `session_index(root)`; a
   miss is a 404. Reject any request carrying a `session`, `bank_path`, `out` or similarly path-shaped
   field with 400 naming the field — accepting one would silently reintroduce the raw-path surface, so
   refuse it loudly rather than ignoring it.
2. Type-guard the remaining body fields the way `handle_quiz_answer` already guards `elapsed_ms`: `count`
   and `seed` must be non-bool integers or fall back to their defaults, `mode` must be one of the five
   session modes, `confidence` must be one of the three levels or `None`.
3. Call the matching `session.do_*` with the resolved path.
4. Send the returned dict as JSON.

`handle_api_start`'s `out` argument is computed server-side — `<root>/_attempts/session_<uuid>.json`,
exactly what `do_start` defaults to — and never taken from the body.

**The containment.** Every one of the four call sites is wrapped in *both*
`except SystemExit as exc: self.send_error(400, str(exc.code))` and
`except Exception as exc: self.send_error(500, str(exc))`, in that order. Both are required:
`SystemExit` derives from `BaseException`, not from `Exception`, so the `except Exception` clause the
existing handlers use does not catch it, and an uncaught `SystemExit` propagates out through
`socketserver`'s request loop and kills the process serving every other bank, every other tab and the day
view. The conditions that raise it here are routine, not exotic — a bank with lint errors, an objective
matching no items, a session already complete (twice), a session file with a missing or future
`schema_version`. Add a comment at the first handler recording that the pairing is deliberate and why, so
a later refactor does not collapse the two clauses into one.

**Route registration and scope.** Define `API_ROUTES` as a four-entry tuple naming exactly `/api/start`,

ahead of every stem pattern), and add them to `ROUTE_CLI` mapping to `start`, `next`, `submit` and
`report`. The four-entry length is asserted in the test: D-04 scopes `/api/*` to exactly these four for
this phase, and the browser-holds-no-key rework that would want more of them is Phase 4's SURF-02 job.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent/browser → `/api/*` | Every field of every JSON body is untrusted; under `--lan` (plan 02-06) the source is any device on the same wifi |
| `/api/*` → filesystem | `do_start` writes a session file and `do_submit` appends to the evidence log; `write_session` will create parent directories, so the path it receives must never be client-derived |
