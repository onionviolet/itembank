<objective>
Ship the settings foundation: one documented file, one schema, one validator, and one command that prints
the contract the way `spec` prints the format contract and rejects a bad value with a named code rather
than a sentence.

**User story (MVP framing):** **As a** learner, **I want to** see every setting the tool has, what each
one accepts and which of them actually do anything yet, **so that** I can configure it without reading
the source and without believing a knob works that does not.

The keys land now with real types, real ranges and real defaults; the behaviour behind five of the seven
arrives in phases 4, 7, 8, 10, 11 and 12, and the schema says so per key rather than leaving a learner to
discover it.
Output: `schemas/settings.schema.json`, `itembank.json`, `surfaces/settings.py`, an `itembank config`
command, and `tests/config_roundtrip.py`.
</objective>

  <action>
Create `surfaces/settings.py` following `protocol_cli.py`'s structure and voice. Module docstring: this is
the settings surface, `itembank config` is to `itembank.json` what `itembank spec` is to the bank format
and `itembank schema` is to the published documents, and there is exactly one validator behind it.

Resolve `SCHEMA_PATH` the same way `protocol_cli.SCHEMA_DIR` does — two `os.path.dirname` calls off
`__file__` plus `"schemas"` — so the module finds its schema regardless of the working directory. Define
`SETTINGS_FILE = "itembank.json"` and `settings_path(base)` returning `os.path.join(base or ".",
SETTINGS_FILE)`.

Define `SETTINGS_CODES` as a sorted tuple built the way `LINT_CODES` is built, holding
`settings.invalid_type`, `settings.invalid_value`, `settings.out_of_range`, `settings.unknown_key`,
`settings.missing_key` and `settings.malformed_file`, with a comment recording the same rule D-16
recorded: adding a code is additive, renaming one is a breaking change for every consumer.

`classify_error(msg)` maps one `schema_validate.validate()` output string to one code by matching the
substrings that validator actually emits: `"expected type"` and `"does not equal const"` for a shape
mismatch, `"is not one of"` for an enum miss, `"is less than minimum"` and `"is greater than maximum"` for
a bound, `"additional property"` for an unknown key, `"missing required key"` for a missing one, with a
documented fallback to `settings.invalid_value` for anything unmatched. This thin classifier is what keeps
`schema_validate.validate()`'s return contract — a list of plain strings — unchanged for its existing CI
callers while still giving D-06 its dotted codes; do not change the validator's return type.

`defaults_from_schema(schema)` walks `properties` recursively and builds the full default object from the
`default` annotations. `load_settings(base)` reads `itembank.json` when present and merges it over those
defaults so a missing key reads as its default rather than as absent; a file that will not parse exits
with `settings.malformed_file` naming the path and the decode error. `write_settings(base, data)` writes
tmp-then-`os.replace()`, `json.dump(..., ensure_ascii=False, indent=2)` plus a trailing newline, matching
`runtime.write_session` exactly — the same crash-safety, and the same byte layout, which is what makes a
repeated `config set` byte-identical rather than merely equivalent.

`get_at(data, dotted)`, `set_at(data, dotted, value)` and `schema_for_key(schema, dotted)` handle dotted
key paths (`daemon.port`, `selection_weights.recency_decay`) by splitting on `.` and walking both the data
and the schema's nested `properties`. `schema_for_key` returning `None` at any level is an unknown key and
produces `settings.unknown_key` — this covers both `nope` and `daemon.nope`.

`cmd_config(a)` has three branches mirroring `cmd_schema`:

- `a.action == "schema"` → `print(open(SCHEMA_PATH, encoding="utf-8").read(), end="")`, verbatim bytes off
  disk, no re-serialisation. Return 0.
- `a.action == "set"` → decode `a.value` with `json.loads` first so `9000`, `true`, `0.4` and a JSON array
