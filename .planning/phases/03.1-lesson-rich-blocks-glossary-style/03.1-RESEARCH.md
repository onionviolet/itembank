## Summary

This phase adds no new dependency, no new parser, no new scorer, and no new evidence store — it is entirely an *additive* extension of machinery that already exists: one more parse path (`[!CHECK:]`), one more callout kind (`[!EXAMPLE]`) against a callout container that **does not yet exist in code** [VERIFIED: `surfaces/lesson.py:242-308 _render_blocks()` has branches for fenced code, `#### heading`, `-`/`1.` lists, and pipe tables only — no blockquote/`[!...]` branch of any kind], two new evidence event types appended to a closed tuple [VERIFIED: `evidence.py:43 KNOWN_EVENT_TYPES = ("response", "retraction", "mark", "day_tick")`], and a rule-registry (`styles/*.md`) whose closed check catalogue reuses the exact pattern `model.py` already uses for `LINT_CODES` [VERIFIED: `model.py:578-590` — a single hardcoded, alphabetically-sorted, deduplicated tuple built once at import time].

Everything this phase needs to build is greenfield inside an established shape: `content_fingerprint()` already proves the style-rewrite-safety claim (D-04's "the hash-drift worry was false"); `parse_lesson()`/`lesson_slug()` are the one precedent for "one independent reader, one slugifier" that TERMS and the style registry both must follow; and `LESSON_TEMPLATE` currently carries a **private, un-tokenized CSS block** that must be migrated onto `SHARED_CSS` + a new `LESSON_CSS` layer before any of `text-lesson`, the heading ramp, or the vendored fonts can land — this is real, uncosted work the phase criteria assume but do not name.

The eight open questions this document is charged with settling are answered in **Open Questions** below; the short version: (1) the "locked house rows as code constants" pattern is not new to this phase — it is exactly what `LINT_CODES` already is, so there is a direct precedent to copy; (2) widening `[!KEY]` into item rationales is real, non-trivial cost because rationale fields are today rendered through a completely different, markdown-blind path (`esc()` in `study.py`), not through `lesson.py`'s renderer — D-05's lesson-only default is the cheap direction; (3) narrowing `[!CHECK:]` to same-bank is additive-compatible with later widening, by the same shape `[LESSON-SRC:]` already proved for cross-file lesson sourcing; (4) `09-02-PLAN.md` has not executed and `subject_profiles` does not exist in the shipped schema yet, so folding `lesson_layout` in is genuinely free today; (5) the Runestone Parsons-to-`build` mapping is **confirmed**, not falsified, with one named gap (no distractor-block or indentation support in `build` today); (6) the 50ms budget is achievable and directly assertable by a `time.perf_counter()` test against pure-Python regex/count operations over a ~30KB document; (7) the Anki `[!KEY]` round-trip needs materially new export code, because the current exporter has no `#guid column` mechanism at all; (8) CSS Anchor Positioning plus the Popover API is Baseline as of 2026 across Chrome, Firefox and Safari, confirming the UI-SPEC's declarative-baseline claim currently.

**Primary recommendation:** treat this phase as five build tracks that share almost no code: (a) `## TERMS`/`[[term]]`/glossary, (b) `[!KEY]`/Anki/evidence, (c) callout-container renderer work (the prerequisite both (a)'s appendix styling and (b)'s card need), (d) the style registry (file format, loader, rule-kind linter, `StylePrompt` compiler), and (e) the `LESSON_TEMPLATE` token migration that criterion 4 requires but no other criterion names. Sequence (c) and (e) early — every other track depends on one or both.

### Pattern 1: One independent reader per new section (the `parse_lesson()` precedent)

**What:** `parse_terms(bank_path)` must mirror `parse_lesson()` exactly: an independent, non-invasive read over the bank's preamble that returns `None` on absence and never changes `parse_bank()`'s return shape.
**When to use:** Any time a new `##`-level section is added to the format contract.
**Example:**
```python
# Source: model.py:167-197, the exact precedent to copy
def parse_lesson(bank_path):
    """A second, independent read over the bank file for a different purpose...
    Never called from inside `load()` or `parse_bank()`, and it changes neither's
    return shape.
    """
    text = open(bank_path, encoding="utf-8").read()
    preamble = []
    for ch in re.split(r"(?m)^(?=Q\d+\.)", text):
        if re.match(r"Q\d+\.", ch.strip()) and parse_question(ch) is not None:
            break
        preamble.append(ch)
    head = "".join(preamble)
    ...
```
`parse_terms()` should reuse the identical `preamble`-accumulation loop (the "stop at the first real question" boundary rule), find `## TERMS` inside it the way `parse_lesson()` finds `## LESSON`, and return `None` when absent.

### Pattern 3: The callout container does not exist yet — build it once, reuse three times

**What:** `[!KEY]`, `[!EXAMPLE]`, `[!CHECK:]`, and the decorative siblings (`[!NOTE]`, `[!WARNING]`) all share one blockquote-marker grammar and one renderer branch.
**When to use:** The very first task in this phase's implementation, because everything else in the "blocks" tracks (TERMS aside) depends on it.
**Example:**

### Anti-Patterns to Avoid

- **A second slugifier for TERMS lookups:** `lesson_slug()` is deliberately the one slugifier for both lookup keys and anchor ids [VERIFIED: `model.py:145-148` — "one slugifier for both the lesson lookup key and the rendered HTML anchor id (D-03) -- a lookup that agrees with an anchor by coincidence eventually disagrees"]. Term keys and `[!KEY]` anchor ids must call this function, never a bespoke regex.
- **Rendering rationale fields (`why`/`disc`/`second`/`trap`) through the lesson's markdown renderer to support `[!KEY]` there:** these fields are today rendered via plain `html.escape()`-style `esc()` in `study.py` [VERIFIED: `surfaces/study.py:158,169,173` — `esc(ex["why"])`, no markdown pass] and via `gift_escape()`/plain TSV cells elsewhere [VERIFIED: `surfaces/gift.py:87-88`, `surfaces/anki.py:30,36`]. This is exactly why D-05's lesson-only scope is the cheap direction — see Open Question 2.
- **A second copy of the pipe-table cell splitter for the style `## Rules` table:** reuse `surfaces/lesson.py:153-163` (`_split_cells`, `_is_separator_row`), don't reimplement.

## Common Pitfalls

### Pitfall 1: Assuming the callout container already exists

**What goes wrong:** A plan that treats `[!KEY]`/`[!EXAMPLE]`/`[!CHECK:]` as "just three more callout kinds" without budgeting the container itself underestimates the phase — there is no blockquote parsing in `_render_blocks()` at all today.
**Why it happens:** The research artifacts (D1/D2/D3, catalogue, mechanics) all talk about "the callout container" as if it is a given, because it is a well-known pattern (GitHub alerts, Obsidian callouts) — but this codebase has not built any version of it yet.
**How to avoid:** Budget one dedicated task for the blockquote-marker grammar (`^>\s*\[!TYPE\]` opening, `>`-continuation body, first non-`>` line closes) and its render branch, before any specific callout kind.
**Warning signs:** A plan whose first `[!KEY]` task assumes `_render_blocks()` "already handles" callouts.

### Pitfall 2: Migrating `LESSON_TEMPLATE`'s CSS as an afterthought

**What goes wrong:** Criterion 4 requires the heading ramp/measure/`text-lesson` to render on Phase 4's token set — but `LESSON_TEMPLATE` today ships a completely private, hardcoded CSS block (`h1{font-size:21px...}`, `h2{font-size:19px...}`, `font:16px/1.55...`) with zero references to `SHARED_CSS` or any `--space-*`/`--font-*` token [VERIFIED: `surfaces/lesson.py:39-82`, the full `LESSON_TEMPLATE` string, quoted in Architecture Patterns above]. A plan that adds `text-lesson` usage inside new callout HTML while leaving the surrounding `h1`/`h2`/`body` rules untouched will produce visibly inconsistent typography (new blocks at 18px Paper-voice serif next to old headings at a hardcoded 21px/19px sans-serif).
**Why it happens:** The UI-SPEC's Design System table states the target state ("Reader CSS — LOCKED: `LESSON_TEMPLATE` stops carrying a private type system") as if it were incidental, when it is a load-bearing prerequisite for the whole heading-ramp criterion.
**How to avoid:** Sequence a dedicated "migrate `LESSON_TEMPLATE` onto `SHARED_CSS` + a new `LESSON_CSS` layer" task early, before or alongside the token additions to `presentation.py`.
**Warning signs:** Any diff that adds `text-lesson`/heading-ramp CSS *inside* new callout markup while `LESSON_TEMPLATE`'s own `<style>` block is untouched.

### Pitfall 3: Treating the style `## Rules` table as free-text severity

**What goes wrong:** A style author (human or model) writes a row claiming `error` severity for a rule the linter has no code for. Silently accepting this makes the style contract decorative — exactly the failure mode D-16/the honesty rule exists to prevent.
**Why it happens:** The pipe-table parser itself has no opinion about whether the `kind`/`id` column names something real; that check has to be a separate validation pass after parsing.
**How to avoid:** `load_style()` must cross-check every parsed row's `kind` against the closed rule-kind set (`order.before`, `density.max`, `style.require`, `style.forbid`, `cadence.section`, `open.with`) and emit `style.rule_unimplemented` for anything else, before the rule is ever applied.
**Warning signs:** A style file with a `kind` column value that does not appear in a hardcoded allowlist anywhere in `model.py`.

### Pitfall 4: Conflating `render_style` and `restyle`

**What goes wrong:** A single function that "renders a lesson in a given style" and quietly falls back to inventing content when the target style needs a block the source doesn't have would violate Directive §4.1 (the runtime cannot fabricate) without anyone noticing until a case-narrative renders as gibberish.
**Why it happens:** Both operations sound like "change how this lesson displays," and the boundary (permutation of existing blocks vs. requiring new content) is subtle.
**How to avoid:** Two separate, separately-named functions/commands from the first line of code. `render_style` must have no model dependency in its call graph, structurally — the cheapest enforcement is that the function's signature never accepts a model client.
**Warning signs:** Any code path where `render_style` imports or calls anything from the Phase 8 model-adapter module.

### Pitfall 5: Widening the `[!KEY]` `id`/`hash` id-space carelessly

**What goes wrong:** `[!KEY]` blocks and items must share `new_item_id()`'s global-uniqueness `taken` set (per the D2 research) — a plan that mints `[!KEY]` ids independently could produce an id collision between a key block and an item, corrupting the "one evidence store needs one key type" invariant.
**Why it happens:** `[!KEY]` blocks are lesson-scoped, items are bank-scoped, and it's tempting to treat their id spaces as separate.
**How to avoid:** `itembank id-assign`'s walk must mint `[!KEY]` ids through the exact same `new_item_id()`/`taken`-set call path as item ids [VERIFIED: `model.py:297-305 new_item_id()`, `model.py:313-394 assign_ids()` with cross-bank `taken`].
**Warning signs:** A separate `new_key_id()` function, or a `[!KEY]` id-minting path that doesn't thread the same `taken` set `assign_ids()` already builds.

### 1. Ruling 13 — hardening the style-registry lock

**Verified against the actual linter machinery, not assumed:** the pattern ruling 13 asks for ("locked house rows as code constants in the linter, not rows parsed out of `styles/house.md`") is **already the shape `LINT_CODES` uses today** [VERIFIED: `model.py:578-590`, quoted in full in Architecture Patterns Pattern 2 above — a single hardcoded, `sorted(set(...))`-built tuple, never read from a data file]. There is no existing `styles/house.md`-reading code to check the three hardening sentences against (this whole subsystem is greenfield — `Glob("styles/**")` over the repo returns nothing), so "verify against the real linter code" resolves to: **there is no contradicting precedent, and there is a directly-supporting one.**

Concretely, all three hardening sentences translate into specific, nameable structures:

- **(a) Locked house rows as code constants:** add `LOCKED_RULE_IDS = frozenset({...})` (or equivalent) to `model.py`, populated with the five-non-negotiable-derived rule ids. `styles/house.md`'s `## Rules` table documents these rows for human readers, but `load_style()`/`lint()` never trust the file's own claim about which rows are locked — the lock membership test is a Python-side lookup against the constant, exactly parallel to how `LINT_CODES` membership is a Python-side lookup, never something `lint()` infers from a markdown file's content.
- **(b) `<!-- style-ignore: -->` cannot suppress a locked rule:** the suppression-application step inside `lint()` (wherever it filters findings against ignore comments) must check `finding.code in LOCKED_RULE_IDS` **before** consulting the ignore-comment table, and refuse the suppression (itself becoming a new lint error, e.g. `style.ignore_locked`) rather than silently applying it.
- **(c) A style cannot re-severity a locked rule in any direction:** the inheritance-resolution step (D-10's "for each child row, if `id` matches a house row, the child row replaces it") must special-case `id in LOCKED_RULE_IDS`: any child row naming a locked id, at any severity including `off`, is `style.override_locked` (already named in the mechanics research and echoed in D-16-adjacent territory).

**Recommendation: adopt all three, as the roadmap's own default-if-unruled states.** The concrete implementation cost is small — one frozenset constant plus two `if id in LOCKED_RULE_IDS` guards in code paths the phase is building anyway (suppression handling, inheritance resolution).

### 6. The 50ms style-pass budget: how to assert it, and is pure Python enough

**Directly assertable by test; pure Python is very likely sufficient, though this session did not run the benchmark.** The style pass (per D-12: structural counts over the parsed heading tree + one shared lexical metrics pass) is bounded, deterministic work over a document that criterion 3c itself bounds at "5000 words" (~30KB of text). The operations involved — `re.split()` for sentence/word boundaries, `collections.Counter`/regex counts for filler-phrase and blocklist matching, a syllable-heuristic pass for readability — are all `O(n)` or `O(n log n)` string operations that Python's `re` engine (implemented in C) handles at multiple MB/s even in worst-case backtracking-free patterns.

**Recommended test design, directly executable in this codebase's existing harness style:**
```python

import time
...
FIXTURE_5000_WORDS = ...  # a synthetic lesson fixture, generated or checked in

start = time.perf_counter()
run_style_pass(FIXTURE_5000_WORDS, style)
```

### 8. Popover API + no-JS degradation: current browser support

**Confirmed current as of this research date (2026-08).** CSS Anchor Positioning — which the UI-SPEC's DOM shape depends on for `anchor-name`/`position-anchor` pairing — reached **Baseline 2026** status: Chrome/Edge have supported it since version 125 (2024), Safari added support at 18.2+ with `@position-try` (the flip-fallback behavior) requiring 18.4+, and Firefox shipped it (the last of the three engines) at version 132, which is what tipped the feature into Baseline classification [CITED: web-platform-dx/web-features GitHub issue #3558; MDN `position-anchor` reference page; OddBird's "Anchor Positioning Updates for Fall 2025"]. ### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A gloss definition leaking a keyed answer through the DOM, ARIA tree, or CSS-off text | Information Disclosure | `glossable()` gate enforced server-side at render time (D-20); the no-leak fixture (§17 item 1 of UI-SPEC) must assert absence in all four surfaces, not just the visible one |
| A `[LESSON-SRC:]`-style path-containment bypass applied to a new file-referencing directive (if one is ever added for TERMS or styles) | Tampering / path traversal | Reuse the exact absolute-path-plus-separator-suffix containment check `parse_lesson()` already implements [VERIFIED: `model.py:213-220` — `resolved != bank_dir and not resolved.startswith(bank_dir + os.sep)`] for any new external-source directive; this phase's TERMS grammar deliberately does NOT add a `[TERMS-SRC:]` external-source directive (per the D1 research: "one shared-file mechanism at a time"), so this pattern is dormant unless a future phase adds one |
| A style file being a governance file a model can write, silently demoting an accessibility or non-negotiable rule | Elevation of Privilege (of the authoring model over the runtime's guarantees) | The `lock` column + `LOCKED_RULE_IDS` code-constant enforcement (Open Question 1) is the mitigation; this is the phase's own security-relevant design decision, not an external threat |
| Unescaped bank-authored text reaching the page through a new render path (`[!KEY]` body, gloss definition, style `## Exemplar`) | Injection (stored XSS via markdown-derived HTML) | Every new text field must go through the existing `_inline()`/`html.escape()` pass before interpolation, matching the discipline already documented for the current renderer [VERIFIED: `surfaces/lesson.py:214-224` `_inline()` docstring: "Escaping before the patterns run is what keeps a markup-shaped stem or heading from reaching the page as markup"] |
