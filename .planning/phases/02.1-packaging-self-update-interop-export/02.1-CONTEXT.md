# Phase 2.1: Packaging, Self-Update & Interop Export - Context

**Gathered:** 2026-08-07
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase delivers four things and nothing else:

1. **A `.pyz` artifact plus one thin launcher per OS** (`.bat` / `.command` /
   `.desktop`), built with stdlib `zipapp`, staying plain readable Python inside.
2. **An app-mode browser window** for the daemon built in Phase 2, falling back to an
   ordinary browser tab when no Chromium-family browser is found.
3. **A self-updater** that checks GitHub Releases, verifies a checksum, and installs
   side by side without ever writing over the running file.
4. **GIFT export** as a second format alongside the existing Anki TSV export, failing
   loudly by item number for anything GIFT cannot express.

**Explicitly not in this phase:** signed native binaries for any OS (`V2-DEL-01`
defers exe / `.app` / AppImage until a second person runs the tool); bundling a Python
interpreter (PyInstaller and Nuitka are ruled out categorically by DEL-02); any new
browser page or HTML fragment (see `02.1-UI-SPEC.md` — this phase adds none); any
behavior behind settings keys owned by later phases.

**One scope-setting fact the plan must not overstate:** `zipapp` does not bundle an
interpreter. "Double-clickable" here means "double-clickable on a machine that already
has Python 3.11+". The launcher's job when Python is missing or too old is to fail with
the exact actionable message `02.1-UI-SPEC.md` already locks — never a silent no-op.

</domain>

## Implementation Decisions

**All decisions in this section were delegated by the user.** Asked which of four gray
areas to discuss, Weibao answered: *"everything, plan the most optimal solution that
gives us the most options and directions in the future."* That is the same steering
instruction `02.1-RESEARCH.md` was written under, now applied to the four areas that

RESEARCH Choice Points 1–8 are already resolved and are **not** re-opened here. This
section covers only what research left to the user or did not reach.

### GIFT `multi` scoring divergence (RESEARCH Open Question 2)

- **D-01:** Ship **both** behaviors behind one flag rather than picking one. Default
  (`itembank export --format gift`) exports `multi` items using GIFT's weighted-answer
  encoding and prints a **non-fatal warning naming each affected item number**, stating
  the divergence (Moodle grades a partial selection as partial credit; itembank's
  scorer is dichotomous). `--strict` promotes those same warnings to loud per-item
  failures, so a bank can be exported under a correctness guarantee when that is what
  the user wants. Research leaned toward warn-and-export alone; adding the flag costs
  one branch and forecloses nothing, which is what the steering instruction asks for.
- **D-02:** `build` (ordering/sequencing) has no GIFT equivalent at all and **always**
  fails loudly by item number, in both modes. `--strict` does not change this and no
  flag makes it exportable. This is Success Criterion 5's own guarantee.
- **D-03:** `table` / `dnd` export as GIFT `matching`, per research's non-obvious
  finding that `matching` accepts repeated right-hand values. Treat RESEARCH assumption
  A1 (any minimum sub-question count) as unverified — the plan must not add a lint rule
  asserting a minimum until a live import confirms one.

### LMS import verification (RESEARCH Open Question 1)

- **D-04:** Success Criterion 5's "a real LMS importer accepts it" is satisfied by a
  **two-layer check**, so the phase can complete whether or not an LMS is reachable on
  the day it ships:
  - **Automated, always runs:** a golden-file test in `tests/gift_export_roundtrip.py`
    asserting exact GIFT output for all six item types over synthetic fixtures,
    including every character in the escape set (`~ = # { } : \`) and the loud-failure
    paths for `build` and for `multi --strict`.
  - **Manual, `checkpoint:human-verify`:** one real import. The planner names a
    concrete, zero-install target it has confirmed reachable at plan time — a free
    hosted Moodle sandbox or a local `moodle-docker` instance — rather than assuming
    Weibao has a Moodle account. Do not name a specific host in the plan without
    checking it responds first.
- **D-05:** If no importer is reachable when the phase is verified, Success Criterion 5
  is recorded **PARTIAL with the reason stated**, and the automated layer alone is
  never reported as satisfying it. `02.1-VALIDATION.md` already carries this row as
  `manual-only`; keep it that way.

### Release identity and distribution

- **D-06:** Introduce a single `__version__ = "X.Y.Z"` module constant in `itembank.py`
  (the existing entry point that already publishes `__all__`), added to `__all__`, and
  surfaced as `itembank --version`. It is the only version value any code reads — the
  updater, the startup banner, and the build script all import the same constant.
  There is no `__version__`, no `VERSION` file, and no git tag in the repo today, so
  this is new ground, not a migration.
  — **Reversibility:** costly — once the updater compares against it and a release has
  shipped, moving the value to a different file means every installed copy's comparison
  path changes; the constant is cheap to move *before* the first release, not after.
- **D-07:** Release tags are plain `vX.Y.Z` with **no pre-release or build suffixes**.
  Choice Point 7's integer-tuple comparison depends on this, and a tag like `v1.3.0-rc1`
  would break the parser. Record it as a constraint on the release process (in the
  build script's own docstring and in whatever release note the phase writes), not only
  as a code comment.
  — **Reversibility:** one-way — a suffixed tag published once is visible to every
  installed copy's updater forever; there is no way to un-publish it from a client that
  already fetched the release list. The parser must therefore **skip** a tag it cannot
  parse rather than crash on it.
- **D-08:** A `build.py` at the repo root reads `__version__`, runs `zipapp`, and emits
  `itembank-X.Y.Z.pyz` plus `SHA256SUMS.txt` in one step, so the constant, the artifact
  filename, and the checksum file can never drift apart. This is dev-time tooling, not
  runtime code.
- **D-09:** The updater does **not** hardcode the repository. It reads owner/name from
  settings (a new, non-required `update` group) with `onionviolet/itembank` as the
  default, and reads an optional token from the environment
  (`ITEMBANK_GITHUB_TOKEN`) — **never** from `itembank.json`, which is a checked-in
  file. A public repo then works with zero configuration; a private repo works by
  setting one environment variable; and the token also raises GitHub's 60-request/hour
  unauthenticated limit (RESEARCH Pitfall 2). Repository visibility was not verified
  this session and this design means the plan does not need to know it.
- **D-10:** RESEARCH Pitfall 8 is in scope for this phase: `surfaces/settings.py:27`
  reads `THIS_PHASE = 2` and `schemas/settings.schema.json`'s `update_policy` carries
  `"x-itembank-phase": 12`. Both are now wrong — update policy is read by *this* phase.
  Set `x-itembank-phase` to `2.1` for `update_policy` and any new `update` keys, and
  bump `THIS_PHASE` to `2.1`. The comparison at `surfaces/settings.py:217` is numeric
  (`phase <= THIS_PHASE`), so a float compares correctly, but the planner must confirm
  the value's other uses tolerate a non-integer before making the change rather than
  assuming it.

### Launch behavior and update installation

- **D-11:** App-mode window is a **setting, not a hardcode**. Add `daemon.window` with
  enum `["app", "tab"]`, default `"app"`. `"app"` attempts Chromium `--app=` and falls
  back to `webbrowser.open()` when no browser is found; `"tab"` always opens an
  ordinary tab. `itembank daemon` and the OS launcher then behave identically — the
  launcher gets no special-cased branch — and the behavior is switchable without a code
  change. The existing `daemon.open_browser` key still gates whether anything opens at
  all; `daemon.window` only chooses which shape.
- **D-12:** The `versions/` directory and `updates/current.json` manifest live **beside
  the running `.pyz` when that directory is writable, falling back to a per-user data
  directory** (`%APPDATA%` on Windows, `$XDG_DATA_HOME` elsewhere) when it is not. This
  keeps a portable USB / Downloads-folder copy self-contained while still allowing an
  update from a read-only install location. `surfaces/day.py:339-343` already implements
  exactly this platform-directory selection — reuse that shape, do not invent a second
  one.
- **D-13:** The schema **default** for `update_policy` stays `opt_in`, unchanged, so a
  fresh install never phones home without being asked. This repo's own checked-in
  `itembank.json` flips to `check_on_launch` so the updater gets dogfooded through
  Phases 3–11, which is the stated reason this phase was pulled forward. Two different
  values in two different places is the point: the default protects a stranger, the
  local file exercises the feature.

### Claude's Discretion

Every decision above (D-01 through D-13) plus every Choice Point in
`02.1-RESEARCH.md` is Claude's discretion under the delegated instruction. The planner
has latitude to revise any of them with a stated reason. Three specifically invite it:

- D-01's `--strict` flag name, if it collides with an existing CLI convention.
- D-09's settings-group shape, if `additionalProperties: false` plus the `required`
  array makes a non-required nested group awkward in the existing schema.
- D-12's writability probe, if a try-write-then-fall-back reads worse than an
  explicit `os.access()` check on the target platform.

## Existing Code Insights

### Reusable Assets

- `surfaces/settings.py:write_settings()` — atomic tmp-then-`os.replace` write. The
  update manifest needs exactly this and nothing more; do not write a second atomic-write
  helper.
- `surfaces/anki.py:cmd_export()` — bank load, transform, write, one status line. GIFT
  export is a second `--format` branch in this same shape, not a new command family.
- `surfaces/day.py:339-343` — platform data-directory selection, already handling both
  Windows and XDG. D-12's fallback root reuses it.
- `surfaces/daemon.py`'s two `webbrowser.open()` call sites — the tab fallback needs no
  new code, only a branch placed before them.
- `model.load()` / `runtime.canonical_key()` / `runtime.answer_text()` — GIFT export
  reads item shapes through these, never by re-parsing a bank.

### Established Patterns

- **One scorer, one parser.** GIFT export is a pure read-side transform. It must not
  reimplement any scoring rule; where GIFT's grading model disagrees with
  `runtime.score_response()`, that disagreement is *reported* (D-01), never reconciled
  by writing a second scorer.
- **Sorted, set-built code tuples.** `LINT_CODES` and `SETTINGS_CODES` are both
  `tuple(sorted({...}))` so sortedness is structural. Any new published code namespace
  this phase adds follows the same construction.
- **Named dotted error codes.** Settings errors are `settings.*`. GIFT export failures
  and update failures should follow the same convention if they publish codes at all.
- **Tests are `python tests/<name>_roundtrip.py`**, no runner, no framework. CI iterates
  `tests/*.py` directly.
- **Additive format changes only.** A bank, a settings file, or a session written before
  this phase must still load after it.

### Integration Points

- `surfaces/cli.py` — three new command surfaces: `itembank update`, `itembank export
  --format gift`, and `itembank --version`.
- `surfaces/daemon.py` `cmd_daemon` — the background update check (when
  `check_on_launch`) and the D-11 window branch both attach here.
- `schemas/settings.schema.json` — `daemon.window` (new) and the `update` group (new,
  non-required), plus the D-10 phase-number corrections.
- `build.py` (new, repo root) — dev-time only, imported by nothing at runtime.

<specifics>
## Specific Ideas

- The user's standing instruction across both this discussion and the research brief:
  *"picking best options with most room for maneuver"* / *"the most optimal solution
  that gives us the most options and directions in the future."* Where two designs cost
  about the same, take the one that keeps a door open. Where one is a one-way door,
  take the other and say why. This is why D-01 ships a flag instead of a verdict, D-09
  reads the repo from settings instead of hardcoding it, D-11 makes the window a
  setting instead of a branch, and D-13 keeps the shipped default different from the
  local one.
- Phase 2.1 exists because Weibao wanted a working double-clickable build of the
  Phase 1 + Phase 2 feature set **sooner**, and wanted the updater dogfooded through the
  remaining phases rather than written last against nothing. A plan that delays a
  runnable artifact to the end of the phase misses the point of pulling it forward.

</specifics>

<deferred>
## Deferred Ideas

- **Signed native binaries** (exe, `.app`, AppImage) and the code-signing certificates
  they need — already deferred by `REQUIREMENTS.md:154` `V2-DEL-01`, revisited when a
  second person runs the tool. A compiled native launcher stub was considered and
  rejected in RESEARCH Choice Point 2 for the same reason.
- **macOS Gatekeeper quarantine on first run** (RESEARCH Pitfall 5) — fully solving it
  requires a paid Apple Developer certificate, which is the deferred item above. This
  phase documents the right-click-Open workaround; it does not fix it.
- **A browser UI for the updater** — no page, no button, no toast. `02.1-UI-SPEC.md`
  scopes the updater to CLI text plus one background startup log line. A visible
  "update ready" affordance in the daemon's index page is a later-phase idea, and the
  UI-SPEC already reserves an accent-color treatment for it.
- **Full SemVer 2.0 precedence** (pre-release and build-metadata ordering) — deliberately
  out per D-07; revisit only if the project ever needs release candidates.

</deferred>
