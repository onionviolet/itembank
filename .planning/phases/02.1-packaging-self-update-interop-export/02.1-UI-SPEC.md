## Phase Framing — Read This First

**This phase authors almost no new browser HTML.** Confirmed by reading `02.1-RESEARCH.md`'s
own Architectural Responsibility Map and Recommended Project Structure: every one of this
phase's six requirements resolves to build-time tooling, an OS-native launcher shim, a CLI
command, or a background check — none of them stand up a new HTTP route with a rendered page.

| Requirement | UI surface | New HTML? |
|---|---|---|
| DEL-01/02 (`.pyz` build) | none — dev-time build script | No |
| DEL-03 (frameless window) | opens the daemon's **existing** `/` index page (unmodified, built in Phase 2) inside an app-mode browser window instead of an ordinary tab; falls back to `webbrowser.open()` exactly as today | No — reuse only |
| DEL-06/07 (self-update) | CLI (`itembank update`) text output, plus a silent background check at daemon launch | No — CLI/text only |
| DEL-08 (GIFT export) | CLI (`itembank export --format gift`) text output, mirroring `surfaces/anki.py:cmd_export()`'s existing pattern exactly (no browser route exists for Anki export today either) | No — CLI/text only |

So this document's real job is a **copywriting and CLI-interaction contract**, not a page
layout. The Design System / Spacing / Typography / Color sections below are declared anyway
(the template requires them, and a future task inside this phase's own scope could legitimately
need a small HTML fragment — see "If a page turns out to be needed" below) but they are
**inherited unmodified** from `surfaces/theme.py:THEME_CSS` and Phase 2's `02-UI-SPEC.md`, not
reinvented here.

**If a page turns out to be needed** (e.g. the planner decides `/` should show an "update
ready" line): it must reuse `THEME_CSS` via the `__THEME__` substitution convention every
existing page uses, the same 12.5/16/21/34px type scale, the same 8-point spacing scale, and the
same 60/30/10 color split Phase 2 already established for `/` and `/report` — never a new
palette or font stack. This document's Copywriting Contract below already specifies the exact
line of copy such a fragment would need, so the planner does not have to invent it.

## Copywriting Contract

This is the real contract for this phase. Every string below is meant to be copied into code
close to verbatim; the executor should not need to invent wording for any of these paths.
Conventions matched: `sys.exit("message")` for a hard stop (existing pattern,
`surfaces/session.py`/`surfaces/anki.py`), `print("%d items -> %s" % (...))` for a plain success
line (`surfaces/anki.py:cmd_export()`), and `"Qn: message"` for a per-item error
(`model.py:lint()`'s own convention, reused rather than a new error-line shape invented for
this phase).

| Element | Copy |
|---------|------|
| Primary CTA (CLI surface — this phase has no button/link, so its analog is the command name itself) | `itembank update` (check, download, verify, and prepare a newer version) and `itembank export --format gift` (produce a GIFT file) |
| Launcher failure — Python missing or too old (Windows `.bat`, Pitfall 6) | `itembank needs Python 3.11 or newer. Install it from https://python.org and run this file again.` then `pause` so the console window stays open long enough to read it — **[AUTO]**: a bare `.bat` that errors and immediately closes the console is a known dead-end failure mode; `pause` is the minimal fix and costs nothing |
| Launcher failure — Python missing or too old (macOS `.command`, Pitfall 6) | Same sentence via `echo`, then `read -p "Press Enter to close..."` for the same reason |
| Launcher failure — Python missing or too old (Linux, Pitfall 6 + Open Question 3) | Same sentence printed to whatever terminal invoked it; **[AUTO] known limitation, documented not silently accepted**: a `.desktop` launch with no visible terminal may show only the OS's own generic "could not run" dialog, not this message — the plan should still print it (best-effort) rather than omit it on the assumption it will never be seen |
| Update check — up to date (`itembank update`, explicit invocation) | `itembank is up to date (v<current>).` |
| Update check — new version found, at daemon launch (`check_on_launch` only, non-blocking, background) | Printed once to the daemon's own startup log, not a browser page: `A new itembank version is available: v<latest> (you're on v<current>). Run 'itembank update' to install it.` |
| Update in progress (`itembank update`, found + downloading) | Three sequential lines, not a spinner: `Downloading itembank v<latest>...` / `Verifying checksum...` / `Installed v<latest> at <path>. Run itembank again to use it.` — **[AUTO]**: matches Choice Point 6's side-by-side design (the running process is never replaced mid-run), so the copy says "run it again," never "relaunching now," to avoid implying an automatic process swap that Choice Point 6 deliberately does not do inside the update command itself |
| Update check — offline/unreachable, `check_on_launch` (background, DEL-07) | **No output at all.** DEL-07's own text: "fails silently when offline" — a printed line here would contradict the requirement |
| Update check — offline/unreachable, explicit `itembank update` (user-initiated) | `Could not reach GitHub to check for updates (offline, or the connection failed). Try again later.` — **[AUTO]**: DEL-07's silence rule is scoped to the *background* check; a user who explicitly typed a command and got no feedback at all cannot tell "you're current" from "the check failed," so an explicit invocation must say which one happened |
| Update check — rate-limited (Pitfall 2), explicit `itembank update` only | `GitHub rate-limited this check -- try again later.` — background `check_on_launch` stays silent for this case too, same as any other offline/unreachable outcome, per DEL-07 |
| Update — checksum verification failed | `Downloaded update failed checksum verification -- discarding it. Nothing was installed. (expected sha256:<first 12 hex chars>..., got sha256:<first 12 hex chars>...)` — truncated digest, not the full 64 hex chars, to keep the line scannable; full values available via `--verbose` if the plan adds one, otherwise this line is sufficient |
| Update — offered version not strictly newer (downgrade rejection, Success Criterion 4) | `v<offered> is not newer than the version you're running (v<current>) -- not installing it.` |
| GIFT export — success, nothing skipped | `%d items -> %s` — **[AUTO] verbatim reuse** of `surfaces/anki.py:cmd_export()`'s own line 42 pattern, so GIFT export reads as the same family of command as the existing Anki export, not a differently-voiced new feature |
| GIFT export — per-item loud failure, `build` type (DEL-08, Success Criterion 5) | `Q<n>: type 'build' (ordering) has no GIFT equivalent -- not exported` — **[AUTO]** follows `model.py:lint()`'s own `"Qn: message"` shape exactly (RESEARCH.md's Code Examples section already drafts this identical line; adopted verbatim here as the locked contract rather than left as an example) |
| GIFT export — per-item loud failure, unresolvable escaping ambiguity | `Q<n>: <field> contains a character sequence GIFT export cannot safely escape -- not exported` — same `Qn:` shape; `<field>` names the specific field (`stem`, `option B`, `why`, etc.) so the author knows exactly what to fix |
| GIFT export — `multi` (pick-N) items, Choice Point 9 | **[AUTO] resolves Choice Point 9 as option 1** (warn-and-proceed, per RESEARCH.md's own lean and the steering instruction's "most room for maneuver" framing — a warning keeps the export usable while still surfacing the divergence, rather than foreclosing GIFT export entirely for any bank containing a `multi` item): `Q<n>: type 'multi' exported as GIFT weighted-answer choices -- a learner selecting only some of the correct options may score partial credit in the LMS, where itembank's own scorer would mark it wrong. Export kept; verify against your LMS if this matters.` Printed as a non-fatal warning (item is still written to the file), never a `Qn: ... -- not exported` line, since it IS exported. **Flag for the planner**: RESEARCH.md's Open Question 2 asks whether Weibao would actually prefer this behavior over the stricter option 2 (fail loudly like `build`); this auto-resolution should be confirmed at plan or execute time, not treated as unappealable |
| GIFT export — whole-bank abort (lint errors present, no `--force`) | `refusing to export a bank with errors; fix them or pass --force` — **[AUTO] verbatim reuse** of `surfaces/anki.py:cmd_export()` line 20, unchanged |
| GIFT export — summary line when any items were skipped | `%d items exported, %d skipped (see above) -> %s` — **[AUTO]**: distinct from the all-clear success line specifically so a partial export never reads as if everything succeeded; this is the concrete mechanism behind Success Criterion 5's "fails loudly... rather than exporting silently wrong" |
| Empty state | Not applicable this phase — no list-collection UI (browser-rendered) is authored; the closest analog, GIFT export's per-item error list, has no "empty" state of its own (zero errors just means the success line above, not an empty-list render) |
| Destructive confirmation | **None in this phase's scope.** Self-update never overwrites the running file (Choice Point 5's side-by-side layout) and requires no confirmation before download+verify (a failed checksum is silently discarded before it could do damage). GIFT export only ever writes a new output file, matching `anki.py`'s own no-confirmation precedent — same resolution Phase 2's `02-UI-SPEC.md` reached for `config set`. |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5). Because this phase authors no
> browser HTML, the elements classified below are the CLI-rendered text surfaces this phase
> does add — treated as first-class "UI" per this project's own framing (`.claude/CLAUDE.md`:
> "every capability has both a route in the daemon and a command in the CLI... Neither surface
> is the real one"). Element kinds are assigned by analogy: a CLI print sequence is
> `static-content`; the GIFT export's per-item error lines are a `list-collection` (a variable-
> length list of `Qn: message` rows).

Applicable state considerations resolved: 7 covered, 2 backstop, 0 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | GIFT export error list (list-collection: per-item `Qn:` failure lines) | ✅ covered | Zero errors renders no error lines at all — just the plain `%d items -> %s` success line, never an empty error section header with nothing under it |
| zero-one-many | GIFT export error list | ✅ covered | One skipped item and many skipped items render the identical `Qn: message` row shape (no singular/plural copy branch), and the summary line's own `%d skipped` count is correct at any N including zero (zero skipped uses the plain success line instead, not `"0 skipped"`) |
| long-text | GIFT export error list (item stems/field names inside `Qn:` lines) | ✅ covered | Plain-text terminal output — content reflows with the terminal's own line wrapping; no truncation/ellipsis logic is introduced, matching the project's existing no-truncation convention (Phase 2's `02-UI-SPEC.md` established the same rule for its list rows) |
| overflow | GIFT export error list (a bank with many `build`/unresolvable items) | 🧪 backstop | Plain sequential stdout lines have no container to overflow — held out as backstop because it was not manually exercised against a fixture bank with a large `build`-item count this session; confirmed at UAT with a fixture carrying 10+ `build` items |
| error | Update check (offline/unreachable/rate-limited, explicit `itembank update`) | ✅ covered | Each distinct failure (offline, rate-limited, checksum-failed, downgrade-rejected) has its own documented line above — no single generic "something went wrong" message covers multiple causes |
| error | Update check (offline/unreachable, background `check_on_launch`) | ✅ covered — dismissed | No output at all is the correct resolution here (DEL-07's explicit "fails silently" requirement); dismissal reason: "silence is the documented behavior, not a gap" |
| error | Launcher (Python missing/too old, all three OS shims) | ✅ covered | Each OS has its own documented message + a mechanism to keep the failure visible (`pause` / `read -p`) rather than a console that flashes and closes |
| loading | Update download (`itembank update`, found + downloading) | ✅ covered — dismissed | Three sequential printed lines (Downloading.../Verifying.../Installed...) substitute for a spinner — dismissal reason: "CLI text-sequence progress matches every other long-running command in this codebase (e.g. `migrate`'s own progress prints); no spinner/progress-bar convention exists anywhere in the project to introduce here" |
| loading | Frameless window open (DEL-03, browser subprocess launch) | 🧪 backstop | The daemon already shows its own `url`/`bound` startup lines before attempting to open a browser (existing `surfaces/daemon.py` behavior, unmodified); whether a slow browser cold-start needs any additional "opening..." text was not resolved this session — held out as backstop, confirmed at UAT by timing a cold Chrome launch against the existing startup log |

### Decision: no new HTML page this phase — **[AUTO] confirmed, not silently assumed**

RESEARCH.md's own Architectural Responsibility Map already places every one of this phase's
capabilities outside the "API/Backend... daemon" or "Browser/Client... presentation" tiers that
would imply a rendered page, except for DEL-03, which explicitly reuses the existing page
unmodified. Nothing in `REQUIREMENTS.md`'s DEL-01/02/03/06/07/08 text or their success criteria
asks for a new browser-visible page. This document records that as a considered decision
(matching Phase 2's own "Decision: `/settings` HTML page" precedent) rather than an omission: if
the planner later decides an "update ready" indicator on `/` is worth the scope, the exact copy
line to use is already specified above (Update check — new version found), and the visual system
to render it in is already specified in the Spacing/Typography/Color sections above — it would
not require a new design-contract question, only a planner decision to build it.
