# Phase 02.1: Code Review Report

**Reviewed:** 2026-08-08T00:00:00Z
**Depth:** standard
**Files Reviewed:** 29

## Summary

Reviewed the packaging/self-update/interop/export deliverables: `build.py`, `resources.py`,
`schema_validate.py`, the two new JSON schemas, `surfaces/gift.py`, `surfaces/launcher.py`,
`surfaces/update.py`, the three OS launcher shims, the wiring changes in `surfaces/cli.py`,
`surfaces/daemon.py`, `surfaces/day.py`, `surfaces/anki.py`, `surfaces/protocol_cli.py`,
`surfaces/session.py`, `itembank.py`, and the associated tests/fixtures.

The bulk of this code is careful and well-tested: `install()`'s verify-then-position sequence,
the `.part`-then-`os.replace()` write, the version-string comparison, the asset-name basename
reduction, and `handoff()`'s guard chain are all exactly as documented and are backed by
targeted tests in `tests/update_roundtrip.py`. GIFT export, settings validation, and the
launcher container logic are similarly solid.

Three problems undercut the module's own stated guarantees, however: a credential leak in
`download_asset()` via unstripped `Authorization` headers on cross-origin HTTP redirects (the
project's explicit review focus), a background-check rate-limit guard that never actually
engages for a fresh install because no manifest is ever written on a "nothing to compare
against yet" check, and a shipped `itembank.json` whose `update_policy` value contradicts the
schema's own declared "opt_in" default -- meaning every fresh checkout of this repository
already has unconsented background network checks turned on out of the box, the exact
outcome `surfaces/update.py`'s own docstrings say must never happen without explicit consent.

## Critical Issues

### CR-01: `download_asset()` forwards the GitHub token to a third-party host on redirect

**File:** `surfaces/update.py:360-381` (also affects `_checksum_fallback()` at `surfaces/update.py:497-522`, which calls `download_asset()` the same way)

**Issue:** When `ITEMBANK_GITHUB_TOKEN` is set, `download_asset()` sends an `Authorization: Bearer <token>` header to `url` (a release asset's `browser_download_url`, e.g. `https://github.com/OWNER/REPO/releases/download/TAG/FILE`). GitHub's release-asset download endpoint responds with a 302 to a different host -- typically `objects.githubusercontent.com` with a signed, pre-authenticated query string that needs no bearer token at all. Python's stdlib `urllib.request.HTTPRedirectHandler.redirect_request` (verified directly against this project's own Python 3.11.9 interpreter) only strips `Content-Length`/`Content-Type` on redirect; it does **not** strip `Authorization`, `Accept`, or any other custom header, and does not check whether the redirect target's host differs from the original request's host:

```
newheaders = {k: v for k, v in req.headers.items()
              if k.lower() not in CONTENT_HEADERS}   # CONTENT_HEADERS = ("content-length", "content-type")
return Request(newurl, ..., headers=newheaders, ...)
```

So a bearer token scoped to `ITEMBANK_GITHUB_TOKEN` -- explicitly documented in this same module as a secret that "never comes from itembank.json, a printed line, or a log" -- is transmitted verbatim to whatever third-party origin GitHub's CDN redirects to. `tests/update_roundtrip.py`'s `test_token_never_comes_from_the_settings_file` only checks that the *initial* request built by `check_latest()` omits `Authorization` when no env var is set; it never exercises `download_asset()`'s redirect path, so this leak has no test coverage today.

**Fix:** Do not send `Authorization` on the asset-download request at all (public release assets need no auth), or build and use a redirect handler/opener that strips `Authorization` whenever the redirect target's host differs from the request's original host:

```python
class _NoCrossHostAuthRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, req, fp, code, msg, headers, newurl):
        new_req = super().redirect_request(req, fp, code, msg, headers, newurl)
        if new_req is not None:
            old_host = urllib.parse.urlsplit(req.full_url).hostname
            new_host = urllib.parse.urlsplit(new_req.full_url).hostname
            if old_host != new_host:
                new_req.remove_header("Authorization")
        return new_req

_opener = urllib.request.build_opener(_NoCrossHostAuthRedirect)
...
with _opener.open(req, timeout=timeout) as resp:
    ...
```

Add a redirecting-stub test to `tests/update_roundtrip.py` asserting the header is absent on the second (cross-host) request.

### CR-02: `background_check()` never establishes a rate-limit baseline on a fresh install, so it makes an unthrottled request on every launch

**File:** `surfaces/update.py:608-663`, specifically the manifest-refresh block at lines 642-650

**Issue:** `should_check(base, interval_hours)` (lines 276-294) returns `True` whenever `read_manifest(base)` is `None` -- i.e. no manifest has ever been written. `background_check()` is documented to "reset should_check's clock" after every completed check so a shared network is not asked again until the interval elapses, but the actual write is conditional on an *existing* manifest:

```python
existing = read_manifest(root)
if existing is not None:
    write_manifest(root, existing.get("version"), existing.get("path"),
                   existing.get("sha256"))
```

On a totally fresh install (no `itembank update` has ever been run, so no manifest exists), `existing` is `None` and nothing is written -- not even a bare "checked_at" record. The next `itembank daemon` launch calls `should_check()` again, finds no manifest, and makes another GitHub request, indefinitely, once per launch, regardless of `check_interval_hours`. This directly defeats DEL-07's stated purpose ("does not exhaust a 60-per-hour budget across every learner's every launch... a shared campus or dorm network"), and is not caught by `tests/update_roundtrip.py::test_background_check_is_silent_on_every_failure`, which only asserts single-call behavior, never a second call against the same (still-manifest-less) `base`.

This compounds directly with CR-03 below: the shipped `itembank.json` already sets `update_policy: check_on_launch`, so this unthrottled path is live for anyone using the repo's own checked-in defaults.

**Fix:** Write a manifest (or a lighter "last checked" record) unconditionally after a completed check, using the currently-running version as the placeholder when no install has ever recorded one:

```python
existing = read_manifest(root)
if existing is not None:
    write_manifest(root, existing.get("version"), existing.get("path"),
                   existing.get("sha256"))
else:
    import itembank
    write_manifest(root, itembank.__version__, "", "")
```

(Adjust `update_manifest.schema.json`'s `minLength: 64` on `sha256` and `required` list if an empty placeholder is used, or introduce a separate `last_checked_at`-only sentinel file so the manifest's own contract -- "names the version and artifact this installation currently trusts" -- is not stretched to cover "nothing has ever been installed.")

### CR-03: Shipped `itembank.json` enables unconsented background update checks by default, contradicting the schema's own declared default

**File:** `itembank.json:15`, cross-referenced against `schemas/settings.schema.json:104-110`

**Issue:** The schema declares `update_policy`'s default as `"opt_in"` (`schemas/settings.schema.json:108`), and `surfaces/update.py:may_check()` documents this as "the mechanical half of the consent prohibition." But this phase's own commit (`5859e07`) changed the repository's checked-in `itembank.json` from `"update_policy": "opt_in"` to `"update_policy": "check_on_launch"`:

```json
"update_policy": "check_on_launch",
```

Since `SETTINGS_FILE = "itembank.json"` is read from the current working directory, and the README's own "Install" section instructs `git clone <this repo>` followed by running `python itembank.py` directly from the checkout, every fresh clone of this repository ships with automatic background GitHub checks turned on -- with no explicit `itembank update` invocation and no learner action beyond cloning. This is precisely the outcome `may_check()`'s docstring says must never happen ("a fresh install that was never asked to update -- this is always `False`"), and it is inconsistent with the project's stated "no telemetry" / degrade-never-block network posture in `CLAUDE.md`. Combined with CR-02, a learner who never runs `itembank update` gets an unthrottled background request on every single `itembank daemon` launch, from the moment they clone the repo.

**Fix:** Revert `itembank.json`'s `update_policy` to `"opt_in"` (matching the schema's own default), or, if `check_on_launch` is intentionally the shipped default going forward, update `schemas/settings.schema.json`'s `default` for `update_policy` to match and document the consent-model change explicitly (README, CLAUDE.md) rather than leaving the schema and the shipped file silently disagreeing.

## Warnings

### WR-01: `cmd_update` reports "up to date" even when a genuinely newer release exists but carries no matching asset

**File:** `surfaces/update.py:571-574`

**Issue:**

```python
if (asset is None or offered is None or running_parsed is None
        or offered == running_parsed):
    print("itembank is up to date (%s)." % running_display)
    return 0
```

`asset is None` (no release asset name matches `_ASSET_RE`) is folded into the same branch as "genuinely up to date." If a release is tagged with a newer, valid `vX.Y.Z` but the uploaded asset is misnamed, missing, or renamed (a packaging mistake on the publishing side), a learner running `itembank update` is told they are already current -- silently masking a real release they cannot get without noticing something is wrong.

**Fix:** Distinguish the two cases with different copy, e.g. "A newer release (%s) exists but has no downloadable artifact for this platform -- check the release page directly," while still exiting 0 (no automated action is possible either way).

### WR-02: `read_manifest()` does not guard against `SchemaError` or a missing bundled schema resource, contradicting its own "never raises" contract

**File:** `surfaces/update.py:187-202`

**Issue:** The docstring promises `read_manifest()` "never raising," yet the body only catches `(OSError, ValueError)` around the manifest file read:

```python
schema = json.loads(resources.read_text(MANIFEST_SCHEMA_RESOURCE))
if schema_validate.validate(raw, schema):
    return None
return raw
```

`resources.read_text()` raises `FileNotFoundError` if `schemas/update_manifest.schema.json` is missing from a corrupted install or a `.pyz` built with a stale `STAGE_DIRS`/`STAGE_FILES` list, and `schema_validate.validate()` calls `check_schema()` internally, which raises `SchemaError` on any schema document using an unsupported keyword. Either would propagate out of `read_manifest()`, out of `should_check()`, into `background_check()`'s outer `try/except Exception` (which does catch it) -- but `read_manifest()` is also called directly by `handoff()` (wrapped) and by tests expecting `None` on any corruption, not an exception. This is defense-in-depth rather than an observed failure today (the schema file is well-formed), but it is exactly the kind of "must never raise on startup" contract this module is built around everywhere else.

**Fix:**
```python
try:
    schema = json.loads(resources.read_text(MANIFEST_SCHEMA_RESOURCE))
    if schema_validate.validate(raw, schema):
        return None
except (OSError, ValueError, schema_validate.SchemaError):
    return None
return raw
```

### WR-03: README.md was not updated for this phase's new commands

**File:** `README.md` (`## Use` section, lines 86-103)

**Issue:** This phase adds `itembank config` (`surfaces/settings.py`), `itembank update` (`surfaces/update.py`), `itembank daemon` (`surfaces/daemon.py`), GIFT export (`itembank export --format gift`), and a top-level `--version` flag (`surfaces/cli.py`), plus the "Install and run (release)" packaging story that `build.py` now produces. None of these appear in the `## Use` command list, and the existing "Install" section still describes only `git clone` + `python itembank.py --help` without pointing to the release/launcher workflow the "Install and run (release)" section (which does exist further down) actually documents. A reader working from the `## Use` block alone would not discover `config`, `update`, `daemon`, or `--format gift` exist at all.

**Fix:** Add `itembank config`, `itembank update`, `itembank daemon`, and the `--format gift` variant to the `## Use` command list, and add `--version` to the flag/usage summary.

**File:** `surfaces/settings.py:145-151`

### IN-02: `_ASSET_RE` uses `$` instead of `\Z`, allowing a one-character trailing-newline bypass

**File:** `surfaces/update.py:315`

**Issue:** `_ASSET_RE = re.compile(r"^itembank-\d+\.\d+\.\d+\.pyz$")`. Python's `re` module treats `$` (without `re.MULTILINE`) as matching at the end of the string *or* immediately before a single trailing `\n`. A release asset named `itembank-9.9.9.pyz\n` (a GitHub asset name is an arbitrary JSON string; nothing prevents a trailing newline) would pass `pick_asset()`'s validation and later be joined into a real filesystem path via `os.path.join(versions_dir, name)`, landing a file with an embedded newline in its name. This is not a traversal (no `/` or `..` survives `os.path.basename()`) and has no known exploitation path here, but it is a real gap in the "only this project's own build shape is accepted" guarantee the surrounding comment claims.

**Fix:** Anchor with `\Z` instead of `$`: `re.compile(r"^itembank-\d+\.\d+\.\d+\.pyz\Z")`.
