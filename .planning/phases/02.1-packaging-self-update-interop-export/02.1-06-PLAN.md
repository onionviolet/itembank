<objective>
Build the half of GIFT export that refuses: `build` items that GIFT cannot express, fields that cannot
be safely escaped, and — under `--strict` — `multi` items whose LMS grading would disagree with the
one scorer. Then take the export to a real LMS importer and find out whether it is accepted.

Purpose: Success Criterion 5 is two claims, and this plan is the second one. "Fails loudly, by item
number, rather than exporting silently wrong" is only true if a partial export looks different from a
complete one to a script as well as to a reader, and only provable against an importer that is not
this codebase.

Output: the loud-failure paths in `surfaces/gift.py`, a build-only fixture, the tests that pin them,
and the recorded outcome of a real Moodle import.
</objective>

Add `GIFT_CODES` as a `tuple(sorted({...}))` in the `gift.` dotted namespace, matching
`SETTINGS_CODES`' construction so sortedness is structural: a code for the unexpressible item type, a
code for the unexpressible field, and a code for the strict-mode scoring-divergence refusal. Each
per-item message is prefixed by its code the same way the settings surface prefixes its own, so a
consumer can branch on the code rather than on the English after it.

**The build refusal.** In `gift_item`, an item whose type is `build` appends the locked refusal line —
the item number, then the statement that ordering has no GIFT equivalent, then the not-exported
marker — to `errors` and returns `None`. This happens in both modes. Do not add a flag, a force
escape, or a degraded ordering encoding: GIFT has no ordering type, and an approximation that reorders
into something else is exactly the silently-wrong export Success Criterion 5 forbids.

**The unexpressible-field refusal.** Add `unexpressible_field(q)`, returning the name of the first
field that cannot be safely written or `None` when every field is fine. A field is unexpressible when,
after escaping, it still carries a character that would restructure the GIFT document — in practice a
line break or a carriage return, because GIFT's answer blocks are line-oriented and no backslash
escape rescues an embedded newline. Check every field each renderer writes, and name them the way an
author would recognise them: the stem, an option by its letter, a matching row by its position, the
category, the short model answer, the general feedback. `gift_item` calls it before dispatching and,
on a non-`None` result, appends the locked refusal line naming that field and returns `None`.

**Strict-mode promotion.** In the multi branch, when `strict` is set, append the same divergence
statement as a per-item failure in the `not exported` shape to `errors` and return `None` instead of
rendering. When `strict` is not set, keep plan 02.1-04's behaviour exactly: render the item and append
the warning. The two modes share one sentence about what diverges and differ only in whether the item
is written and which list the message lands in.

**The summary and the exit code.** In `export_gift`, print each warning and each error as its own
console line before the summary, in item order, with no section header above them — zero errors must
render nothing at all rather than an empty header. Then choose the summary line: the locked all-clear
line when nothing was skipped, and the locked exported-and-skipped line naming both counts and the
path when anything was. Return one when anything was skipped and zero otherwise. The per-item row
shape is identical for one skipped item and for many: no singular or plural copy branch, and no zero
count printed when nothing was skipped.

The output file is written even when every item was skipped — an empty GIFT document plus a loud
summary and a non-zero exit is a more useful state than a missing file, because it makes the
"nothing was expressible" case visible in the same place as every other outcome.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bank markdown → GIFT document | Author-controlled text that cannot be safely escaped must be refused rather than written |
| GIFT document → external LMS | A file this tool writes is parsed and graded by a system outside this project's control |
| exported file → hosted Moodle sandbox | Item text crosses to a third-party demo host during the manual verification |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.1-25 | Tampering | unescapable field | high | mitigate | `unexpressible_field` refuses any item whose escaped field still carries a line break, naming the field, rather than writing a document whose structure the importer would read as different questions than the author wrote |
| T-02.1-26 | Repudiation | partial export mistaken for complete | high | mitigate | A skipped item forces the distinct exported-and-skipped summary line and a non-zero exit code, so neither a reader nor a calling script can mistake a partial export for a complete one |
| T-02.1-27 | Information Disclosure | manual import to a public demo host | medium | mitigate | The manual verification uses the synthetic fixture banks this repository ships, never a real course bank. The demo sandbox is a public host that resets on a schedule; no learner evidence and no private bank is uploaded |
| T-02.1-28 | Tampering | strict-mode bypass | medium | mitigate | The `build` refusal is unconditional and shares no flag with the strict-mode promotion, so no combination of flags can make an ordering item exportable |
| T-02.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — this plan installs no package from any registry and adds no dependency |
</threat_model>
