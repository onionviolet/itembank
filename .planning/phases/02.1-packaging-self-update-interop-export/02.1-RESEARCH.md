## Summary

This phase has almost no third-party-library surface — the CLAUDE.md constraint
("Python standard library only... no install step") is achievable for every piece of
this phase except the frameless window, where the only real GUI-webview library
(`pywebview`) requires a pip install and per-OS system packages. The recommended path
threads that needle by shelling out to whatever Chromium-family browser is already
installed on the machine, in `--app=` mode — a zero-dependency technique with a
well-known, readable prior-art implementation (the `eel` package's `chrome.py`) that
this project can read and adapt rather than depend on.

One critical scope-setting finding: **`zipapp` produces a `.pyz` file that still
requires a Python interpreter already installed on the target machine** to run at all —
there is no bundling of the interpreter itself (that is what PyInstaller/Nuitka do, and
both are explicitly ruled out by DEL-02's "no build step, still plain Python inside"
requirement, and by `REQUIREMENTS.md`'s own v2 line: `V2-DEL-01: Signed binaries — exe,
.app, AppImage — revisited when a second person runs the tool`
[VERIFIED: `.planning/REQUIREMENTS.md:154`]). This phase's "double-clickable" is
therefore "double-clickable on a machine that already has Python 3.11+," not a
Python-free installer. That is consistent with a one-learner tool being packaged for
its own author, and it is exactly what the v2 line defers — but the planner should not
let a task description imply more than this delivers, and the launcher's job is to
fail with a clear, actionable message (not a silent double-click no-op) when Python is
missing or too old.

The GitHub Releases `digest` field was live-verified this session against a real
repository's API response (`cli/cli`) — it exists, is populated, and has the exact
shape `sha256:<64-hex-chars>` on the asset object. This resolves the ROADMAP's flagged
open decision directly: build the checksum verification path around
`asset["digest"]`, and ship a `SHA256SUMS.txt` release asset as a cheap, redundant
fallback (the digest field returns `null` for any asset uploaded before the feature's
June 2025 GA, so a defensive `is None` check is required even though itembank's own
future releases will all postdate that).

GIFT research produced one non-obvious, decision-changing finding: Moodle's `matching`
question type accepts **repeated right-hand answers across sub-questions**, which
makes it a structural match for itembank's `table`/`dnd` type (many rows into a
handful of shared categories) — not a "cannot express" case as a naive reading of
GIFT's five-type list would suggest. The only itembank item type genuinely
inexpressible in GIFT is `build` (ordering/sequencing has no GIFT equivalent at all).
`multi` (pick-N, dichotomous) is structurally expressible via GIFT's weighted-answer
mechanism but with a real scoring-semantics divergence from itembank's all-or-nothing
scorer that the planner must decide how to surface (flagged as an explicit choice
point, not silently resolved here).

**Primary recommendation:** Build the `.pyz` with stdlib `zipapp` (no compression
flag needed at this size), ship one thin OS-native launcher per platform that shells
out to `py`/`python3` explicitly rather than relying on file-association state, open
the daemon in a Chromium `--app=` window with OS-appropriate browser-path detection
(never `pywebview`), implement the updater as a side-by-side `versions/` directory
plus a small JSON pointer manifest (never symlinks, never `os.execv` on Windows), and
extend `surfaces/anki.py`'s existing export pattern with a `gift` format that fails
loudly, by item number, only for `build` items and for any character-escaping
ambiguity it cannot resolve.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| `.pyz` packaging (build-time) | Build/Distribution (offline, dev-time tooling) | — | Not a runtime concern; a `python -m zipapp` invocation, likely wrapped in a small `build.py`/Makefile-equivalent script, that runs before a release is cut |
| Per-OS double-click launcher | Browser/Client (native OS shell) | CLI (the `.pyz`'s own `__main__.py` entry point it invokes) | The launcher is a thin OS-native shim (`.bat`/`.command`/`.desktop`); all real logic still lives in the `.pyz`, invoked as a subprocess by the shim |
| Frameless app window | Browser/Client | API/Backend (the daemon it points at) | Purely a client-side presentation choice over the existing HTTP daemon; the daemon (`surfaces/daemon.py`) is completely unaware whether it's rendered in a tab or an app-mode window |
| Self-update (check/download/verify/swap) | CLI/Backend (local process, no server component) | — | Runs either as an explicit `itembank update` command or as a startup check inside `cmd_daemon`/the launcher; touches the filesystem only, never the daemon's HTTP surface |
| GIFT export | API/Backend (pure data transform) | — | Mirrors `surfaces/anki.py`'s existing `cmd_export`: reads a bank via `model.load()`, writes a text file; no server, no browser involvement |

## Choice Points (Claude's Discretion — steering-instruction-driven)

Each of these was an open implementation choice with no locked user decision. Per the
steering instruction, the more reversible / more capable-at-similar-cost option was
picked, and is called out here rather than silently baked into the plan.

### Choice Point 1 — `.pyz` build tool: locked, not actually a choice
DEL-01's own text names `zipapp` explicitly ("built with stdlib `zipapp`"). No
alternative considered; `PyInstaller`/`Nuitka`/`briefcase` are ruled out categorically
by DEL-02 ("still plain Python inside... without unpacking a build step") since all
three compile or freeze the interpreter into the artifact.

### Choice Point 2 — per-OS launcher shape
**Recommendation:** ship all three, each explicitly invoking the interpreter rather
than trusting file-association state (association can be missing, stale, or
overridden by another Python install):
- **Windows:** a `.bat` file — `py -3 "%~dp0itembank.pyz" %*` — alongside the raw
  `.pyz` (which Windows *does* associate automatically at Python-install time per
  `docs.python.org`, CITED below, but a `.bat` is a strictly cheaper, more robust
  safety net and costs nothing to also ship).
- **macOS:** a `.command` file — `#!/bin/bash\ncd "$(dirname "$0")" && exec python3
  itembank.pyz "$@"` — chmod +x. Gatekeeper's quarantine flag on downloaded files is
  a known first-run friction point (see Pitfall 6); solving it fully requires a paid
  Apple Developer signing certificate, explicitly out of v1 scope per
  `V2-DEL-01` [VERIFIED: `.planning/REQUIREMENTS.md:154`].
- **Linux:** a `.desktop` file (double-click-from-file-manager reliability varies too
  much across desktop environments to trust a bare executable-with-shebang alone,
  per this session's research), *and* the `.pyz` itself stays `chmod +x` with its
  `/usr/bin/env python3` shebang so `./itembank.pyz` also works from any terminal —
  both are cheap, and having both is strictly more capable at near-zero added cost
  (steering instruction's "lean toward the more complete option where the cost
  difference is small").

**Why not a compiled native stub (e.g., a tiny C launcher) instead:** more capable in
theory (removes the Python-preinstalled dependency for the launcher itself, though not
for the `.pyz` it invokes) but a genuine one-way door — it reintroduces a
per-OS build toolchain and compiled-binary distribution problem this phase exists to
avoid, and duplicates work `V2-DEL-01`'s signed-binaries line already earmarks for a
later milestone. Rejected.

### Choice Point 3 — frameless window mechanism
**Recommendation:** shell out to an installed Chromium-family browser (`Chrome`,
`Edge`, or `Chromium`, in that preference order) with the `--app=<url>` flag via
`subprocess.Popen`, falling back to stdlib `webbrowser.open()` for an ordinary tab
when none is found. **Do not use `pywebview`.**

**Why:** `pywebview` requires a pip install and, per this session's research, real
per-OS system dependencies beyond that — `pythonnet`/WebView2 runtime on older
Windows, `pyobjc-framework-WebKit` and friends on a non-bundled macOS Python, and
`PyGObject`/GTK + WebKit2 dev packages on Linux
[CITED: `pywebview.flowrl.com/guide/installation.html`, cross-checked via
`github.com/r0x0r/pywebview`]. That would open a **third** named exception to the
"Python standard library only" constraint (joining vendored KaTeX and stdlib
`urllib`), and unlike those two, it is not reversible without touching how the daemon
is launched on every platform. Package-legitimacy check flags it `SUS` (see Package
Legitimacy Audit) purely on a downloads-signal data gap, not on any real integrity
concern — it is a long-established, actively maintained project — but the
stdlib-only violation stands regardless of legitimacy.

The `--app=` shell-out is the same technique the `eel` package (an established,
MIT-licensed prior-art project solving exactly this problem) implements internally in
its `chrome.py` module [CITED:
`github.com/samuelhwilliams/Eel/blob/main/eel/chrome.py`] — worth reading directly as
a reference rather than depending on the whole `eel` package, which itself still
requires a pip install.

**Caveat for the planner:** a Chrome/Edge `--app=` window is not literally
borderless — it keeps the OS title bar (minimize/maximize/close) but hides the
browser's own chrome (tabs, address bar, bookmarks bar). That is the conventional
meaning of "frameless app window" in this space (confirmed by both the `eel` prior
art and general web search results), and matches Success Criterion 1's intent, but
should not be read as a literal kiosk-mode borderless window — `--kiosk` exists but
removes the user's ability to close/resize normally, which is a worse UX for a study
tool the learner opens and closes repeatedly.

### Choice Point 4 — browser-path detection strategy
**Recommendation:** layer three lookups, cheapest first:
1. `shutil.which("chrome"/"msedge"/"chromium"/...)` — stdlib, fast, POSIX-friendly.
2. OS-specific known-location probe when (1) fails:
   - **Windows:** query the registry `App Paths` key via stdlib `winreg` —
     `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\chrome.exe` (and
     `msedge.exe`) — this is the same mechanism `eel`'s `chrome.py` uses [CITED], and
     it was **live-verified on this session's own Windows 11 dev machine**: `reg
     query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App
     Paths\chrome.exe"` returned `(Default) REG_SZ C:\Program
     Files\Google\Chrome\Application\chrome.exe`, and the same for `msedge.exe`
     [VERIFIED: live `reg query` this session]. Critically, **`where chrome` and
     `where msedge` both failed on this same machine** despite both browsers being
     installed at their standard paths — confirming `shutil.which()` alone is
     insufficient on Windows and the registry probe is not optional.
   - **macOS:** fixed paths (`/Applications/Google Chrome.app/Contents/MacOS/Google
     Chrome`, `/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge`) with
     an `mdfind` fallback for non-default install locations, mirroring `eel`'s
     approach [CITED].
   - **Linux:** `shutil.which()` across a short list of common binary names
     (`google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser`,
     `microsoft-edge`) — `eel` uses a third-party `whichcraft` package for this same
     job; itembank should use stdlib `shutil.which` instead, which is equivalent for
     this purpose and keeps the stdlib-only guarantee.
3. Neither found → stdlib `webbrowser.open()`, an ordinary tab — this is the exact
   function `surfaces/daemon.py` already calls today at two call sites
   (`webbrowser.open(url)` at line 1015, and `threading.Timer(0.4, lambda:
   webbrowser.open(url)).start()` at line 1072
   [VERIFIED: `surfaces/daemon.py:1015`, `surfaces/daemon.py:1072`]) — so the
   fallback path requires no new code, only branching before those existing calls.

### Choice Point 5 — self-update side-by-side layout and swap mechanism
**Recommendation:** a `versions/` directory holding every downloaded `.pyz` by
version-qualified filename (e.g. `versions/itembank-1.3.0.pyz`), plus a small JSON
pointer manifest (e.g. `updates/current.json`, `{"version": "1.3.0", "path":
"versions/itembank-1.3.0.pyz"}`) written with the exact tmp-then-`os.replace()`
pattern `surfaces/settings.py`'s `write_settings()` already implements
[VERIFIED: `surfaces/settings.py:110-122`, quoted below]. The launcher (or the
daemon's own relaunch code) reads this manifest to decide which `.pyz` to invoke next
time — the currently-running file is never opened for writing, satisfying Success
Criterion 3 structurally rather than by convention.

```python
# surfaces/settings.py:110-122 (VERIFIED, quoted verbatim — the pattern to reuse,
# not reinvent, for the update-manifest write)
def write_settings(base, data):
    target = settings_path(base)
    target_dir = os.path.dirname(os.path.abspath(target))
    os.makedirs(target_dir, exist_ok=True)
    tmp = target + ".tmp"
    with open(tmp, "w", encoding="utf-8") as fh:
        json.dump(data, fh, ensure_ascii=False, indent=2)
        fh.write("\n")
    os.replace(tmp, target)
```

**Why not a symlink** (e.g. `itembank-current.pyz -> versions/itembank-1.3.0.pyz`):
POSIX symlinks are trivial, but Windows symlinks require either Administrator
privilege or Developer Mode enabled (pre-Windows-10-1703 always required admin) — a
real one-way UX cost on the one OS this project's own dev machine runs. A JSON
pointer file needs no privilege on any OS and is trivially atomic with the pattern
already in the codebase. Rejected the symlink approach specifically because it is
*not* the option with the most room for maneuver on Windows.

**Why not overwrite in place with a `.bak` rename:** violates Success Criterion 3
directly ("leaves the currently-running process untouched... never overwriting the
running file") — a running `.pyz` held open by the interpreter can usually be
replaced on POSIX (unlink semantics) but Windows holds a file lock on an
in-use executable/DLL-mapped file, so an in-place overwrite would fail outright on
Windows mid-run. Side-by-side avoids the question entirely.

### Choice Point 6 — relaunch mechanism after an update
**Recommendation:** `subprocess.Popen([sys.executable, new_pyz_path, *sys.argv[1:]],
close_fds=True)` followed by `sys.exit(0)` in the old process — **not**
`os.execv`/`os.execve`. On POSIX, `os.execv` genuinely replaces the process image and
would work; on Windows it does not — CPython emulates it via `spawnv`, which
**creates a new process and returns control to the caller** rather than replacing it,
a documented, longstanding platform difference [CITED: search cross-referencing
`bugs.python.org`/`github.com/python/cpython` issue history this session]. Using
`subprocess.Popen` + explicit `sys.exit()` is the cross-platform-correct pattern and
avoids relying on `os.execv`'s POSIX-only real behavior silently degrading to
"spawns a second process and doesn't clean up" on the one OS most likely to run this
tool day to day, given the project's own dev machine.

### Choice Point 7 — version-comparison semantics ("strictly newer")
**Recommendation:** parse `X.Y.Z` as a plain integer tuple and compare with ordinary
tuple comparison (`(1, 3, 0) > (1, 2, 9)`), stdlib only. **Do not** depend on the
`packaging` library (a pip install — a fourth named exception with no offsetting
benefit here) and do not hand-roll full SemVer 2.0 precedence (pre-release/build
metadata ordering) — itembank's own releases are the only input to this comparison,
so the project can simply commit to plain `vX.Y.Z` git tags with no pre-release
suffixes, which a tuple comparison handles correctly and unambiguously. Document this
constraint on the *release process*, not only in code: a tag like `v1.3.0-rc1` would
break the naive parser and must not be used.

**Pitfall:** never compare version strings lexicographically (`"1.10.0" <
"1.9.0"` is `True` as strings, wrong numerically) — split-and-int-cast first.

### Choice Point 8 — checksum source: `digest` field vs. `SHA256SUMS.txt`
**Recommendation:** primary path is the GitHub Releases API `digest` field
(live-verified this session, see Summary and Sources) since it needs no extra
release-asset upload step and is now confirmed to actually exist and populate
correctly. **Also** publish a `SHA256SUMS.txt` asset with every release as a
redundant, human-auditable fallback — cheap to generate at release-build time
(`hashlib.sha256` over the same artifacts already being uploaded), and it is the
ROADMAP's own explicitly-named fallback for exactly this contingency ("fall back to
`SHA256SUMS.txt` if it surprises"). Both paths share the same verification code
(`hashlib.sha256(data).hexdigest()` compared against a parsed expected value); only
where the expected value comes from differs. A `None` digest (pre-June-2025 legacy
asset, or a GitHub outage returning a null/absent field) must trigger the
`SHA256SUMS.txt` path rather than silently skipping verification.

### Choice Point 9 — GIFT `multi` (pick-N) scoring-semantics divergence
Not fully resolved here — flagged explicitly for the planner and, ideally, the user.

GIFT can structurally express "select multiple correct options" via per-answer
percentage weights (e.g. `{~%50%A ~%50%B ~%-100%C}`), but Moodle's grading of that
encoding is **partial-credit by default** — a learner who selects exactly one of two
correct options scores 50% in the LMS, whereas itembank's own scorer is dichotomous
(`score_response()` returns `True` only on an exact set match to `canonical_key()`
[VERIFIED: `runtime.py:120-130`]). A partial selection that itembank would mark wrong
could show as a passing/partial grade in the LMS. This is exactly the "silently wrong"
failure mode Success Criterion 5 warns about, and it does not have a clean fix within
GIFT's own grading model.

**Two options for the planner**, presented without a silent pick per the steering
instruction:
1. Export `multi` normally (weighted encoding), and print a **non-fatal warning by
   item number** at export time documenting the divergence — keeps the export usable
   for the common case (LMS agrees with itembank on complete-right and any-wrong
   answers; only a strictly-partial-but-not-wrong selection diverges).
2. Treat `multi` as GIFT-inexpressible under strict scoring parity and **fail loudly**
   by item number alongside `build` — more conservative, but removes the option to
   export any bank containing `multi` items via GIFT at all, which may be a
   meaningful fraction of a real bank.

This research leans toward option 1 (closer to "most room for maneuver" — the
learner/instructor can still choose not to use the exported file if the warning
matters to them, whereas option 2 forecloses the export outright), but the actual
LMS-import behavior (does Moodle clip negative totals to zero? is the "partial"
scenario even reachable in the LMS's own UI for a required-N-selections question?)
is unverified against a live import and belongs in Open Questions / a
`checkpoint:human-verify` before this ships.

### Pattern 1: Registry-first, PATH-second browser detection
**What:** try `shutil.which()` first (fast, cross-platform), then fall through to an
OS-specific known-location probe (registry on Windows, fixed paths + `mdfind` on
macOS, extended `which()` name list on Linux), then `webbrowser.open()`.
**When to use:** any time the daemon needs to open a frameless window (Choice Point
3/4).
**Example:**
```python
# Pattern adapted from eel/chrome.py (CITED: github.com/samuelhwilliams/Eel),
# rewritten stdlib-only (no whichcraft dependency) — illustrative, not verbatim.
import shutil, subprocess, sys

CHROME_NAMES = ("google-chrome-stable", "google-chrome", "chromium", "chromium-browser")

def find_chrome_windows():
    import winreg
    for hive in (winreg.HKEY_CURRENT_USER, winreg.HKEY_LOCAL_MACHINE):
        try:
            key = winreg.OpenKey(
                hive, r"SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\chrome.exe")
            return winreg.QueryValue(key, None)
        except OSError:
            continue
    return None

def find_browser():
    if sys.platform == "win32":
        return find_chrome_windows() or shutil.which("msedge")
    if sys.platform == "darwin":
        mac_path = "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
        import os
        return mac_path if os.path.exists(mac_path) else None
    for name in CHROME_NAMES:
        found = shutil.which(name)
        if found:
            return found
    return None

def open_app_window(url, no_open=False):
    if no_open:
        return
    browser = find_browser()
    if browser:
        subprocess.Popen([browser, "--app=%s" % url])
    else:
        import webbrowser
        webbrowser.open(url)
```

### Pattern 2: Side-by-side update with a JSON pointer manifest
**What:** never overwrite the running `.pyz`; download the new version alongside it,
verify, then atomically flip a pointer file the launcher reads next time.
**When to use:** the entire self-update flow (DEL-06, Success Criterion 3/4).
**Example:**
```python
# Reuses surfaces/settings.py's write pattern (VERIFIED, quoted above) rather than
# a new atomic-write helper.
import hashlib, json, os, urllib.request

def verify_digest(data, expected):   # expected: "sha256:<hex>" or None
    if expected is None:
        return None                  # caller must fall back to SHA256SUMS.txt
    algo, _, hexval = expected.partition(":")
    if algo != "sha256":
        return False
    return hashlib.sha256(data).hexdigest() == hexval

def write_manifest(base, version, rel_path):
    target = os.path.join(base, "updates", "current.json")
    os.makedirs(os.path.dirname(target), exist_ok=True)
    tmp = target + ".tmp"
    with open(tmp, "w", encoding="utf-8") as fh:
        json.dump({"version": version, "path": rel_path}, fh, indent=2)
        fh.write("\n")
    os.replace(tmp, target)   # same tmp-then-replace pattern as write_settings()
```

### Pattern 3: GIFT escaping as one canonical function
**What:** a single `gift_escape(text)` function every export code path calls,
mirroring the project's own "one scorer / one canonical function" architectural
philosophy (`canonical_response()` is the precedent: one function, every caller uses
it, no surface reimplements the rule).
**When to use:** every user-authored text field written into the GIFT file (stem,
option text, feedback/`why`, category names) — not only the ones that look risky at a
glance. A bank author innocently writing `"between 50% and 60%"` or `"A ~ B"` in a
stem would corrupt the exported file if any single field is missed.
**Example:**
```python
import re

_GIFT_ESCAPE = re.compile(r"([~=#{}:\\])")

def gift_escape(text):
    return _GIFT_ESCAPE.sub(r"\\\1", text or "")
```

### Anti-Patterns to Avoid
- **Bundling `pywebview` "just for this one feature":** reopens a stdlib-only
  exception with no easy way to close it again once settings/config/launcher code
  assumes it exists. Shell out instead.
- **Hand-parsing SemVer pre-release/build-metadata precedence:** itembank controls
  its own tag format; don't build generality the project's own release process will
  never exercise.
- **Reimplementing GIFT escaping per item type:** one function, every call site,
  matching the project's existing `canonical_response()`/`score_response()`
  single-function precedent.
- **Trusting `shutil.which()` alone on Windows:** live-verified this session to miss
  both Chrome and Edge on a real Windows 11 machine where both are installed at their
  standard locations. Registry lookup is not optional on Windows.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Atomic settings/manifest writes | A new tmp-file-and-rename helper | `surfaces/settings.py`'s existing `write_settings()` pattern (tmp file, `os.replace`) | Already proven, already the codebase's one canonical atomic-write shape; `runtime.write_session()` uses the identical pattern too |
| JSON structure validation for a new update-manifest schema | A second hand-written validator | `schema_validate.py`'s existing `validate(instance, schema)` | The project already has exactly one validator, reused by both `lint` and `config`; a third would violate the "one validator" precedent |
| Version comparison | Full SemVer 2.0 precedence parser | Plain `tuple(int(x) for x in v.split("."))` comparison | itembank controls its own tag format; no pre-release/build-metadata input will ever reach this code if the release process sticks to plain `vX.Y.Z` tags |
| Browser automation for the frameless window | Selenium/Playwright-style webdriver control | A single `subprocess.Popen([browser, "--app=" + url])` call | The daemon needs a *window*, not scripted control of page content — a webdriver is enormous overkill and a real dependency |
| GIFT format encoding | A general-purpose GIFT/Moodle export library from PyPI | A ~50-line hand-written mapper over itembank's own six item-type dicts | GIFT's grammar is small and stable (unchanged since Moodle's early versions); a whole dependency for six format cases the project already fully controls the input shape of is not proportionate, and keeps zero new install steps |

**Key insight:** every "don't hand-roll" in this phase points *back into the existing
codebase's own precedents* (`write_settings`, `schema_validate.validate`,
`canonical_response`-style single-function-per-rule), not out to a new dependency —
this phase's stdlib-only constraint makes "the library to use" almost always "the
pattern this project already established," not an external package.

## Common Pitfalls

### Pitfall 1: `os.execv` silently misbehaves on Windows
**What goes wrong:** the relaunch-after-update code appears to work in local testing
(a new process does start) but the old process does not cleanly exit the way POSIX
`exec` semantics imply, and error/exit-code propagation differs from what the code
assumes.
**Why it happens:** Windows has no real `exec()` syscall; CPython's `os.execv` on
Windows is implemented via `spawnv`, which creates a **new** process and returns
control to the caller rather than replacing the process image [CITED: cross-checked
via CPython issue-tracker history this session].
**How to avoid:** use `subprocess.Popen([sys.executable, new_path, *args])` followed
by an explicit `sys.exit(0)` on every platform — never branch platform-specific
relaunch logic on `os.execv`.
**Warning signs:** a relaunch that appears to work when run manually from a terminal
but leaves zombie/duplicate processes, or loses stdout, when launched by double-click.

### Pitfall 2: GitHub's unauthenticated rate limit is 60 requests/hour, per IP
**What goes wrong:** `check_on_launch` calling the Releases API on every daemon
startup exhausts the budget quickly on a shared network (school/dorm NAT), and every
learner behind that IP starts silently failing the check — which is *supposed* to
degrade gracefully, but only if the code distinguishes "rate limited" from "genuinely
no update available" for its own diagnostics, and avoids making the problem worse by
re-checking every launch.
**Why it happens:** confirmed via a live, unauthenticated request this session —
`X-RateLimit-Limit: 60` in the response headers [VERIFIED: live `curl -sI
https://api.github.com/repos/cli/cli/releases/latest` this session].
**How to avoid:** cache the last-checked timestamp locally (e.g., beside
`updates/current.json`) and only actually call the API if more than some interval
(24h is a reasonable default) has elapsed since the last check, independent of how
often `check_on_launch` fires the intent to check.
**Warning signs:** update checks that work in isolated testing but stop resolving for
everyone on the same network simultaneously.

### Pitfall 3: `digest` is `null` for assets uploaded before the feature's GA
**What goes wrong:** a checksum-verification code path that assumes `asset["digest"]`
is always a string throws or silently skips verification on any pre-June-2025 release
asset.
**Why it happens:** the field was GA'd June 3, 2025 [CITED:
`github.blog/changelog/2025-06-03-releases-now-expose-digests-for-release-assets`];
older assets retain `digest: null`.
**How to avoid:** explicit `if digest is None:` branch to the `SHA256SUMS.txt`
fallback (Choice Point 8), never treat a missing digest as "verification passed" or
skip it silently.
**Warning signs:** not reachable for itembank's *own future* releases (all postdate
the GA), but a real risk if the updater is ever pointed at a differently-configured
repo, or if GitHub has a transient outage returning a partial asset object.

### Pitfall 4: Windows file-lock semantics block in-place `.pyz` replacement
**What goes wrong:** an update mechanism that tries to overwrite the currently-running
`.pyz` in place works fine in POSIX-only testing and then fails outright (or corrupts
the running process's mapped file) on Windows.
**Why it happens:** Windows holds an open handle/lock on a file the running
interpreter loaded, and does not allow arbitrary overwrite of an in-use file the way
POSIX unlink-and-recreate semantics allow.
**How to avoid:** side-by-side layout (Choice Point 5) sidesteps this entirely — the
running file is never opened for writing by the updater.
**Warning signs:** an update that works when tested via WSL/POSIX but fails with a
permission or sharing-violation error on the actual Windows dev machine.

### Pitfall 5: Gatekeeper quarantine blocks `.command` first-run silently
**What goes wrong:** a downloaded `.command` launcher, double-clicked for the first
time on macOS, fails with an opaque "operation not permitted" in Terminal output — no
standard Gatekeeper dialog appears to guide the user.
**Why it happens:** macOS attaches a quarantine extended attribute
(`com.apple.quarantine`) to files downloaded via a browser or delivered through most
channels other than the App Store or a signed installer [CITED: this session's
research on `.command` Gatekeeper behavior].
**How to avoid:** cannot be fully solved without a paid Apple Developer signing
certificate (explicitly out of v1 scope, deferred by `V2-DEL-01`). Document the
right-click-then-Open workaround (or `xattr -d com.apple.quarantine`) prominently in
the shipped README/release notes rather than letting it surface as an unexplained
failure.
**Warning signs:** "it works when I build it myself but not when a learner downloads
the release asset" — the quarantine flag is attached at download time, not build time.

### Pitfall 6: `.pyz` "double-clickable" still requires Python pre-installed
**What goes wrong:** a task or plan step implicitly treats DEL-01's "double-clickable
artifact" as equivalent to a self-contained installer (like an `.exe` built by
PyInstaller), and scope creeps toward bundling an interpreter — which DEL-02 and the
stdlib-only constraint both forbid.
**Why it happens:** `zipapp` genuinely produces a runnable, double-clickable file on a
machine with a correctly-configured Python install, but does nothing at all — no
error dialog, in the worst case just an "how do you want to open this file" OS prompt
— on a machine without one.
**How to avoid:** treat the launcher's Python-detection failure path as a first-class
requirement, not an edge case: print/show a clear, actionable message
("itembank needs Python 3.11+; install it from python.org and try again") rather than
letting the OS's own generic file-association failure be the only signal.
**Warning signs:** none locally (the dev machine always has Python) — this only
surfaces on a genuinely fresh target machine, which is exactly why it needs to be
called out here rather than discovered late.

### Pitfall 7: GIFT weighted-multi-answer partial credit diverges from itembank's dichotomous scorer
See Choice Point 9 above — a real, unresolved scoring-semantics gap between GIFT's
partial-credit model and `score_response()`'s all-or-nothing verdict
[VERIFIED: `runtime.py:120-130`], not a hypothetical edge case.

### Pitfall 8: `settings.py`'s `THIS_PHASE` and the `update_policy` schema key both still say phase "12"
**What goes wrong:** once this phase's code lands, `itembank config` will keep
reporting `update_policy` as `inert -- read from phase 12` even though this phase
(numbered `2.1`) is the one actually reading it — because both the code constant and
the schema annotation predate this roadmap insertion.
**Why it happens:** `surfaces/settings.py:27` sets `THIS_PHASE = 2` (an `int`), and
`schemas/settings.schema.json`'s `update_policy` property carries `"x-itembank-phase":
12` [VERIFIED: `surfaces/settings.py:27`, `schemas/settings.schema.json:109`] — both
were written before Phase 12 was renumbered/moved to `2.1`.
**How to avoid:** the planner must update both together: bump
`schemas/settings.schema.json`'s `update_policy` (and `daemon`'s own sub-keys stay at
`2`, unaffected) `x-itembank-phase` from `12` to whatever this phase's actual
identifier resolves to in that field's type (the field is currently used as a plain
number for `<=` comparison at `surfaces/settings.py:197` — a fractional phase number
like `2.1` compares correctly against `THIS_PHASE` as a Python float, but
`THIS_PHASE` itself must also become `2.1`, not stay `2`, or the new key will still
read as inert).
**Warning signs:** `itembank config`'s printed table still says `inert -- read from
phase 12` after this phase's own code is merged and the setting is actually being
read — a quick post-implementation check the planner should verify explicitly.

## Code Examples

### GIFT export skeleton, adapted from itembank's own field shapes
```python
# Source: this session's read of runtime.py (answer_text, canonical_response,
# canonical_key) and model.py (parse_question) — VERIFIED field shapes, not GIFT-
# specific prior art. Illustrative skeleton, not a complete implementation.

def gift_mc(q):
    lines = ["::Q%d:: %s {" % (q["number"], gift_escape(q["stem"]))]
    for letter in sorted(q["opts"]):
        marker = "=" if letter in q["correct"] else "~"
        feedback = q["da"].get(letter, "")
        fb = (" # " + gift_escape(feedback)) if feedback else ""
        lines.append("%s%s%s" % (marker, gift_escape(q["opts"][letter]), fb))
    lines.append("}")
    return "\n".join(lines)

def gift_matching(q):    # table/dnd -> GIFT matching (Choice Point resolved:
                          # repeated right-hand category values are valid GIFT)
    lines = ["::Q%d:: %s {" % (q["number"], gift_escape(q["stem"]))]
    for row in q["rows"]:
        lines.append("=%s -> %s" % (gift_escape(row["text"]), gift_escape(row["cat"])))
    lines.append("}")
    return "\n".join(lines)

def gift_export_item(q, errors):
    if q["type"] == "build":
        errors.append("Q%d: type 'build' (ordering) has no GIFT equivalent -- "
                      "cannot export" % q["number"])
        return None
    if q["type"] in ("mc", "multi"):
        return gift_mc(q)
    if q["type"] in ("table", "dnd"):
        return gift_matching(q)
    if q["type"] == "short":
        return "::Q%d:: %s {=%s}" % (
            q["number"], gift_escape(q["stem"]), gift_escape(q.get("model", "")))
    errors.append("Q%d: unrecognized type %r" % (q["number"], q["type"]))
    return None
```

### Update-check-and-fetch skeleton
```python
# Source: this session's own design over stdlib urllib/hashlib, informed by the
# live-verified GitHub API shape. Illustrative, not a complete implementation.
import json, urllib.error, urllib.request

def check_latest(owner, repo, timeout=5):
    url = "https://api.github.com/repos/%s/%s/releases/latest" % (owner, repo)
    req = urllib.request.Request(url, headers={"Accept": "application/vnd.github+json"})
    try:
        with urllib.request.urlopen(req, timeout=timeout) as resp:
            return json.loads(resp.read())
    except (urllib.error.URLError, TimeoutError, OSError):
        return None    # offline / unreachable -- degrade silently (DEL-07)
```

## Open Questions

1. **Does the real target LMS (Moodle, unspecified version) actually accept the
   `table`/`dnd`-as-`matching` export this research recommends, at the row counts
   itembank banks typically have?**
   - What we know: GIFT's `matching` syntax structurally supports repeated
     right-hand values (VERIFIED via two independent search results this session),
     which functionally matches itembank's categorize-rows-into-buckets shape.
   - What's unclear: any hard minimum sub-question count, and whether Moodle's
     specific version in use handles a large row count (some banks may have many
     more rows than a typical textbook matching question) gracefully in its own UI
     after import.
   - Recommendation: Success Criterion 5 itself calls for testing against "a real
     LMS importer" — this should be an explicit manual verification step
     (`checkpoint:human-verify`) in the plan, not assumed correct from documentation
     alone.

2. **Should `multi`-type GIFT export fail loudly or warn-and-proceed (Choice Point
   9)?**
   - What we know: the scoring-semantics divergence is real and documented above.
   - What's unclear: which failure mode Weibao (the sole user) would actually prefer
     — this is a product decision the steering instruction's "maximum flexibility"
     framing doesn't fully resolve, since the two options trade off differently
     (usability of the export vs. correctness guarantee).
   - Recommendation: surface this exact choice to the user during planning/execution
     rather than the planner silently picking one; both are cheap to implement, so
     the cost of asking is low.

3. **Is there a genuinely reliable "raw executable double-click" path on Linux, or is
   `.desktop` truly required in all cases?**
   - What we know: file-manager behavior for executable files varies significantly
     across GNOME/Nautilus, KDE/Dolphin, XFCE/Thunar, etc. — some prompt "Run or
     Display", some just open as an archive.
   - What's unclear: this session's research did not test on an actual Linux desktop
     environment (no Linux machine available in this session).
   - Recommendation: ship the `.desktop` file as the primary documented path per
     Choice Point 2; treat the bare-executable path as a bonus for terminal users,
     not a promised double-click UX.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|-----------------|---------|---------------------|
| V5 Input Validation | yes | GIFT-escape every user-authored text field before writing it into the export (Pattern 3); validate the update manifest against a JSON Schema via the existing `schema_validate.py` before trusting it |
| V6 Cryptography | yes | SHA-256 via stdlib `hashlib` for update verification — never hand-roll a hash comparison (e.g., naive string `==` is fine here since SHA-256 hex digests are not secret and timing attacks don't apply to a public checksum, but the comparison must be against the *verified* expected value, not a value read from the same untrusted download) |
| V10 (Malicious Code / Supply Chain, ASVS 4.x numbering varies) | yes | Update downloads must occur over HTTPS (stdlib `urllib.request` verifies TLS certs by default — do not disable verification); the update source URL must be constructed from a fixed, hardcoded `owner/repo`, never from user input, to prevent a manipulated config value redirecting the updater at an attacker-controlled release feed |
| V14 Configuration | yes | The `update_policy` setting is already schema-validated (existing `settings.schema.json` enum, VERIFIED) — no new configuration surface needed for the policy itself |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Malicious/compromised release asset served under a valid-looking GitHub URL | Tampering | SHA-256 checksum verification against the `digest` field (or `SHA256SUMS.txt` fallback) before the downloaded `.pyz` is ever written to the `versions/` path the manifest can point at |
| Downgrade attack (attacker serves an old, vulnerable release as "latest") | Tampering | Strictly-newer version comparison (Choice Point 7) rejects any non-newer version even with a valid checksum — this is explicitly named in Success Criterion 4 |
| Config-driven URL injection redirecting the updater to an attacker's feed | Tampering / Spoofing | Hardcode `owner/repo` in code, not in `itembank.json`; the settings schema's `update_policy` only toggles *when* to check, never *where* |
| Man-in-the-middle on the download | Tampering / Information Disclosure | stdlib `urllib.request` verifies TLS by default over HTTPS; never construct an `http://` (non-TLS) request for the update path |
| Path traversal via a maliciously-named release asset (`../../etc/whatever.pyz`) | Tampering | Sanitize/validate the asset filename before joining it into the `versions/` directory path — never trust the API's own `name` field verbatim as a path component without a basename/allowlist check |
