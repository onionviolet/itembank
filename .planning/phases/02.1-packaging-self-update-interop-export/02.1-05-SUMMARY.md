# Phase 02.1 Plan 05: The updater's decision half -- version compare, checksum verification, offline-silent check Summary

**`surfaces/update.py` can tell a newer release from an older one, real bytes from tampered bytes, and an unreachable GitHub from a genuine no-update -- and none of those paths can raise into a caller or make a network request without explicit consent.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 2 (Task 1 was a pre-resolved decision checkpoint, recorded not re-executed)
- **Files modified:** 3 (all created)

## Accomplishments

- `surfaces/update.py`: `parse_version`/`is_newer` (strict integer-tuple comparison, no checksum argument -- Success Criterion 4 as one function), `verify_digest`/`parse_sha256sums` (three-outcome checksum verification sharing one comparison, digest-field-first with a `SHA256SUMS.txt` fallback), `update_root()` (writable-directory probe beside the running `.pyz`, falling back to `surfaces/day.py`'s existing win32/darwin/else platform data-directory selection -- no second copy), `read_manifest`/`write_manifest` (atomic tmp-then-`os.replace`, schema-validated), `check_latest` (GitHub Releases fetch that degrades to `None` on any failure and distinguishes rate-limiting via an optional `status` dict), `should_check` (interval-based rate-limit guard reading the manifest's own `checked_at`), `may_check` (the opt-in consent gate)
- `schemas/update_manifest.schema.json`: typed contract for `updates/current.json` -- `schema_version`, `version`, `path`, `sha256`, `checked_at`, `additionalProperties: false`
- `tests/update_roundtrip.py`: nine test functions covering strictly-newer comparison, checksum accept/reject/abstain, the `SHA256SUMS.txt` fallback (including a filename-prefix collision), offline/timeout/HTTP-error silence, rate-limited distinguishability, atomic manifest validation and corruption recovery, a writable `update_root()`, the opt-in consent gate, and the token-never-from-settings-file prohibition -- zero real network requests, every `urlopen` call site substituted

## Decisions Made

- **Task 1's checkpoint (release identity contract) was resolved as option-a** by the orchestrator before this executor ran, per the harness's `checkpoint_already_resolved` instruction: plain `vX.Y.Z` tags, the GitHub asset `digest` field read first with a `SHA256SUMS.txt` fallback. Implemented exactly as CONTEXT.md D-07 and RESEARCH Choice Points 7/8 describe -- an unparseable (suffixed) tag is skipped as no-update, never crashes the parser.
- `should_check()`'s "last-check timestamp beside the manifest" is read from the manifest's own `checked_at` field rather than a second sibling file. `write_manifest`'s parameters (`version`, `path`, `sha256`, `checked_at`) double as both "what this installation currently trusts" and "when that was last verified against GitHub" -- no manifest on disk means `should_check()` returns `True` (never checked). This keeps the module's exported surface exactly the twelve names the plan's frontmatter lists, with no third file format to validate.
- Added `may_check(policy, explicit)` as the policy gate Task 3's own action text names ("whatever the module exposes as the policy gate") but the frontmatter's `exports` table does not list by name. It is a single pure boolean function with no network code of its own -- the actual background-check orchestration (`background_check`, `cmd_update`) is explicitly out of scope for this plan per the `important_note` and belongs to plan 02.1-07.
- `check_latest` reads `ITEMBANK_GITHUB_TOKEN` from the environment itself when no explicit `token` argument is passed. The original Task 2 implementation left `token` defaulting to `None` with no internal source, which meant no caller in this plan's own scope could actually satisfy D-09 without either hardcoding an environment read at every call site or reading it from somewhere the plan forbids. Found while writing `test_token_never_comes_from_the_settings_file`; fixed inline (Rule 1) and committed separately since Task 2 had already landed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `check_latest` never actually read `ITEMBANK_GITHUB_TOKEN`**
- **Found during:** Task 3 (writing `test_token_never_comes_from_the_settings_file`)
- **Issue:** Task 2's `check_latest(repo, timeout=5, token=None)` left `token` as a plain pass-through parameter with no internal environment read, so D-09's contract ("reads an optional token from the environment... never from `itembank.json`") had no implementation anywhere in the module -- a real caller would have had to invent its own environment read, risking a second, inconsistent source.
- **Fix:** `check_latest` now falls back to `os.environ.get("ITEMBANK_GITHUB_TOKEN")` when `token` is `None`, documented in the function's own docstring without naming the settings filename literally (keeping the `grep -c 'itembank.json'` acceptance criterion at 0).
- **Files modified:** `surfaces/update.py`
- **Verification:** `test_token_never_comes_from_the_settings_file` (settings file carries a token-looking key; asserted no `Authorization` header is sent from it); `grep -c 'itembank.json' surfaces/update.py` reports 0
- **Committed in:** `4d53904` (separate fix commit, since Task 2's own commit had already landed before the bug surfaced)
