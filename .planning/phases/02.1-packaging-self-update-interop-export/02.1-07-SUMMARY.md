## Decisions Made

- **The `SHA256SUMS.txt` fallback lives in the caller, not in `install()`.** The plan's action text describes `install()` as fetching the checksum-file asset when a release's `digest` field is absent, but `install()`'s locked signature (`base, version, name, data, expected`) carries no URL or repository to fetch from. `cmd_update` now resolves `expected` -- via the digest field first, falling back to a new `_checksum_fallback(release, name, timeout)` helper that finds and downloads the release's own `SHA256SUMS.txt` asset -- before calling `install()`, which stays network-free and does exactly what its own docstring says: "Verify first."
- **Idempotent re-installs reuse the stored `checked_at` rather than calling `datetime.now()` again**, so two sequential `install()` calls of the same version produce byte-identical manifest files deterministically (not "usually, if both calls land in the same wall-clock second"). This makes the plan's own verify script's exact-byte manifest comparison a reliable assertion rather than an occasionally-flaky one.
- **`background_check(root, cfg)` treats `root` as the literal base directory** (matching `read_manifest(base)`, `write_manifest(base, ...)`, `should_check(base, ...)` throughout the rest of the module) rather than calling `update_root()` internally. This is both consistent with the module's existing design and the only way a test can point the function at an isolated tempdir instead of this machine's real per-user data directory.
- **`background_check` refreshes an existing manifest's `checked_at`** after a completed check (whether or not anything newer was found), so `should_check`'s rate-limit clock actually advances launch to launch -- but only when a manifest already exists. When nothing has ever been installed, this step is skipped rather than fabricating a manifest with an invented path/digest, since the schema requires real string values for both and a fake pointer could later mislead `handoff`.
- **A mid-flight download failure folds into the same "Could not reach GitHub" line** as the pre-check offline outcome, rather than inventing a seventh locked line. UI-SPEC's Copywriting Contract names exactly six outcomes for `itembank update`; a download failure after the "Downloading..." line is, functionally, the same unreachable-GitHub cause.
