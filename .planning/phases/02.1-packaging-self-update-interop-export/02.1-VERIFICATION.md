### Gaps Summary

No gaps remain. All three findings from the initial report are closed and verified against the actual code in this session:

1. **CR-01 (token leak on redirect)** — closed by plan 02.1-08. `download_asset`, `_checksum_fallback` (via `download_asset`), and `check_latest` all route through the one `_open_request` seam whose `AuthStrippingRedirectHandler` removes Authorization the instant the origin (scheme/host/port, default-port-resolved) changes; the token is additionally host-gated before the header is ever built. The redirect path is exercised end to end through the module's real opener with a substituted transport; the cross-host hop carries no Authorization header and no token string, the same-host hop keeps it, and the return-to-origin hop stays stripped.
2. **CR-02 (throttle never engages on a fresh install)** — closed by plan 02.1-09. The clock moved into `updates/check_state.json`, written unconditionally after any check whose `status["reached"]` is true (before the `release is None` early return); `should_check` reads both clocks and trusts the more recent. Two launches inside the interval against a manifest-less base make exactly one request — asserted at 24h and 0h intervals, plus unreachable and rate-limited cases and manifest-clock retention.
3. **CR-03 (unconsented background check on a checkout)** — closed by plan 02.1-09. The first background check on any machine prints the locked disclosure, records `notified_at` only, and returns without a request; `opt_in` (the schema default for a settings-less directory) never prints or asks. The deliberate schema-vs-repo `update_policy` divergence is now documented in the schema description, README Install, and CLAUDE.md Constraints rather than being silent.

The remaining status is `human_needed` only because the phase's real-OS, real-LMS, and real-release behaviors cannot be verified from this environment — not because any automated or code-level check failed.
