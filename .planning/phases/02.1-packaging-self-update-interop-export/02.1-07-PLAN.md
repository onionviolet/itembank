<objective>
Close the updater: download the offered artifact, verify it before it can be pointed at, land it beside
the running one, and let the next launch pick it up — plus the two surfaces that expose all of it, an
explicit command that says what happened and a background check that says nothing.

Purpose: Success Criterion 3 is a structural claim, not a behavioural one — "leaves the currently-
running process untouched" is true because the running file is never opened for writing, not because
the code is careful. This plan builds the layout that makes it structurally true, and the handoff that
makes a side-by-side install actually reach the learner.

Output: the install half of `surfaces/update.py`, the `update` subcommand, the daemon's background
check, the handoff in the generated entry point, and the tests that pin all of it.
</objective>

`pick_asset(release)` takes a parsed release document and returns the artifact to fetch, or `None`.
Choose the asset whose name matches the artifact shape this project's own build script emits — the
fixed prefix, the version, and the archive suffix — and take the first match when several qualify,
returning `None` when none does. Never trust the API's `name` field as a path component: reduce it to
its basename and reject any name that does not match the expected shape before it is used to build a
filesystem path. Return the asset's download url and its digest field alongside the name, and return
the digest as `None` when the field is absent or null rather than substituting anything.

`download_asset(url, token=None, timeout=30)` fetches the bytes over https with the same header set
and the same failure handling `check_latest` uses: every network error class returns `None` and none
of them raises. Cap what is read so a hostile or broken response cannot exhaust memory — the artifact
this project builds is well under ten megabytes, so a ceiling an order of magnitude above that is
generous and still bounded.

`install(base, version, name, data, expected)` is where Success Criterion 3 becomes structural.
Verify first: run `verify_digest(data, expected)` and, on a `None` result, fetch and parse the
checksum-file asset through `parse_sha256sums` and compare against that instead. Return `None` when
verification fails or cannot be completed — the bytes are discarded and nothing is written. Only after
verification passes, create the versions directory under `base`, write the bytes to the target name
with a partial suffix, and `os.replace` that onto the version-qualified final name. Writing to a
partial name first is what makes an interrupted download leave nothing at the path anything reads.
Then write the pointer manifest with `write_manifest`, recording the version, the artifact's path
relative to `base`, its digest, and the timestamp. Return the installed path.

Nothing in this function may open the running artifact for writing, and there is no code path that
does: the target name always carries the version being installed, and a version equal to the running
one never reaches `install` because `is_newer` refused it upstream. Make idempotency explicit rather
than incidental — when the target path already exists and its digest matches, skip the write, rewrite
the manifest to the same values, and return the existing path, so a second run adds no second copy.

`handoff(argv)` is what makes a side-by-side install reach the learner. Read the manifest under
`update_root()`; return immediately on a missing or invalid manifest. Return when the manifest's
version is not strictly newer than the running `itembank.__version__` — the same comparison, not a
second one. Return when the manifest's target path resolves to the artifact this process is already
running from, which is the loop guard. Return when the target file is missing or its digest does not
match what the manifest recorded, because a manifest is a pointer and a pointer to changed bytes is
not trustworthy. Otherwise spawn `subprocess.Popen([sys.executable, target, *argv], close_fds=True)`
and `sys.exit(0)`. Use the spawn-and-exit pair on every platform and do not branch on platform: the
exec family has no real implementation on Windows, where it spawns a new process and returns to the
caller instead of replacing the image, so a platform branch here would silently leave two processes
alive on the one operating system this project's own dev machine runs. Wrap the whole function body so
that any unexpected exception returns rather than propagating — a broken updater must never stop the
tool from starting.

In `build.py`, extend `MAIN_TEMPLATE` so the generated entry point attempts the handoff before
dispatching to the CLI: insert the archive directory onto the path, import the update module, call
`handoff` with the argument list, and only then call the CLI entry point. Put the handoff call inside
a guard that swallows any exception, for the same degrade-never-block reason. Keep the template short;
this is the one branch it is allowed to grow.

override or `cfg["update"]["repo"]`, read the token from the environment variable and from nowhere
else, and call `check_latest`. Then branch to exactly one of the locked outcomes, and never print two:

Unreachable — `check_latest` returned `None` for an ordinary failure: print the locked offline line
saying the check could not reach GitHub and to try again later. This is the case DEL-07's silence rule
does not cover: a learner who typed a command and got nothing back cannot tell "you are current" from

Rate-limited — `check_latest` returned `None` with the rate-limit condition set: print the locked
rate-limited line instead.

Not newer — the offered tag parses but `is_newer` refuses it: print the locked downgrade-rejection

Up to date — the offered tag is not newer and equals the running one, or no asset was offered at all:

line by whether the offered version is below the running one or the same as it.

Newer — print the three locked sequential lines as the work happens, not before it: the downloading
line, then the verifying line after the bytes are in hand, then the installed line naming the version

plan does not introduce one. When the check-only flag was given, stop after reporting that a newer

readable in a narrow terminal, and stating that nothing was installed.
