## Flagged planner assumption (unresolved edge, surfaced not dropped)

The deterministic edge probe returned `unclassified` for DEL-06, so no acceptance criterion was
auto-derived for it.

- **A-DEL-06 — the shape of an itembank release.** Assumed: one GitHub Releases `latest` response
  carrying exactly one asset whose name matches the artifact this project's own `build.py` emits, plus
  a `SHA256SUMS.txt` asset. The `digest` field's shape was live-verified on 2026-08-07 against a real
  response and is `sha256:` followed by 64 hex characters, resolving the ROADMAP's flagged open
  decision. **Unverified:** behaviour when a release carries several matching assets or none — no
  itembank release exists yet to test against. This plan treats "no asset whose name matches the
  expected artifact shape" as no-update rather than as an error, and takes the first match when
  several exist; both are recorded here rather than discovered later.

<task type="checkpoint:decision" gate="blocking">
  <decision>The release identity contract: what a version tag may look like, and where the expected checksum comes from.</decision>
  <context>
Both halves of this are one-way doors. Once a release is published, every installed copy's updater
reads its tag and its checksum forever, and there is no way to un-publish either from a client that
has already fetched the release list. No itembank release has been cut yet, so this is the last
moment the door is cheap.

Two facts were live-verified on 2026-08-07 against a real GitHub Releases response and are not in
question: the asset object carries a `digest` field shaped as `sha256:` followed by 64 hex characters,
and unauthenticated requests are limited to 60 per hour per IP. What is being decided is the policy
built on top of them.

The undo cost, concretely: if a tag carrying a suffix is ever published under option A, every
installed copy's integer-tuple parser sees a tag it cannot read. The plan mitigates that by skipping
an unparseable tag rather than crashing on it, so the failure is "no update offered" rather than a
broken client — but a release that no client can see is still a release that has to be re-cut under a
different tag.
  </context>
  <options>
    <option id="option-a">
      <name>Plain `vX.Y.Z` tags, digest first with a `SHA256SUMS.txt` fallback (what CONTEXT.md D-07 and RESEARCH Choice Points 7 and 8 recommend)</name>
      <pros>Simplest parser, stdlib only, no dependency on a version library. Two independent checksum sources, so a null digest on a legacy or partially-served asset still verifies. Both are what the ROADMAP's own open-decision line proposed.</pros>
      <cons>Forecloses release candidates: no `-rc1`, no `-beta`, no build metadata, ever, without changing the parser in every installed copy first. The release process has to enforce that by discipline, not by code.</cons>
    </option>
    <option id="option-b">
      <name>Plain `vX.Y.Z` tags, `SHA256SUMS.txt` as the only checksum source</name>
      <pros>One code path instead of two, and a checksum file a human can read and audit. Independent of a GitHub API field that has only existed since mid-2025.</pros>
      <cons>A second network request per check, spending twice the rate-limit budget on an already-tight 60-per-hour allowance. Loses the redundancy that makes a partially-served asset object recoverable.</cons>
    </option>
    <option id="option-c">
      <name>Support a pre-release suffix now: parse `vX.Y.Z` and an optional `-rcN`, ordering a release candidate below its own final release</name>
      <pros>Keeps the release-candidate door open, which the phases that follow may want when the updater itself is being dogfooded. Undoing it later is easy — a client that understands suffixes reads a plain tag fine.</pros>
      <cons>More parser to write and to test for a case this one-learner project may never use, and full precedence rules are a known source of subtle ordering bugs. RESEARCH explicitly named hand-rolling this an anti-pattern.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>

`UPDATE_CODES` is a `tuple(sorted({...}))` of dotted codes in the `update.` namespace, matching
`SETTINGS_CODES`' construction exactly so sortedness is structural: codes for an unreachable check, a
rate-limited check, a checksum mismatch, a rejected downgrade, a malformed manifest, and a missing
asset.

`parse_version(text)` strips a single leading `v`, splits on dots, and returns a tuple of integers —
or `None` when any component is not an integer or the component count is not three. Returning `None`
rather than raising is what makes an unparseable tag a skipped release instead of a crashed check.
`is_newer(offered, running)` parses both and returns true only when both parse and the offered tuple
sorts strictly above the running one. Equal is not newer. This is Success Criterion 4 stated as one
function, and it must be independent of any checksum result: nothing in this function may consult a
digest.

`verify_digest(data, expected)` returns three distinct outcomes and never conflates them. Given a
`None` or empty expected value it returns `None`, meaning "no expectation available, use the fallback"
— never treat that as a pass; the digest field is null for any asset uploaded before mid-2025, and a
transient partial response can produce the same shape. Given a value whose algorithm prefix is not
sha256 it returns false. Otherwise it compares `hashlib.sha256(data).hexdigest()` against the hex half
and returns the boolean. `parse_sha256sums(text, name)` scans a checksum file's lines for the entry
naming `name` and returns its hex digest or `None`, so the fallback path shares the same comparison
code and differs only in where the expected value came from.

`update_root()` returns the base directory the versions directory and the manifest live under. Prefer
the directory holding the running `.pyz` — take it from `resources.archive_path()` — when that
directory is writable, so a copy carried on a USB stick or sitting in a Downloads folder stays
self-contained. Fall back to the platform per-user data directory otherwise, reusing the exact
`win32`/`darwin`/else branch `surfaces/day.py` already implements, with an itembank-named subdirectory
under it. When the process is not running from a `.pyz` at all, return the per-user directory too —
a checkout has no artifact to sit beside. CONTEXT.md names the writability probe as a discretion
point: implement it as a try-write-then-clean-up of a temporary name in the candidate directory,
because a permission bit can be present while the filesystem is read-only, and record the choice in
the SUMMARY. `MANIFEST_REL` and `VERSIONS_REL` name the manifest path and the versions directory
relative to that root.

Create `schemas/update_manifest.schema.json` modelled on `schemas/settings.schema.json`'s conventions:
a schema id and title, `type` object, `additionalProperties` false, a `required` array, and typed
described properties for the schema version, the installed version string, the path to the installed
artifact relative to the update root, the artifact's sha256 hex digest, and the timestamp the check
that produced it ran. `read_manifest(base)` loads it, validates it through the one existing
`schema_validate.validate()`, and returns `None` on a missing file or a validation failure rather than
raising — a corrupt pointer must degrade to "no newer version installed", never to a crash on startup.
`write_manifest(base, ...)` writes it with the same tmp-then-`os.replace` sequence `write_settings()`
uses; do not add a second atomic-write helper.

`check_latest(repo, timeout=5, token=None)` builds the releases-latest URL from the `owner/name` value
it was handed — never a hardcoded repository and never a URL taken from anything but the settings
value — sets the GitHub JSON accept header and a user-agent naming itembank, adds an authorization
header only when a token was passed, and returns the parsed response. Wrap the request so that
`urllib.error.URLError`, `urllib.error.HTTPError`, `TimeoutError` and `OSError` all return `None`;
distinguish a rate-limit response from an ordinary failure by reading the remaining-requests response
header before returning, so the caller can print the rate-limit line for an explicit invocation while
still returning `None`. Read the token from the environment variable named in the settings schema's
own description and from nowhere else — never from the settings file, which is checked in. The
request must be https; do not construct a plaintext URL and do not disable certificate verification.

`should_check(base, interval_hours)` reads the last-check timestamp beside the manifest and returns
false when less than `interval_hours` have elapsed. This is the rate-limit guard: `check_on_launch`
expresses an intent to check, and this function decides whether an actual request is made, so a
shared campus or dorm network does not exhaust a 60-per-hour budget across every launch.
