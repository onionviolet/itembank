## 1. System Classification

**System Type:** Hybrid structured generation and rubric assistance behind a deterministic safety gate  
**Description:** A provider-neutral adapter produces error-specific hint candidates and per-rubric-point review suggestions. The runtime validates structured output, enforces the Phase 6 fact/tier boundary, and exposes only passed content. Authored teaching, scoring, and evidence remain functional without a model.

**Critical Failure Modes:**
1. Answer, key, or higher-tier facts reach the learner.
2. Model output changes a score, accepted mark, tier, or item selection.
3. Provider-native or malformed output bypasses the typed adapter/gate.
4. Model failure blocks the offline learning loop.
5. Secrets or leaked output enter ordinary learner reports.

## 1b. Domain Context

**Industry Vertical:** Education / assessment integrity  
**User Population:** One learner using EMT, mathematics, and introductory CS material with human review of prose marking  
**Stakes Level:** High  
**Output Consequence:** A bad hint can contaminate measurement or teach the answer; a bad rubric suggestion can misstate mastery unless held pending.

### What Domain Experts Evaluate Against

| Dimension | Good | Bad | Stakes |
|---|---|---|---|
| Tier fidelity | Uses only facts enumerated for the unlocked tier | Names, entails, or narrows to reserved answer facts | Critical |
| Error specificity | Addresses the learner's actual wrong move | Generic restatement or unrelated lecture | High |
| Pedagogical usefulness | Prompts the next reasoning step without solving it | Reveals the solution or gives empty encouragement | High |
| Rubric fidelity | One cited suggestion per authored rubric point, including uncertainty | Invents criteria or emits an accepted verdict | Critical |
| Offline continuity | Typed unavailable result and authored fallback | Spinner, crash, or blocked sitting | Critical |

### Known Failure Modes in This Domain

Prompt injection asking for the key; paraphrased or implied leakage; option-elimination that uniquely identifies an answer; unsupported certainty in manual marking; provider variance; repeated retry cost; and hidden provenance.

### Regulatory / Compliance Context

No formal certification regime is claimed. The binding constraints are local evidence residency, no telemetry, accepted hosted transit of item text, and explicit pending human review for prose marking.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|---|---|
| Assessment author/instructor | Label permitted versus reserved facts and adjudicate leakage/usefulness cases |
| Learner/operator | Confirm fallback, provenance, and retry behavior are understandable |

## 2. Framework Decision

**Selected Framework:** Direct Python standard-library adapter plus versioned JSON Schema contracts  
**Version:** Python runtime pinned by the project; adapter/schema protocol version `1`  
**Rationale:** The project forbids runtime dependencies and requires hosted CLI and local OpenAI-compatible transports to share one interface. A general agent framework would add authority and state the model must not own. The model provider is replaceable; deterministic schemas, gates, timeouts, and evidence are the framework.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|---|---|
| OpenAI Agents SDK | Provider-specific and an unnecessary runtime dependency |
| LangGraph/LangChain | Adds orchestration/state abstractions to two bounded request types |
| Pydantic runtime models | External dependency conflicts with the stdlib-only production contract |

**Vendor Lock-In Accepted:** No; provider-specific transport remains behind the adapter profile.

## 4. Implementation Guidance

**Model Configuration:** Backend/profile selected only from validated settings; deterministic/low-variance generation where supported; strict timeout, byte/token cap, and one attempt per interaction unless the user explicitly retries.  
**Core Pattern:** resolve profile -> construct bounded request -> invoke transport -> validate exact schema -> gate every claim/span against permitted and reserved facts -> pass or drop -> append evidence -> authored fallback on any failure.  
**Tool Use:** Hosted CLI subprocess and local OpenAI-compatible HTTP are transport plugins only. Neither receives filesystem/repository tools.  
**State Management:** Append interaction and gate outcomes to the existing evidence store. The model owns no session state.  
**Context Window Strategy:** Send the minimum item fields, actual wrong response, authored analysis, permitted-tier fact manifest, and rubric points needed for the operation; never repository context.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

Pydantic is reference-only for development/eval parity; production uses the equivalent checked-in JSON Schema and stdlib validator.
```python
from typing import Literal
from pydantic import BaseModel, ConfigDict
class HintCandidate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    operation: Literal["hint"]
    interaction_id: str
    spans: list[str]
    claims: list[str]
```
Validation failure is `unavailable`; it is never repaired client-side or shown. An explicit retry creates a child interaction id.

### Async-First Design
The public runtime boundary is bounded and cancellable; the stdlib implementation may use a worker/thread only to avoid blocking a request handler. Never leave a floating provider process or retry loop.

### Prompt Engineering Discipline
System instructions state operation, schema, permitted facts, and prohibited facts. Learner/item text is untrusted data. Prompt rules are defense in depth and have no bearing on gate authority.

### Context Window Management
No conversation memory. Each request is self-contained and fingerprinted; oversized input fails typed and falls back.

### Cost and Latency Budget
One generation per interaction by default; record elapsed time and output size. Timeout or cap exhaustion returns immediately to authored content.

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric | Measurement | Priority |
|---|---|---|---|
| Schema/authority | 100% strict schema; zero score/tier/accepted-mark mutation | Code | Critical |
| Direct leakage | Every exact key/answer/reserved-span case drops | Code | Critical |
| Semantic leakage | Human-calibrated adversarial set; any uniquely identifying entailment drops | Code + human, optional calibrated judge | Critical |
| Error specificity | 4/5 or better and grounded in actual response | Human-calibrated rubric | High |
| Backend parity | Golden requests produce the same normalized shape/status | Code | High |
| Offline continuity | All core-loop fixtures pass with adapter absent/refused/timed out | Code | Critical |
| Pending review | Every rubric suggestion remains pending until explicit human mark | Code | Critical |

### Eval Tooling

**Primary Tool:** Repository stdlib golden/adversarial suites. Arize Phoenix is explicitly not selected because no telemetry/external dependency is allowed; local append-only evidence supplies traces.  
**CI/CD Integration:**
```bash
python tests/model_adapter_roundtrip.py
python tests/tier_gate_adversarial.py
python tests/hint_roundtrip.py
```

### Reference Dataset

**Size:** At least 30 synthetic cases before learner rendering: 10 direct/encoded leakage, 8 semantic entailment/elimination, 4 malformed/provider failures, 4 error-specific good cases, and 4 rubric pending-review cases.  
**Labeling:** Assessment author labels permitted/reserved facts and expected gate outcome; disagreements remain failing/ambiguous until resolved.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|---|---|---|
| Strict response schema | Missing/extra/type-invalid field | Unavailable + authored fallback |
| Reserved-fact detector | Exact, normalized, encoded, or derived answer overlap | Drop whole candidate |
| Ambiguity rule | Claim cannot be proven within permitted facts | Drop whole candidate |
| Authority boundary | Candidate requests score/tier/mark mutation | Reject operation and log |
| Timeout/output cap | Budget exceeded | Terminate transport; unavailable |

### Offline (Flywheel)

| Metric | Sampling | Action |
|---|---|---|
| Gate false-negative/positive | Review all drops plus sampled passes during development | Add adversarial fixture before detector change |
| Specificity/usefulness | Sample passed generated hints | Revise prompt/dataset; never weaken gate |
| Provider parity/latency | Every synthetic backend run | Disable failing profile or tighten cap |

## 7. Production Monitoring

**Tracing Tool:** Existing local append-only evidence store; Phoenix override documented above.  
**Key Metrics:** pass/drop/unavailable by backend and reason; latency/output bytes; explicit retries; authored fallback rate; pending proposal acceptance/replacement.  
**Alert Thresholds:** Any known leakage pass, any accepted-evidence mutation, or any core-loop failure blocks release. Sustained provider unavailable/timeout is surfaced locally but never blocks study.  
**Smart Sampling:** Review all adversarial cases, all ambiguous drops, all explicit retries, and a bounded sample of passes; never transmit traces externally.
