# Phase 999.1: Advanced Visual Item Families — Research

**Gathered:** 2026-08-11
**Status:** brief; resolves the four implemented families and names the two
deferred ones

## Why the phase exists

06.1 delivered plot + number line as protocol integer 1: one declarative
envelope, key-free public projection, exact SCALAR scoring, committed-action
evidence, and an accessible SVG+HTML renderer. ROADMAP Phase 999.1 (BACKLOG,
kept at the 2026-08-10 review for the mechanical reason that 06.1 was
unexecuted — now merged and verified) asks for the advanced families:
`hotspot`, `diagram`, `timeline`, `trace`, geometry/construction, and
dense-simulation-style responses. This phase executes four of the six and
records the other two as named gaps.

## Resolved Questions

### RQ-1: New version or additive extension of protocol 1?
**Resolution: additive extension; version stays 1.** The envelope is a
transport/contract shape, not a taxonomy. New families only grow the three
closed allowlists (`VISUAL_INTERACTIONS`, `VISUAL_KINDS`, `VISUAL_ACTIONS`)
and the per-interaction scene-member allowlist. Reasons: (a) 06.1-01-PLAN
explicitly says "extend it additively"; (b) `public_item` emits one module
constant, so bumping would relabel existing plot items and break 06.1's
locked tests; (c) the interact request, evidence field set, observation shape,
and renderer contract are unchanged, so `interaction_version` still means
"envelope version". Consequence: old consumers that hard-code protocol-1
actions still work for protocol-1 items; new items declare their own
`interaction`.

### RQ-2: What is the semantic response grammar per family?
All values are canonical SCALAR strings (`fractions.Fraction`, existing
grammar) or stable authored ids; never pixels, pointer coordinates, or
screenshots.

| Family | `SCORING.kind` | Wire response | `VISUAL_ACTIONS` (committed) |
|---|---|---|---|
| hotspot | `hotspot` | `{"kind":"hotspot","region":ID}` | `select_hotspot` |
| timeline | `timeline_event` | `{"kind":"timeline_event","event":ID,"value":SCALAR}` | `place_timeline_event`, `move_timeline_event` |
| diagram | `diagram_connection` | `{"kind":"diagram_connection","from":ID,"to":ID}` | `connect_diagram` |
| trace | `trace_path` | `{"kind":"trace_path","points":[{"x":S,"y":S},...]}` | `place_trace_point`, `move_trace_point` |

An exact wire-shape rule (no extra keys) keeps forged authority fields
invalid, exactly as 06.1 does. Identifiers: `[A-Za-z0-9_-]{1,64}`, unique per
scene, no script-bearing tokens (the existing `_reject_visual_exec` scan
covers them).

### RQ-3: How are the new families scored?
Through the same `_visual_verdict` dispatch, with per-family helpers named
`_*_verdict` (the one-scorer structural scan forbids `def *score*`):

- **hotspot**: exact region-id equality (discrete; tolerance must be empty).
- **timeline**: exact event id + value within per-coordinate tolerance (0 =
  exact tick compare; reuses grid/domain helpers).
- **diagram**: exact from/to pair; `from != to` is validated (self-loops are
  invalid, not scored); ids must exist in the scene.
- **trace**: submitted point count must equal the authored `point_count` and
  each point must be within per-coordinate tolerance of the matching accepted
  point (element-wise, in order). Count mismatch or out-of-domain/off-grid
  points fail closed.

Discrete families with a non-empty tolerance and continuous families with a
zero tolerance are authoring errors (lint) and fail validation — the
discrete/continuous boundary is per-family, not inferred.

### RQ-4: What scene configuration does each family carry?
Closed per-interaction scene members (union used by lint):

- **hotspot**: `version`, `plane` (`{width,height}` in abstract units),
  `regions` (`[{id,label,shape,coords}]`; `shape` ∈ `rect`|`circle`|`polygon`,
  coords as SCALARs in plane units), `initial` (selected region id or null),
  `actions`, `accessibility`.
- **timeline**: `version`, `axis` (existing `canonical_axis`), `events`
  (`[{id,label}]`), `initial`, `actions`, `accessibility`.
- **diagram**: `version`, `plane`, `nodes` (`[{id,label,x,y}]`), `initial`,
  `actions`, `accessibility`.
- **trace**: `version`, `axes` (existing two-axis geometry), `point_count`
  (positive integer, bounded ≤ 50), `initial` (the authored reference polyline
  as `points` — public scene data, like 06.1's `initial`), `actions`,
  `accessibility`.

The reference polyline in `initial.points` is *scene data*, not the accepted
answer: the accepted trace is the private `SCORING.accepted` list. An author
may (and for a trace item should) make the reference path and the accepted
path coincide, but the scorer reads only `accepted` — the renderer can draw
the public path without revealing the verdict.

### RQ-5: Which new lint codes are needed?
Reuse the 06.1 codes where the cause is the same (unknown member/action/kind,
invalid axis/scalar, malformed JSON, executable member, empty accessibility).
Add exactly two:
- `item.visual_duplicate_id` — duplicate `regions`/`events`/`nodes` ids.
- `item.visual_invalid_geometry` — malformed `plane`/`regions`/`nodes`
  shapes, unknown `shape`, coords outside the plane, `point_count` out of
  bounds, or a tolerance on a discrete family.

### RQ-6: Does the renderer need a new surface?
No — one `asVisual` adapter dispatches on `interaction`. Each family adds an
SVG scene + adjacent semantic controls (radio/select lists, steppers,
select-pairs) that reduce through one state object and one serializer, exactly
as 06.1 does. The offline static path (`asVisualOffline`) already refuses
every visual item by type with the served-runtime copy; no change.

### RQ-7: What about the deferred families?
- **Geometry/construction**: needs a multi-step construction protocol —
  drawn-object history, undo/redo, step-scoped validation, and a sequence
  response grammar (`{"kind":"construction","steps":[...]}`). That is a
  protocol-design effort (compare 06.1-RESEARCH's locked bounds) and belongs
  in a dedicated phase, not a response-kind extension here.
- **Dense-simulation-style**: 06.1's canvas rule requires the identical
  semantic HTML state/control path. A safe first slice is a *deterministic
  parametric simulation*: `SCALAR` parameter sliders authored in the scene, a
  deterministic authored readout rule executed in the runtime (no bank JS), a
  final parameter-set response, and "run" as an observation-only action. The
  readout rule grammar (arithmetic over parameters, bounded, no scripting) is
  a design question; defer.

## Named gaps carried into the HANDOFF

1. Geometry/construction family — protocol design needed (RQ-7).
2. Dense-simulation-style responses — deterministic-parametric design,
   canvas-rule gate (RQ-7).
3. Diagram label/match variants and multi-connection responses.
4. Trace: only one ordered polyline with fixed `point_count`; free-length
   tracing and multi-segment matching deferred.
