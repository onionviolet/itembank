<objective>
Write the grammar down well enough that a model with nothing but `itembank spec` can author a lesson
that lints clean on the first attempt — and then actually try it.

**User story (MVP framing, from ROADMAP Phase 3 Goal):** **As a** tutor model asked to write the
lesson an item is drawn from, **I want to** read one contract that tells me exactly what a lesson looks
like, **so that** what I write parses, links and lints without a round trip through the source.

Purpose: LESSON-05 and ROADMAP Success Criterion 4 are the same claim, and it is the only one in this
phase that cannot be closed by a `python` one-liner. The spec goes last on purpose: it documents what
actually shipped rather than what was planned, including the renderer's real markdown scope from plan
03-04 and the four lint codes from plan 03-03.

Output: the LESSON grammar inside `model.SPEC`, a test that keeps the spec and the published codes from
drifting apart, and a human trial of the criterion the spec exists to satisfy.
</objective>

  <action>
Write the coverage assertions into `tests/lesson_roundtrip.py` first, run the file, and confirm they

**1. `model.py` — the grammar block.** Add a LESSON section to `SPEC`, and add the item tag one line to
the existing shared-fields block beside the other optional bracketed tags, so an author reading the
shared fields sees it without having to reach the new section. Write it in the constant's established
voice: instructions to an author, with the reason stated wherever the rule would otherwise look
arbitrary.

Cover, in this order:

- **Placement.** The section opens with the lesson heading marker and lives above the first question
  marker; its subheadings are one level deeper. Say explicitly that a bank with no lesson section
  parses exactly as it did before this existed, because that is the promise that makes adding a lesson
  to a real bank safe.
- **The external source.** The directive, its position in the same region, that its path resolves
  relative to the bank file, that a path resolving outside the bank's own directory is refused rather
  than read, and that an external source takes precedence when a bank carries both. State the reason
  for the refusal in one clause: a bank should not be able to name an arbitrary file on the machine.
- **The item tag.** Its shape, that it names readable heading text rather than an id, and that one item
  carries at most one.
- **The slug rule.** Lowercased, whitespace collapsed, punctuation dropped. State it concretely enough
  that an author can see for themselves that two headings differing only in punctuation or casing will
  collide, and say that a collision is an error because a reference to either becomes ambiguous. This
  paragraph is what turns a linter message into something an author could have predicted.
- **What renders.** The exact list of constructs the reader supports, taken from what plan 03-04
  actually shipped, and one sentence saying anything outside that list appears as literal text. An
  author who knows the boundary does not write past it.
- **The fenced-block convention.** The info string and what it is for: a later phase attaches maths
  rendering and a run button to it by name, so the info string is worth writing correctly even though
  nothing acts on it yet.
- **The one constraint.** A line inside lesson prose that begins like a question marker ends the lesson
  there. This is a property of the split boundary that has always existed and that the grammar tells
  authors to avoid rather than trying to make the boundary context-sensitive, which would put the
  compatibility promise at risk for a rare authoring habit.
- **The lint codes.** All four by name, what triggers each, and which are errors and which is the
  warning. Say why the orphan case is a warning: a lesson legitimately teaches more than it tests.

Keep every existing line of `SPEC` intact — other tests and CI grep it for substrings, and the constant
is a published contract where a rewrite is a breaking change for every consumer even when the words
improve. There is nowhere else to add this text: `itembank schema --all` publishes this constant
verbatim, so one edit reaches both commands, and a second copy anywhere would be a second contract.

  <what-built>
The whole phase. A `LESSON` grammar that lives above the first question in a bank or in a shared
external file; a `LESSON-REF` item tag that links an item to a heading; four lint codes that fail a
dangling reference by item number; a reader at `GET /lesson/<bank>` with its `itembank lesson` twin,
rendering headings, paragraphs, lists, tables, inline and fenced code, emphasis and links; links running
both ways between a heading and the items that test it; and `itembank spec` documenting all of it.

Three things in this phase cannot be closed by a command, and are collected here rather than left as
silent gaps. Two are the backstop rows `03-UI-SPEC.md`'s UI Considerations flagged; the third is
ROADMAP Success Criterion 4 itself, which is a claim about whether a model can act on the spec and is
testable only by trying it.
  </what-built>
  <how-to-verify>
**1. The spec-sufficiency trial (ROADMAP SC4, LESSON-05).** Run `python itembank.py spec` and copy its
output. Open a fresh model session with no access to this repository. Give it only that output and ask
it to write a bank containing a `LESSON` section with two headings and three items, at least one
tagged with a `LESSON-REF`. Save what it produces and run `python itembank.py lint <that file>`.

It must exit 0 on the **first** attempt. If it does not, read the failures: each one names a thing the
spec did not say clearly enough. That is the finding — report which rule the model got wrong, not just
that it failed.

**2. A full-chapter lesson renders and scrolls (UI-SPEC E1 long-text backstop).** Make a large lesson —
roughly 20,000 words is the figure UI-SPEC names; padding one of the fixtures' sections with repeated
paragraphs is enough. Start `python itembank.py daemon fixtures --no-open --port 0`, open
`/lesson/<that bank>` in a browser, and scroll from top to bottom.

Expected: one continuous document, no pagination, no lazy loading, no perceptible stall while
scrolling. Report whether the scroll felt smooth — this is a perceived-performance judgment and there
is no timing threshold that means anything without a human reading it.

**3. `itembank lesson` on a very large external source does not read as a hang (UI-SPEC E5 long-text
backstop).** Point a bank's `[LESSON-SRC:]` at the largest lesson file you have and run
`python itembank.py lesson <that bank> --out /tmp/big.html`. The command prints nothing until it
finishes, by design.

Report whether the silence read as a hang. If it did, that is the signal to add a progress line — and
only if it did; UI-SPEC deliberately left this unsolved rather than adding output nobody needed.

**4. A quick pass over the two link directions in a real browser.** Open `/lesson/lesson_bank`, click a
backlink, confirm it lands on the quiz with that item shown first. From the quiz item, click
`Read the lesson`, confirm it opens a new tab at the right heading. Then open
`/lesson/lesson_bank#<a-slug>` directly and confirm the browser lands on that section.
  </how-to-verify>
