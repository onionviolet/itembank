> **Phase goal (quoted verbatim from `.planning/ROADMAP.md` § Phase 7 — this line is
> NOT in user-story form; run `/gsd mvp-phase 7` to convert it before the next replan):**
> A session is assembled by rule, not by hand — targeted at an objective, a difficulty,
> or a discrimination pair — and the tool can say why it picked each item.

<objective>
Teach the format contract two new additive tags — `[PAIR:]` for a named confusion set
(D-07) and `[PREREQ:]` for the prerequisite objectives an item assumes (D-12) — and give
`select()` the two filters that read them. After this plan a learner can ask for a
discrimination pair by name and get both items served together, and can filter a session
to the items that build on a named prerequisite.

Purpose: SEL-04 and the prerequisite half of SEL-01 have no backing field anywhere in the
codebase today. `model.py:61`'s `conf` parses `CONFIDENCE:` — the author's confidence in
the item, not a confusion set — a finding 07-RESEARCH.md verified rather than assumed.
Both tags are genuinely new ground.

Output: two parsed fields, two lint codes, two spec filters, and a fixture that carries
real pair groups and a real prerequisite chain for every later plan to test against.
</objective>

## Trust Boundaries

|----------|-------------|
| Bank markdown → `model.parse_question()` | Author-supplied tag text becomes a parsed field |
| CLI argv / `/api/start` body → `select()` | A `pair` or `prerequisite` value becomes a filter |

| T-07-01 | Denial of Service | `filter_by_pair` / `filter_by_prereq` | low | mitigate | Both are exact string comparisons over an in-memory list, never regex and never a scan of anything unbounded; a bank is already fully parsed before either runs |
