> **Phase goal (quoted verbatim from `.planning/ROADMAP.md` § Phase 7 — this line is
> NOT in user-story form; run `/gsd mvp-phase 7` to convert it before the next replan):**
> A session is assembled by rule, not by hand — targeted at an objective, a difficulty,
> or a discrimination pair — and the tool can say why it picked each item.

<objective>
Make a sitting say, on the record, what it asked for. Two one-way doors are walked through
here and both are gated first: the field name that separates selection composition from
feedback policy (D-11), and what the append-only evidence log records about a selection
(D-03). Neither can be undone later without a migration over the log, which is why they
are decided before the four compositions are built on top of them in plan 07-05.

Purpose: the collision is not hypothetical. `schemas/session.schema.json:41-44`,
`schemas/response.schema.json:59-62` and `surfaces/daemon.py:670` already enumerate
`"remediation"` as a *feedback* mode value — one of this phase's four *selection* mode
names, already shipped in the wrong axis, in two published contracts. Documented coupling
is no longer available as an option.

Output: a distinct `selection_mode` field on the request, the session and every response
event; the resolved spec recorded on the session and once in the evidence log; and both
published contracts extended additively.
</objective>

  <name>Task 1: DECISION (one-way, D-11) — the selection-mode field name</name>
  <decision>What names the selection composition on the request, the session and the evidence log — a distinct `selection_mode` field, or the existing `mode` field?</decision>
  <context>
`mode` already means *feedback policy* everywhere in shipped code: MODE-01..06 in
`REQUIREMENTS.md`, the enum in `schemas/session.schema.json:41-44`, the wider enum in
`schemas/response.schema.json:59-62`, and `surfaces/daemon.py:670`'s `SESSION_MODES`.
Three of this phase's four selection-mode names (`diagnostic`, `practice`, `exam`) are
already values in that feedback enum verbatim, and the fourth, `remediation`, is sitting
in it too with no MODE-0x requirement behind it.

The evidence log is append-only. Once a value is written under a conflated field, telling
the two axes apart later needs a migration over every recorded event — there is no
in-place rename. That is what makes this a one-way door rather than a naming preference,
and it is why you are being asked before anything is written rather than after.
  </context>
  <options>
    <option id="option-a">
      <name>A distinct `selection_mode` field (07-CONTEXT.md D-11's resolution; recommended)</name>
      <pros>The two axes can never alias, in any surface or any recorded event. `mode` keeps meaning exactly what it already means in two published schemas and one daemon constant, so nothing shipped changes meaning. A query can ask "how did I do on exam-mode *feedback* under practice-mode *selection*", which is a real question and unaskable under any other option. Both schema changes are additive optional fields, so no session or event written before today becomes invalid.</pros>
      <cons>One more field on the session, on the response event and on the spec. A reader skimming a session file sees two mode-ish keys and has to know which is which; the schema descriptions carry that burden.</cons>
    </option>
    <option id="option-b">
      <name>Reuse `mode` for both, with a documented rule that the two are always set together</name>
      <pros>No new field anywhere. A session file has one mode key.</pros>
      <cons>The rule is documentation, not a mechanism, and `remediation` is already in the feedback enum with nothing behind it — the conflation is already half-shipped. Splitting them later means a migration over the whole append-only log. This is the option the research explicitly recommends against after verifying the collision in three files.</cons>
    </option>
    <option id="option-c">
      <name>Rename the existing feedback field to `feedback_mode` and give `mode` to selection</name>
      <pros>The clearest final vocabulary; `mode` ends up meaning the newer, more load-bearing axis.</pros>
      <cons>A breaking change to two published contracts and every event already recorded under `mode`, i.e. exactly the migration the other options exist to avoid — and it would land in the middle of a phase whose scope is selection, not a contract rename.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Task 2 below is written for option-a; choosing option-b or option-c requires this plan to be revised before execution continues.</resume-signal>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argv / `/api/start` body → the resolved spec | A learner-supplied `selection_mode` becomes a recorded value |
| the resolved spec → the append-only evidence log | Request data crosses into permanent, un-editable storage |
| the recorded `selection_spec` → any later reader | Whatever is written here is readable by every later phase and every report |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Denial of Service | `selection_mode` arriving from `/api/start` | medium | mitigate | An absent or unrecognised value is coerced to `"practice"` in the same defensive style as the existing `count`/`seed`/`mode` coercions; `select()` additionally raises a named `SystemExit`, which `handle_api_start`'s existing `except SystemExit` clause turns into a 400 rather than killing the daemon |
