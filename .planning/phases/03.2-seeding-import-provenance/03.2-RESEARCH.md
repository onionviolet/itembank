## Summary

Three findings:

1. **D-02's stdlib-only .apkg claim is unmeetable for modern Anki exports, and the fix is one pinned dependency.** Modern Anki exports (2.1.50+) ship `collection.anki21b` - a zstd-compressed SQLite database inside the .apkg ZIP [VERIFIED via web: Anki forums thread 31788; the 5mdld/anki-apkg-extractor README ("collection.anki21b = zstd-compressed SQLite"); gnosis-anki's "Support modern .apkg format (zstd-compressed)"). The Python stdlib has no zstd decoder (the `zlib` module covers deflate only), and there is no pure-Python zstd implementation (Anki forums: "There is no pure Python library that decompresses these files. You can use a package like pyzstd"). The handoff's default applies: take one dependency (`zstandard`), pin it, checksum it, license-review it under Directive 4a, and say so plainly. The load-bearing requirement is D-03's second clause - lossless import with a per-note account, no note silently dropped - not the stdlib-only mechanism.
2. **The importer composes with existing machinery as a client, not a validator:** it reads the ZIP (stdlib `zipfile`), decodes the collection (zstandard + `sqlite3`), maps Anki note types to itembank item types (a named mapping table - unknown types take the GIFT loud-refusal path per D-04), runs `model.lint()` on every candidate before anything is written (D-05), and writes nothing without the human-accept loop (D-06). The existing `surfaces/gift.py` refusal pattern is the template; `itembank guard` extends its globs for D-17 rather than adding a second guard.
3. **The six-stage order (D-08) is the phase's own finding, not borrowed:** deterministic source selection before drafting, deterministic checks before any model critique, and independent verification before human accept. No plan may reorder it or carry an invented adherence figure - the CONTEXT names the staging as a structural argument with no benchmark (the named unknown).

## 1. The .apkg format - what D-02 actually requires

**Finding: the .apkg container is a ZIP, but the collection inside changed format.**

| Member | Anki < 2.1.50 | Anki 2.1.50+ |
|---|---|---|
| `collection.anki2` | plain SQLite | - (legacy) |
| `collection.anki21` | SQLite | SQLite (legacy 2.1) |
| `collection.anki21b` | - | **zstd-compressed SQLite** |
| `media` | JSON map | JSON map |

Anki 2.1.50+ exports ship `collection.anki21b` (zstd-compressed) [VERIFIED: Anki forums thread 31788; anki-apkg-extractor README; gnosis-anki changelog]. The stdlib's `zipfile` opens the ZIP fine; `sqlite3` opens the legacy collections fine; **neither decodes zstd**. There is no pure-Python zstd decoder ("There is no pure Python library that decompresses these files" - Anki forums), so a modern .apkg cannot be read stdlib-only.

**Resolution (default per the handoff):** take one pinned dependency - `zstandard` (the maintained binding; `pyzstd` is the addon-ecosystem alternative) - with a recorded checksum and license review per Directive 4a, and update D-02's mechanism note in the plan: ZIP + sqlite3 via stdlib, zstd via the one pinned dependency. The D-03 guarantee (exhaustive per-note report, no silent drop) is the load-bearing clause and is unchanged. If a legacy `.apkg` (plain SQLite member) is detected, the importer reads it with zero extra dependencies - the dependency is conditional on the member type, not a blanket requirement.

**Empirical verification (2026-08-10, this session):** a real, modern shared deck
was downloaded and inspected rather than relying on web sources alone. The
sample (`504_Absolutely_Essential_Words_Persian.apkg`, 106,459 bytes, exported
2023-05-04, 504 notes) contains exactly these members:

```text
meta                2       0
collection.anki21   311296  8   (plain SQLite, deflate-compressed inside the ZIP)
collection.anki2    38912   0   (legacy plain SQLite, stored)
media               2       0
```

`collection.anki21` opened directly with stdlib `sqlite3` (tables: cards, col,
graves, notes, revlog) — **no zstd required for this file**. So the zstd claim
is real but conditional, not universal: `collection.anki21b` appears when the
exporter targets Anki 2.1.50+ ("optionally target Anki 2.1.50+" in the 2.1.50
release notes), while compatibility/default exports still ship plain
`collection.anki21`. The importer MUST detect the collection member and branch:
`collection.anki21b` → zstandard; `collection.anki21`/`collection.anki2` →
stdlib `sqlite3` only. This confirms the resolution above: the zstandard
dependency is conditional on the member type, and the D-03 per-note accounting
clause is the load-bearing requirement regardless of format.

## 2. The importer shape

The importer is a client of the one parser/validator (D-05):

1. `zipfile` opens the .apkg; inspect members. `media` map read for note-to-media reference resolution (referenced media copied beside the bank, or referenced by name - executor discretion; source media files are not the author's prose and are not governed by D-13).
2. Detect the collection member: `collection.anki21b` - decode with the pinned zstandard; `collection.anki21`/`collection.anki2` - plain `sqlite3`.
3. Read the `notes` table (fields, tags, note type id) and the `note_types` table; map each note type to an itembank item type through a named mapping table (`anki_note_type_map`). Unknown note types take the GIFT loud-refusal path per D-04 - named per note, never approximated.
4. Build candidate items, run `model.lint()` (D-05); lint failures are reported per candidate, nothing is written.
5. The per-note report (D-03) is exhaustive: converted / skipped / refused, each with the note id and reason, output to stdout and the report file. No note is silently dropped.

## 3. The seeding loop and its two surfaces (D-06..D-10)

- The accept loop is **draft - lint - retry - human accept, one item at a time** (D-06). Nothing writes to a bank without an accept; autonomy beyond that is Phase 11's.
- Both surfaces (D-07): one accept endpoint (CLI + daemon route), never two implementations of the decision. The browser surface is a client of the same endpoint the CLI calls.
- Batch framing (D-09): the UI shows staged progress and a cancel; it never presents as interactive chat; a cancelled run writes nothing.
- Degrade-never-block (D-10): with no model backend, seeding refuses by name; import, lint, [SRC:] resolution, and the coverage map still work.
- The default authoring backend is a hosted coding-agent-class model (Directive 1); prompt-size and latency budgets are written against it.

## 4. Provenance, paraphrase lint, and edges (D-11..D-16)

- `## SOURCES` registry (D-11): additive section mapping source ids to locators; `[SRC: <id> <locators>]` and `[OBJ: framework/objective-id]` resolve through it; an unresolvable id is a lint error naming the id and the file.
- Coverage map (D-12): computed on demand from the bank and the registry, never stored.
- Paraphrase lint (D-13): stdlib winnowing over fingerprints (k-gram hashing, window size at executor discretion); error at >=8 consecutive copied words, warn above Jaccard 0.25; both thresholds are settings; **source text is never stored** - the defensible posture for AAOS-derivative EMT content, and a one-way design decision per the CONTEXT.
- `style.unsourced_specific` (D-14): numerals, units, and doses require a `[SRC:]`; a structural check registering into the closed LINT_CODES catalogue Phase 3.1 defines - it does not open the catalogue.
- `[CASE:]` (D-15) and `[PREREQ:]` (D-16): authored grouping and edges, linted here (cycle detection, unresolvable targets), consumed by Phases 6/7.

## 5. Corpus and calibration (D-17/D-18)

- The real EMT/Math 1400/CSCI 1100 corpus lives beside the private bank, outside this repo; `itembank guard` extends its globs to keep it out of CI (D-17).
- The corpus is the calibration set for every Phase 3.1 style warning (D-18): a warning ships enabled only with a recorded false-positive rate; above ~20% it ships disabled by default. The calibration run and its recorded rates are a deliverable of this phase.
- D-19 (contention): seeding writes items, style passes write prose; with the two-file lesson layout default they do not contend for one file.
