# Phase 17A — UI Design Contract

> Visual and interaction contract for the token freeze, typographic hierarchy,
> responsive shell, and accessible component primitives serving every surface
> named by 16B and 16C. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Non-interactive session; every point the workflow would
> normally ask a question about is resolved here and marked **ASSUMPTION** so
> the checker and planner can revisit it explicitly rather than silently.

**Binding scope reminder (from 17A-CONTEXT.md).** 17A styles and freezes what
16B and 16C already specified structurally; it does not re-decide their IA,
routes, copy, or mode authority. This document is additive over
`.planning/UI-SPEC.md` (project-level, cross-phase), `16B-UI-SPEC.md`, and
`16C-UI-SPEC.md`. Where those documents say "deferred to 17A," this document
is where that deferral resolves. Nothing here contradicts a LOCKED row in any
of those three documents.

**The freeze gate itself is out of scope for this document.** Per D-11
(17A-CONTEXT.md), no 14B-or-later freeze — including 17A's own — closes
before the Phase 13.9 walking skeleton has been walked. This UI-SPEC defines
the contract the freeze will be measured against; it does not declare the
freeze closed.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — stdlib Python with embedded server-rendered HTML/CSS/vanilla JS. No shadcn, registry, npm, or external component dependency (unchanged since Phase 4; confirmed this session: `components.json`, `tailwind.config.*`, `postcss.config.*` all absent). |
| Preset | not applicable |
| Component library | none — native semantic HTML first; inline SVG for visual items; vendored KaTeX for math. `surfaces/presentation.py`'s `surface_shell`/primitives are the one shared component layer every route composes. |
| Icon library | none introduced by this phase. Every state marker (anchor chips, job outcomes, fill-state blocks) renders as a **text label first**; a glyph, when added, is a decorative addition that never replaces the label (16B/16C already ruled icons "deferred to 17A's token freeze, rendered as a text label alone until then" — this phase keeps that rule rather than adopting an icon set, see Iconography below). |
| Font | Vendored, shipped, and in production use: Source Serif 4 (400/600) and iA Writer Quattro (400/700, resolves to 700 under a `600` request per the shipped weight-matching rule) under `vendor/`, OFL-1.1, pinned and checksummed. **Correction of a stale record:** `.planning/UI-SPEC.md:485` still reads "Status: NOT ADOPTED"; this is false as of this session (`surfaces/presentation.py` lines 117-126 ship all four `@font-face` rules; `STATE.md` line 493 records the vendoring). §7.4 of the project UI-SPEC should be marked adopted the next time that document is touched (recorded here per the CONTEXT.md `<specifics>` note; not this phase's file to edit directly). |

**shadcn gate result:** not applicable, per the same reasoning `16B-UI-SPEC.md` and `16C-UI-SPEC.md` recorded. This project is not React/Next.js/Vite. `Tool: none` is recorded per the gate's own instruction for this case. Registry safety: not applicable, no component registry exists in this project.

**Design inspiration, translated into concrete rules (per user direction "be inspired by DeepSeek harness and other comprehensive stuff").** This is interpreted as borrowed *qualities*, never borrowed branding, chrome, or a second design language:

| Quality observed in dense, polished AI/dev-tool harnesses | Concrete rule adopted here |
|---|---|
| Calm, restrained color; one accent hue doing real work, not decoration everywhere | Reuses the existing 60/30/10 split and the "accent reserved for" list below; no new accent use is authorized by this document. |
| Dense information layout that never feels cluttered, achieved by hierarchy and whitespace rhythm rather than by hiding density | The 4/8px micro-rhythm (`--space-1`/`--space-2`) governs compact chrome (chips, labels, table cells); the 24/32/48px rhythm (`--space-4..6`) governs section breaks; nothing in between is invented. |
| Monospace/ledger-style status widgets that read as "the system talking," visually distinct from prose | Already the product's own thesis (`--font-ledger` voice, project `UI-SPEC.md` §7.3); 17A's job is to apply it consistently to every new 16B/16C surface rather than invent a second status idiom. |
| Well-structured bordered panels with thin, low-contrast borders and minimal or no shadow | Matches the already-fixed "modest surface treatment" rule (`UI-SPEC.md` §15.3); this phase's card/panel primitive uses `--line` borders at `--r-2` radius, never a drop shadow beyond the smallest functional elevation the existing `--card`/`--bg` split already implies. |
| Progressive disclosure as the default posture for secondary information (side panels, metadata, long lists start collapsed) | Locked structurally in the **Progressive Disclosure & Default-Collapsed Contract** section below — this is the direct implementation of the second half of the user direction. |
| Sticky, minimal top context rather than a heavy persistent toolbar | Already fixed by RTS-02's two-row sticky-context-line ceiling; 17A applies it, does not relax it. |

No new visual "theme" is being borrowed. These rows exist so a plan or an
executor has a named reason for a density/disclosure choice instead of
reaching for an arbitrary card-grid-and-gradient default.

## Token Freeze Scope & Proof (D-01, D-02, D-03)

**What freezes.** The existing token layer is the base, extended only by
whatever the winning visual direction adds:

- **Color** — `surfaces/theme.py` `BASE_TOKENS`, `SEMANTIC_TOKENS`, and the
  accent-derivation pipeline (`TEXT_CONTRAST=4.5`, `FOCUS_CONTRAST=3.0`).
  Measured, current values are reproduced in the Color section below so this
  document is checkable against served bytes, not just against prose.
- **Non-color** — `surfaces/presentation.py` `SHARED_CSS`: four vendored
  `@font-face` rules, `--space-1..7`, `--measure-prose`/`--measure-wide`,
  `--r-1/2/3`, the four voice tokens, `--weight-normal`/`--weight-emphasis`.
- **Type scale** — currently *unfrozen*: literal `font-size` values are
  scattered per surface (12px, 16px, 18px lesson-only, 20px, 32px are the
  distinct sizes actually in use today, confirmed by direct code inspection
  of `quiz_page.py`, `lesson.py`, `study.py`, `presentation.py` this
  session). This phase's job is to **name these as tokens** (see Typography)
  so "twelve sizes to five" (13.5's own framing of the same defect,
  `STATE.md` line 577) becomes "five named tokens, applied everywhere,"
  not a fresh redesign of the sizes themselves. No new size is introduced
  beyond what is already rendering.

**Proof mechanism (D-01).** The freeze is proven on served bytes, not
documentation: `tests/stylesheet_roundtrip.py` already asserts every daemon
route's four `@font-face` rules resolve to 200 and that every `var(--…)`
reference in a served document resolves to a custom property defined in that
same document (RTS-01). The 17A freeze fixture extends this exact pattern to
cover the newly named type-scale tokens and every 16B/16C surface once built.
A plan that adds a route without passing this fixture has not frozen
anything, regardless of what its own CSS claims.

## Spacing Scale

Declared values (confirmed shipped in `presentation.py` `SHARED_CSS`, not
newly introduced):

| Token | Value | Usage |
|-------|-------|-------|
| `--space-1` | 4px | Icon/glyph gaps, chip inline padding, compact label spacing |
| `--space-2` | 8px | Compact element spacing, table cell padding, chip gaps |
| `--space-3` | 16px | Default element spacing, card interior padding |
| `--space-4` | 24px | Section padding, panel gaps |
| `--space-5` | 32px | Layout gaps, `h2` top margin |
| `--space-6` | 48px | Major section breaks |
| `--space-7` | 64px | Page-level spacing |

Exceptions: dense day-page cells may use 36px only when a neighboring target
stays at the 44px floor (carried forward from the project-level `UI-SPEC.md`
§7 Tokens table; unchanged by this phase). No new spacing value is
introduced.

**Touch target floor:** 44px minimum for any interactive control, inherited
from the project-level accessibility gates (`UI-SPEC.md` §8) and restated as
binding on every new 16B/16C component this phase styles (note-capture
affordances, anchor pickers, disclosure toggles, chip actions).

## Typography

**The five named tokens this phase freezes** (collapsing the scattered
literal sizes found in code to exactly these, per D-03):

| Token | Size | Weight | Line Height | Voice | Scope |
|-------|------|--------|-------------|-------|-------|
| `--text-xs` | 12px | 400 | 1.4 | Chrome or Ledger, per context | Labels, provenance, compact status, table headers, chip text |
| `--text-body` | 16px | 400 | 1.5 | any of the four, per §7.3 assignment | Default UI copy, item stems/options, prose that is not sustained lesson reading |
| `--text-lesson` | 18px | 400 | `--leading-lesson` (1.65) | `--font-paper` only | Sustained authored lesson prose only (unchanged scope rule from the project UI-SPEC — not a general fifth UI size) |
| `--text-heading` | 20px | 600 | 1.2 | Chrome (tool headings) or Paper (lesson section headings) | Section/activity/panel headings |
| `--text-display` | 32px | 600 | 1.1–1.2 | Chrome | Page-level result, score, or major report heading only |

**ASSUMPTION (checker/planner-revisable):** these five names and their pixel
values are a direct transcription of what is already rendering today across
`quiz_page.py`, `lesson.py`, `study.py`, and `presentation.py` — this phase
does not invent a sixth size or move an existing size. If a 16B/16C component
genuinely needs a size between 16 and 18 or between 20 and 32, that need is
routed through this table's existing rows first (does the content belong in
`--text-lesson` scope, or is it a heading?) before a new token is proposed;
adding a sixth token requires a recorded reason (per the extensibility
discipline already governing the style registry).

**Weights:** `--weight-normal` (400) and `--weight-emphasis` (600) only — the
LOCKED 2026-08-10 ruling stands unchanged; no third weight, and a face
without a 600 master (iA Writer Quattro) resolves up to its shipped 700 by
ordinary CSS matching, still one emphasis tier.

**Measure (confirmed from code, corrected from a stale documentation
value):** `--measure-prose: 59ch` and `--measure-wide: 80ch`. The
project-level `UI-SPEC.md` still documents `66ch`/`90ch` in places (§7.1,
§8), but `presentation.py`'s own comment block (lines 76–86) records that
plan 14-02 deliberately moved these values so that the *rendered* character
count at 18px Paper voice lands at 66 real characters (not the raw `ch`
count) — the shipped code is authoritative per the same "code wins over a
stale spec line" precedent §7's weight ruling already established. 17A's
freeze fixture measures against **59ch/80ch**, not the older documented
numbers.

**Voice assignment rule (unchanged, restated as binding on every 17A
component):** voice is assigned by who authored the string, never by visual
preference (`UI-SPEC.md` §7.3). A new component this phase styles that
cannot say which of Paper/Ledger/Chrome/Code (or "no voice, Chrome-voice
pending container" for model output) a string belongs to has found a spec
gap in 16B/16C, not a free styling choice — resolve it by checking those
documents' own voice-assignment tables before inventing one here.

All seven semantic tokens (`ok`/`bad`/`warn`/`unknown`/`pending` plus their
`_bg` pairs, plus `edge`) are already measured against the project's own
`contrast_ratio` function and asserted by
`tests/stylesheet_roundtrip.py:check_semantic_token_contrast`. This phase
does not re-pick a value; it verifies the fixture still passes as 16B/16C
surfaces begin consuming these tokens for the first time (a new *consumer*
of `--pending`, for example, cannot regress the *token's* own measured
contrast, but a poor pairing choice in a new component — e.g. `--pending` text
on `--card` instead of `--pending_bg` — is a real defect this phase's
component contracts below must not introduce).

**Accent reserved for (never widened by this phase):** focus rings, the
current/selected nav item, and exactly one primary action per screen (e.g.
"Resume {course}", "Save to my notes", "Accept into course"). Never a status
chip, an Activity job outcome, a fill-state block, a degraded-state banner,
or a destructive action — those are semantic tokens by contract, restated
verbatim from `16B-UI-SPEC.md`/`16C-UI-SPEC.md`.

**Never-color-alone rule:** every semantic-token usage carries a required
text label (already tabulated exhaustively in 16B's and 16C's Color
sections; this document does not repeat those ~25 state/label pairs, it
inherits them as binding and supplies only the pixel-adjacent styling: token
→ background pairing, border treatment, icon-optional glyph slot).

## Configurable vs. Fixed (LOCKED, carried forward verbatim from `UI-SPEC.md` §15.3 — D-10)

| Configurable (safe bounds apply) | Fixed (never configurable, never themeable) |
|---|---|
| Light/dark palette (accent source only; semantic tokens stay fixed per mode) | Content hierarchy |
| Density (see Density Tokens below) | Status meaning (which token means what) |
| Reading measure, within safe bounds | Focus visibility |
| Font choice, from approved local assets only | Contrast (WCAG floors) |
| Modest surface treatment (border weight/radius within the `--r-1..3` set) | Keyboard order |
| Optional motion (respecting reduced-motion) | Target size (44px floor) |
| | Zoom and reflow behavior |
| | Non-color state cues |
| | Source and acceptance visibility |
| | Semantic equivalence across widths |

Authors select semantic roles (a callout kind, a state token), never raw
colors, shadows, coordinates, arbitrary icons, or animation curves. This
table is the literal clamp the token-abuse fixture checks against.

**Density tokens (new, this phase's addition, extends rather than replaces
the existing spacing scale — Claude's Discretion per CONTEXT.md).**

| Token | Comfortable (default) | Compact |
|---|---|---|
| `--density-row-gap` | `--space-3` (16px) | `--space-2` (8px) |
| `--density-card-pad` | `--space-3` (16px) | `--space-2` (8px) |
| `--density-list-gap` | `--space-2` (8px) | `--space-1` (4px) |

Density is a *configurable* token per the table above; it never drops below
compact (still an aliased multiple of the existing `--space-*` scale, never
a new raw pixel value) and never affects the 44px touch-target floor, which
is fixed regardless of density.

## Three-Direction Prototype Contract (D-04, D-05, D-07, VISUAL-01)

**This is 17A's actual deliverable before any freeze**, not an optional
exploration. The prototypes render the one specified synthetic flow (research
report 10 §251-262, reproduced here so a plan does not have to cross-reference
it):

1. Shelf resume
2. A source-linked objective
3. A long lesson containing: definition, warning, table, cited image, inline
   prediction, inline check
4. A wrong answer with entitled feedback and retry
5. Evidence review with sparse data and a pending prose mark
6. An AI-proposed lesson change with citations and diff
7. Agent and offline status

All three directions — **Structured Studio**, **Quiet Workbench**, **Guided
Canvas** — project this identical flow. A prototype that shows a different
demo scenario per direction has not satisfied VISUAL-01 and cannot be used
for the direction comparison.

**Direction definitions (from research report 10 / synthesis §9.3), stated
as concrete deltas over the shared token layer so a prototype builder has a
checklist, not a mood board:**

| Axis | Structured Studio | Quiet Workbench | Guided Canvas |
|---|---|---|---|
| Panel structure | Two-column workspace (Activity + Contextual support), sticky context line, bordered cards | Single-column, generous vertical rhythm, minimal chrome, support panel becomes an inline disclosure rather than a persistent column | Staged, step-framed panels for guided moments only; more visual scaffolding (numbered steps, progress-through-stage markers using text, never a percent) |
| Density | `--density: comfortable` default | `--density: comfortable`, biased toward *more* whitespace in reading contexts (larger effective line length within the `--measure-prose` ceiling, more vertical space between blocks) | `--density: comfortable`, but staging chrome (step markers) adds structural elements Quiet Workbench omits |
| Card/border treatment | Visible `--line` borders at `--r-2`, distinct card boundaries | Borders present but lower-contrast application (rely more on whitespace than border to separate blocks), matching a "reading surface" feel | Cards present, staged sections get a slightly heavier `--r-3` treatment to read as a distinct "guided moment" container |
| Disclosure default | Collapsed-by-default per the Progressive Disclosure Contract below, uniformly | Collapsed-by-default, same contract, with an even stronger bias toward hiding secondary panels since the direction's whole thesis is calm density | Collapsed-by-default, same contract, but a guided moment may pre-expand exactly the tier the flow's current stage needs (never more) |
| Where each direction "wins" per the working hypothesis | Everyday reading, practice, and evidence review (the majority of session time) | Long-form lesson reading and evidence review specifically | Bounded guided-learning moments (first walkthrough steps, a guided note-construction prompt) |

**Working hypothesis for effort allocation (D-05, not the decided answer):**
Structured Studio as the base, with Quiet Workbench density borrowed for long
reading/review and Guided Canvas staging bounded to guided moments — this
supersedes research report 10's original Quiet-Workbench-first
recommendation per `UI-SPEC.md:786-793`. **This is a hypothesis for where to
spend prototype-building effort, not a pre-decided freeze.** The 17A plan set
must place an explicit `checkpoint:decision` between prototype completion and
the token freeze; no plan may treat this hypothesis as settled before Weibao
sees all three renders of the identical flow.

**Prototype implementation vehicle (Claude's Discretion, resolved here):**
static fixture pages under a clearly non-production path (e.g.
`prototypes/17a/<direction>/`), not served daemon routes, so a prototype
**cannot** be accidentally reached by a learner and never needs its own
route/CLI parity entry. Prototypes are explicitly not accepted as production
components without review — the freeze gate is what promotes the winning
direction's actual tokens/components into `presentation.py`/`theme.py`,
never the prototype files themselves.

**Reversibility requirement (binding, D-04):** each prototype direction must
be independently removable without touching the other two or the shipped
surfaces. Concretely: prototypes consume the same frozen non-color tokens
(`--space-*`, `--r-*`, voice tokens) so they render legibly even before a
final color/density choice, but store their direction-specific CSS in
separate, deletable files rather than branching inline conditionals into
`presentation.py`.

## Direction-Neutral Rendering Decisions (D-06)

The ~15 rendering decisions 16B and 16C explicitly deferred to 17A are
resolved here as **rules applied identically across all three prototype
directions**, so they cannot become an accidental fourth variable in the
direction comparison. None is left to executor judgment.

| # | Decision point (source) | Ruling | Reasoning |
|---|---|---|---|
| 1 | CourseShelf scroll-vs-clip (16B-UI-SPEC overflow row, CourseShelf) | **Scroll, never clip or paginate.** The shelf is a single vertically scrolling list at any card count; no "load more" button, no pagination control. | Matches the project's existing "long content" rule (wrap/scroll, never a hidden screenshot or silent clip); a course shelf is not expected to reach a size where pagination earns its complexity at one-learner scale. |
| 2 | ActivityView long job lists (16B-UI-SPEC overflow row, ActivityView) | **Scroll**, grouped "Needs your input" first, then in-progress, then completed/failed, each group internally reverse-chronological. No pagination. | Same reasoning as #1; Activity's own contract already forbids inventing a percent, so a length-based pagination control would be an invented affordance with no data backing it. |
| 3 | FirstLaunchWalkthrough narrow copy | **No copy shortening on narrow widths.** Walkthrough step copy wraps to multiple lines rather than truncating; a step callout's height is intrinsic to its content, never fixed. | The walkthrough is shown once and is optional (Start/Skip); it does not need the density discipline a persistent panel needs, so truncation would trade a one-time UX for a real accessibility cost (hidden onboarding text) with no upside. |
| 4 | SettingsPanel long root paths, no mid-path ellipsis | **Wrap at path separators, never truncate mid-segment, never hide the drive/root.** A long approved-root path wraps onto a second line inside its row; `overflow-wrap: anywhere` as the fallback if a single segment itself is pathologically long. | 16B's own permission-denied copy rule already forbids hiding a resolved path behind an ellipsis for a *different* reason (never showing a resolved absolute path at all, basename-only); for settings' own approved-roots list — which the learner explicitly configured and needs to verify — the opposite risk applies: hiding part of a path the learner is auditing is actively unsafe. Wrap, don't hide. |
| 5 | NoteCapturePanel scroll-vs-grow | **Grow up to 8 lines (`--text-body` line-height), then scroll internally.** The capture textarea auto-grows with content until it reaches roughly 8 visible lines, after which it becomes an internally scrolling fixed-height region; the surrounding page never grows unboundedly. | Matches common editor-field ergonomics (the field itself scrolls once it exceeds a comfortable glance-height) while keeping the anchored lesson content beneath it stable — an unboundedly growing capture panel would push the anchor out of view, working against the "focus returns to the anchored block after save" accessibility rule 16C already locks. |
| 6 | NotesPanelEvidence grouping | **Grouped by objective (per 16C's own listing structure), each group collapsed to its first 3 notes with an in-group "Show all {N} notes" disclosure control past that.** Groups themselves are never collapsed — the group heading and its first 3 rows are always visible. | Reuses the Progressive Disclosure Contract's "long list" pattern (below) rather than inventing a bespoke rule; keeping the group heading always visible preserves the objective-grouping structure 16C's contract requires while bounding first-paint length. |
| 7 | ProgressComprehensionDisplay long lists | **The seven claim-dimension rows are never collapsed or paginated** (GRAPH-03 requires every dimension visible, not hidden behind a disclosure); **per-objective fill-state lists** (many objectives) follow the same "first N visible, disclosure past that" pattern as #6, with N=10. | The seven dimension rows are a fixed, small, always-relevant set — collapsing them would contradict the "no aggregate hides the parts" principle the whole contract exists to protect. Per-objective lists are unbounded in the general case and follow the standard long-list pattern. |
| 8 | NoteOutputTrio node labels (concept map) | **Fixed-width truncation with an ellipsis at the visual node, full label always available via focus/hover with an accessible equivalent** (the textual adjacency fallback list, which never truncates). | The graphic concept-map node is explicitly a secondary projection (16C: "textual adjacency structure is the 16C contract; any richer graphic must keep it as the accessible equivalent") — truncating the *decorative* graphic label is acceptable exactly because the accessible textual form is never truncated. |
| 9 | Anchor-state chips (visual form) | **Small chip: token-colored left border or dot (never fill-only) + `--text-xs` Ledger-voice label, never an icon-only chip.** Chip background stays `--card`/`--chip`, never the full semantic-bg fill (that intensity is reserved for banners), keeping chips legible in a dense note list. | Matches the "restrained color" DeepSeek-inspired principle above — a list of many chips filled solid in five different hues would read as noisy; a border/dot accent plus text label carries the same information at lower visual weight, and text-first satisfies the no-icon-library rule. |
| 10 | Fill-state glyphs (D-14A-3 per-objective standing) | **Five discrete filled blocks** (`▪▪▪▫▫` rendered as five adjacent `--r-1` mini-rectangles, filled count = current standing), with the fixed legend text always adjacent, never a continuous bar. | Five blocks is the smallest count that reads as genuinely discrete (not readable as a smoothed bar) while giving enough resolution to show real movement; matches the "self-adjustable fill state... never a probability number" contract, and the discreteness itself is the anti-precision-theater signal GRAPH-03 requires. |

Two further deferred items resolved here for completeness, not explicitly
enumerated in D-06's list but implied by it:

| # | Decision point | Ruling | Reasoning |
|---|---|---|---|

## Progressive Disclosure & Default-Collapsed Contract

> Direct implementation of the user direction: "consider subtle stuff like
> collapsing all of the hints originally, and more." Every collapsible
> surface below states its **default state**, its **expand affordance**, its
> **keyboard/screen-reader equivalent**, and whether **state persists**. This
> section is binding on every 16B/16C component this phase styles; an
> executor does not choose collapse behavior ad hoc.

**Governing rule, restated first because it is the one non-negotiable:** UI
default-collapsed behavior is a **presentation layer on top of the runtime's
own disclosure gate**, never a substitute for it. A hidden hint tier's text
is absent from the DOM until the runtime actually unlocks it (RTS-09,
unchanged); a *shown* tier's card may still start visually collapsed by this
contract, but a *locked* tier is never in the DOM to collapse in the first
place. Collapsing something the runtime has not yet authorized would be a
CSS-only leak risk (inspectable, screen-reader-reachable) that this contract
explicitly forbids by construction: **collapse applies only to content the
runtime has already released to the public payload.**

### 1. Hint ladder (RTS-08, TEACH-02/03, extending the shipped six-tier ladder)

| Property | Contract |
|---|---|
| Default state | **Fully collapsed at zero shown tiers**, identical to today's shipped behavior — the ladder region exists (so its presence is discoverable) but shows only the "I'm stumped — show the next hint" control (LOCKED copy) and zero tier cards. This is not a new behavior; this phase locks it as the *styled* default rather than an incidental one. |
| Expand affordance | Each unlock event (a genuinely different retry, or the explicit stumped action) adds **exactly one** new tier card, appended below the previous ones, never replacing or collapsing an already-shown tier. A shown tier card is not itself collapsible — once shown, it stays visible for the rest of the attempt (RTS-08: "each opened tier adds a card and replaces none"). |
| Keyboard/screen-reader equivalent | The "show next hint" control is a normal button, reachable in tab order after the response controls; activating it moves focus to the newly appended card's heading so a screen-reader user lands on the new content, not back at the top of the ladder. No `aria-expanded` toggle exists on a *shown* card (it is not collapsible once shown) — `aria-expanded="false"` exists only on the "show next hint" control itself, describing whether more tiers remain available, not a content-hiding state. |
| Persistence | Per-attempt only, from the runtime's own held-cursor state — reused verbatim, not a new persistence layer. A page reload before the attempt resolves re-renders exactly the tiers already unlocked (already true; this phase adds no new storage). |

### 2. Rationale / explanation panels (study mode, `AttemptPanel` per-option rationale)

| Property | Contract |
|---|---|
| Default state | **Collapsed until the response is scored.** Before submission, no rationale text exists in the DOM (unchanged no-leak rule). After scoring, the rationale panel renders **collapsed by default** via a native `<details>` element — visible in the DOM (already scored, so no leak risk) but not visually expanded, so the learner's eye lands on the verdict first, the explanation second, by deliberate choice. |
| Expand affordance | Native `<details>`/`<summary>` — summary text is the specific per-option label already specified by the surface (e.g. "Why B is correct," never a bare "Details"), never a generic chevron with no label. |
| Keyboard/screen-reader equivalent | Native `<details>` is inherently keyboard-operable (Enter/Space on the summary) and screen-reader-announced (`role` and expanded state are native, no ARIA authored by hand). No `aria-expanded` scripting needed — this is the reason `<details>` is preferred over a custom disclosure widget here. |
| Persistence | Does not persist across page loads — a re-rendered attempt (e.g. via `report`/`study`) starts collapsed again each time; this is a reading-order nudge, not a saved preference, so persisting it would add complexity with no evidence-store benefit. |

### 3. Secondary metadata (objective tags, difficulty, provenance/citations)

| Property | Contract |
|---|---|
| Default state | **Collapsed behind a single `<details>` disclosure**, reusing the shipped `ContextLine` "Details" pattern (`UI-SPEC.md` §3: "Secondary metadata is in an accessible `<details>` disclosure. It is sticky but never obscures focused content.") — this phase extends that exact pattern to every new 16B/16C surface carrying similar metadata (source locators in `SourceCitation`, the objective/difficulty pairing on an item, provenance in `NoteOutputTrio`'s notebook mode). No new disclosure idiom is invented; one pattern, reused everywhere metadata is secondary. |
| Expand affordance | `<details>` with a summary naming what it contains, e.g. "Objective and source details," never bare "More." |
| Keyboard/screen-reader equivalent | Native `<details>`, as above — no custom ARIA. |
| Persistence | Does not persist; each page view starts with metadata collapsed. **Exception:** the never-hover-only rule remains binding — a hover-revealed definition (glossary term, RTS-05) always has this same disclosure or an equivalent click/keyboard path; hover is never the *only* way to reach it. |

### 4. Long option lists and tables (avoiding overwhelming first paint)

| Property | Contract |
|---|---|
| Default state | An item's response options (mc/multi/table/dnd/build) render **in full, never collapsed** — options are the primary task, not secondary metadata, and hiding an answer choice would be an accessibility and assessment-integrity defect, not a density win. What collapses instead is **everything around the options**: rationale (rule 2, post-score only), metadata (rule 3), and long *reference* tables inside lesson prose (rule 5). |
| Long reference tables in lesson prose | A table wider than `--measure-wide` (80ch) or taller than roughly 10 rows on first paint renders with its **first 5 rows visible plus a "Show all {N} rows" `<details>` control**, reusing the same disclosure idiom — never a silent horizontal scroll-only clip that hides row count, and never truncating a table's *columns* (the existing horizontal-scroll-wrapper rule for narrow widths is unchanged and orthogonal to this row-count rule). |
| Keyboard/screen-reader equivalent | Native `<details>` around the table body's overflow rows; the visible-first-5 rows and the headers are never removed, only the overflow rows are behind the toggle, so a screen reader reading top-to-bottom encounters a normal (if partial) table followed by an explicit "show more" control, not a truncated table with no indication more exists. |
| Persistence | Does not persist. |

### 5. Additional collapsible surfaces hunted per the user direction

| Surface | Default state | Expand affordance | Keyboard/SR equivalent | Persists? |
|---|---|---|---|---|
| `AgentAssist` panel (contextual agent support) | Collapsed by default, matching the shipped rule ("Collapsed by default unless requested," `UI-SPEC.md` §4) — this phase extends it to every 16B/16C surface that can carry agent support, never just the original tracer. | Explicit "Ask for a different explanation" control (LOCKED copy) or an equivalent named affordance; never auto-expands on page load or on a timer. | Standard disclosure button, `aria-expanded` scripted (this one genuinely needs a custom toggle since its content is dynamically fetched, unlike the static `<details>` cases above); status changes (`thinking`/`sourcing`/etc.) announce through the one `role=status` region. | Does not persist across navigations; each new activity's agent panel starts collapsed. |
| `EvidenceDrawer` (selection/trend/audit rationale) | Collapsed — shows the summary line only ("Why this item?" / recommendation reason) with the full evidence trail behind a disclosure. | "Review evidence" control (LOCKED copy, reused). | Native `<details>` where content is static per render; a custom toggle only if the drawer content requires a fetch, in which case it follows the `AgentAssist` pattern (scripted `aria-expanded`, loading state announced once). | Does not persist. |
| `NotesPanelEvidence` per-objective groups | See Direction-Neutral Decision #6 — first 3 notes visible, disclosure past that, group heading never collapsed. | "Show all {N} notes" control. | Native `<details>`. | Does not persist (each Evidence-panel visit re-collapses to first 3). |
| `ActivityView` completed/failed job history (as opposed to "needs your input," which is never collapsed) | The "needs your input" group is **never collapsed** (it is the actionable set); completed/failed history collapses to the most recent 5 with a "Show earlier activity" disclosure. | "Show earlier activity" control. | Native `<details>`. | Does not persist. |
| `LegacyUpgradeReview` "Proposed changes ({N})" diff list, when N is large | Individual diffs are **not** collapsed by default (each carries its own accept/reject and must be reviewable without an extra click, per the bounded-diff review discipline) — but the list itself paginates past 10 items with a "Show next 10" control rather than rendering an unbounded page, distinct from the scroll pattern used elsewhere because a reviewer working through diffs benefits from a bounded working set. | "Show next 10 proposed changes" control. | Standard button; the diff region itself is native content, no `<details>` needed since nothing is hidden within a shown diff. | Does not persist. |
| Loading states for any of the above (long multi-root reads, per 16B/16C's own "loading" backstop rows) | Not a collapse state — a genuinely slow read shows a stated loading line ("Loading notes…" in Ledger voice) in place of the disclosure control until data resolves; never a spinner with no text. | n/a | The loading line is announced once via `role=status`, replaced by the real content (collapsed per its own rule above) when ready. | n/a |

### 6. Empty states (cross-referencing, not restating, the Copywriting Contract)

Every collapsible surface above has a defined empty state already specified
by 16B or 16C's own Copywriting Contract (e.g. "No notes yet for this
course," "No courses yet"); this document's job is only to confirm the
**styling** rule: an empty state never renders a disclosure control with
nothing behind it — if a section would collapse to zero items, it renders
its empty-state copy directly, with no "Show 0 notes" toggle.

### 7. Focus order (binding restatement)

Every disclosure control in this section sits **after** its owning region's
primary content in DOM and tab order (reusing the shipped rule: "the
activity canvas is the focus landing point after navigation... contextual
support follows in DOM order and never takes focus after an ordinary
submit"). Expanding a `<details>` never moves focus away from the control
that triggered it, except the hint-ladder rule above (which deliberately
moves focus to the newly appended card, because that is genuinely new
content the learner asked for, not a re-disclosure of existing content).

### 8. Reduced-motion variant of every expand/collapse

**Fixed rule, non-configurable (already LOCKED at the project level, restated
here as binding on every disclosure this phase adds):** `<details>` open/close
uses the browser's native (instant) toggle — no authored animation exists to
suppress. Any *scripted* disclosure this phase adds (`AgentAssist`'s
dynamically-fetched panel, the "Show next 10" diff pagination) uses at most a
150ms functional transition (height/opacity), and `prefers-reduced-motion:
reduce` removes that transition entirely, rendering an instant show/hide —
identical outcome, no animation frame, matching the project's existing
150ms-max / reduced-motion rule verbatim. No new motion budget is introduced.

## Iconography (resolved, extends the "text label first" rule)

No icon library is adopted by this phase. Where a state benefits from a
compact visual marker (anchor-state chips, job outcomes, the fill-state
blocks), the marker is one of:

1. A **text label**, always present and always sufficient alone (the primary
   channel, per every 16B/16C color-token table's "required label" column).
2. A **CSS-only shape** (border-left accent, filled block, dot) using the
   semantic token's color — never an SVG sprite sheet, emoji, or third-party
   icon font. This keeps the freeze's registry-safety posture unchanged
   (still zero third-party assets beyond the two vendored OFL fonts and
   KaTeX).

If a later phase demonstrates a genuine need for a real icon set (e.g. for
the concept-map's graphic node types), that is a new, separately-vetted
supply-chain decision, out of 17A's scope per the "no new architecture"
boundary.

## Accessibility QA Mechanism (D-09)

A layout-capable verification mechanism is a prerequisite for the freeze
gate, because jsdom-style assertion alone cannot verify layout-dependent
gates (zoom/reflow, focus visibility under real rendering, responsive
snapshots at 1280/768/375). Ruling, carried forward from CONTEXT.md:

- A **dev-only driven-browser harness** is permitted (2026-08-09 constraint
  relaxation), pinned, checksummed, and license-reviewed per the supply-chain
  rule, never shipped in the runtime.
- Paired with a **scripted human QA pass** — AI never self-certifies
  accessibility (A11Y-01). Weibao is the acceptance authority, including the
  deliberately hover-only variant that must fail equivalence review.
- **Tool choice is Claude's Discretion per CONTEXT.md**, resolved here with a
  recommendation rather than a hard pick, since the actual selection belongs
  to the planning/execution phase where the supply-chain checkpoint runs:
  prefer a tool this repository can vendor or pin the same way KaTeX and the
  two fonts were vendored (an explicit version, a recorded checksum, a named
  license review) over an unpinned dependency resolved at install time.
