<objective>
Decide, once and in one place, what the evidence store considers a *distinct* response — and make
every undo a compensating event rather than a deletion.

Purpose: this is phase success criterion 3. D-17 fixes the idempotency key as session + item +
attempt number + canonical answer, built on `runtime.canonical_response()`, which already decides
what a response *is* across every surface. RESEARCH.md Common Pitfall 1 found the one place that
rule does not implement literally: `canonical_response()` returns `None` for constructed response
by design (`runtime.py:78-79`), so a literal reading either crashes on a `short` submission or
treats every `short` answer in an attempt as the same one. The documented extension — hash the
normalized text when the canonical form is `None` — lands here and is covered by the test.

D-10 is the other half: reversibility means compensating events. Undoing appends a retraction that
references the original; nothing is removed. That makes a raw line count of the log an overstatement
of history, so every view and every count the learner sees reads through the retraction filter.

Output: a lock held across the dedupe check and the write, an attempt-numbering rule that
distinguishes a retry from a second attempt, `itembank retract`, and retraction-aware views.
</objective>

    contains the `session_id`, so a duplicate can only ever come from the same sitting, and a
    sitting is at most a few hundred events — eight megabytes is three orders of magnitude of
    headroom. Document the residual honestly too: a duplicate older than the window would be
    recorded a second time, which is recoverable by retraction and cannot happen within one sitting.

    **Fix the attempt rule.** Replace `attempt_number(log, session_id, item_key)` with
    `attempt_number(log, session_id, item_key, canon)` implementing D-17's distinction in one
    sentence: an attempt is opened by a distinct canonical answer and stays open until a different
    canonical answer arrives. Concretely — find the most recent *live* response event for that
    session and item key; if there is none, return 1; if its `canonical` equals `canon`, return its
    `attempt_number` (a retry stays inside the attempt it is retrying, so it produces the same
    dedupe key and dedupes); otherwise return its `attempt_number` plus one (a different answer
    opens the next attempt, so it produces a different key and records). Write that sentence into
    the docstring — it is the rule the whole of PROTO-03 rests on, and it is not recoverable from
    reading the code.

    Note in the docstring that this is D-18's definition, landed one phase ahead of the Phase 6
    cursor-hold that will make attempt numbers routinely exceed 1, so that evidence recorded before
    and after that phase lives under one rule rather than in two inconsistent eras.

    **Make `append_event` idempotent.** It now: computes nothing itself (the event already carries
    its `dedupe_key`), serializes the line, and calls `append_line_checked`. When the key already
    exists it returns `{"accepted": False, "status": "already_recorded", "event_id": <the existing
    event's id>}` and writes nothing. When it does not, it writes and returns `{"accepted": True,
    "status": "recorded", "event_id": <the new id>}`. An event whose `dedupe_key` is `None` — a
    retraction — always writes. Update the docstring to say that `recorded` and `already_recorded`
    are different answers and the caller must surface which, because PROTO-03's requirement is not
    just "does not double-record" but "and the tool says which happened".

    **Confirm the short fallback.** `idempotency_canon` already falls back to

    `canonical_response` directly, and that the value it stores in the event's `canonical` field is
    the same value fed into `dedupe_key` — if those two diverge, the attempt rule above compares the
    wrong thing and every short retry looks like a new attempt.

    **Report it at the surface.** In `surfaces/session.py`'s `cmd_submit`, keep printing the

    for that item and answer — the response is recorded, just earlier — but still advance the cursor
    and write the session, because a retry after a crash is the session catching up rather than a

## Flagged Assumptions (probe-surfaced, unresolved)

- **PROTO-03 — `unclassified` edge, unresolved.** The probe could not classify a boundary for
  "submitting the same response twice does not record two attempts, and the tool says which
  happened," so no automatic acceptance criterion was derived. Two assumptions stand in its place
  and are recorded rather than hidden:
  1. **Short-answer normalization.** Dedupe for constructed response compares the
     whitespace-collapsed, lowercased text. No source artifact fixes this normalization; it is
     chosen here because it matches how a learner retries a typed answer (re-typing with different
     spacing or capitalization is the same answer) while keeping two genuinely different sentences
     apart. A stricter rule would fail to dedupe an obvious retry; a looser one would silently
     merge two real answers.
  2. **The tail window.** `DEDUPE_WINDOW_BYTES` bounds the dedupe scan. Because a dedupe key
     contains the `session_id`, a duplicate can only come from the same sitting, so the bound is
     safe in practice; a duplicate older than the window would be recorded again and is recoverable
     by retraction. Stated in the code and carried here rather than assumed away.
