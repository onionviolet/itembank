<objective>
Make the published contract enforceable and deliverable: enforceable by a CI step that validates
real runtime output against `schemas/*.json` on every push (PROTO-04), and deliverable by one
command whose output is everything an agent with no repository access needs (PROTO-05).

Purpose: D-15 named an open cost the planner had to solve explicitly — there is no JSON Schema
validator in the standard library, so either a minimal one is written or the CI check stays
shallow. **This plan writes the minimal one, and the decisive design choice is that it fails loud
on a keyword it does not implement.** A validator that silently ignores `patternProperties` would
report a green build while checking half the contract, which is worse than no check because it
looks like one. Plan 01-05 already fixed the schemas to a keyword subset precisely so this
validator can enforce all of it.

PROTO-05 is the requirement that decides whether the rest of the milestone's authoring and
tutoring loops can run cold. `model.SPEC` is the precedent: a self-contained contract printed
verbatim. `itembank schema --all` is the JSON equivalent, and it carries `SPEC` inside it so one
paste covers both the bank format and the runtime shapes.

Output: `schema_validate.py`, `surfaces/protocol_cli.py`, the `itembank schema` command, a new CI
step, and two new tests.
</objective>

  <action>
    Create `schema_validate.py` at the repository root. Standard library only: `json`, `os`, `sys`.
    Its module docstring states what it is and, more importantly, what it is not — a subset
    validator for the five schemas this repository publishes, not a general-purpose JSON Schema
    implementation, and that it refuses to run against a schema using a keyword it does not
    implement so that a green result always means the whole document was checked.

    Define `SUPPORTED` as a frozenset of the keywords it enforces: `type`, `properties`, `required`,
    `additionalProperties`, `enum`, `const`, `items`, `minItems`, `minLength`, `$defs`, `$ref`,
    `oneOf`. Define `ANNOTATIONS` as a frozenset of keywords it accepts and ignores: `$schema`,
    `$id`, `title`, `description`, `x-itembank-version`. Define `SchemaError` as an `Exception`
    subclass for a problem with the *schema*, distinct from a problem with the instance.

    Define `check_schema(schema, path="#")` walking the schema document recursively and raising
    `SchemaError("unsupported keyword %r at %s" % (kw, path))` for any key that is in neither set.
    Walk into `properties` and `$defs` values as schemas but treat their *keys* as property names
    rather than keywords; walk into `items` and each member of `oneOf` as schemas. Call it once at
    the top of `validate` so an unsupported keyword is reported before a single instance is
    examined.

    Define `validate(instance, schema, root=None, path="$")` returning a list of error strings, one
    per failure, each shaped `"%s: %s" % (path, message)` so a caller can print them the way
    `cmd_lint` prints lint entries. `root` carries the top-level document so `$ref` can resolve.
    Implement each keyword:
    - `$ref` — accept only the local `#/$defs/<name>` form; anything else is a `SchemaError`.
      Resolve against `root` and validate the instance against the referenced subschema.
    - `type` — a string or a list of strings; map JSON type names to Python types with `integer`
      matching `int` but not `bool` (a `bool` is an `int` in Python and would otherwise validate as
      an integer, which is exactly the kind of silent pass this validator exists to avoid), `number`
      matching `int` or `float` but not `bool`, `null` matching `None`, and `object`, `array`,
      `string`, `boolean` matching the obvious types.
    - `enum` — membership by `==`.
    - `const` — equality.
    - `required` — every named key present in the instance dict.
    - `properties` — validate each present key against its subschema, extending `path` with
      `"." + key`.
    - `additionalProperties` — when `false`, report every instance key not named in `properties`.
    - `items` — validate every element, extending `path` with `"[%d]" % i`.
    - `minItems`, `minLength` — length checks on arrays and strings respectively, both counting
      elements and code points rather than bytes.
    - `oneOf` — collect errors from every branch; pass when exactly one branch produces no errors,
      and on failure report how many matched along with the first branch's errors, so a
      near-miss is diagnosable rather than just "no branch matched".

    Define `main(argv)` giving it a CLI:
    - `python schema_validate.py <schema.json> <instance.json>` — validate one document; `-` for the
      instance reads stdin.
    - `--jsonl <path>` in place of the instance path — validate every non-blank line of a JSONL file
      independently, prefixing each error with the line number.
    - `--array <path> <key>` — validate every element of `instance[key]`, for the `errors` and
      `warnings` arrays `lint --json` emits.
    Print each error on its own line and a closing `"%d instances, %d errors"` summary in the house
    reporting style. Exit 0 when there are no errors and 1 otherwise; exit 2 with the message on a
    `SchemaError`, so "the schema is broken" is distinguishable from "the data is wrong" by exit
    code alone. Guard the CLI behind `if __name__ == "__main__": sys.exit(main(sys.argv[1:]))`.

    Export `SUPPORTED`, `SchemaError` and `validate` from `itembank.py`, adding a
    `from schema_validate import (...)` block after the existing ones with the same `# noqa: E402`
    marker, and the names into `__all__` in alphabetical position.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| schema document → validator | A hand-written schema may use a keyword the validator does not implement; treating that as "no constraint" would produce a false green |
| runtime payload → validator | Real command output is the untrusted side of the contract check |
| contract → external agent | `itembank schema --all` is consumed by a model with no other context; anything missing or wrong there produces confidently wrong behaviour with no error |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-14 | Spoofing | `schema_validate.validate` silently ignoring an unimplemented keyword | high | mitigate | `check_schema` runs before any instance is examined and raises `SchemaError` on a keyword outside `SUPPORTED` or `ANNOTATIONS`; the CLI exits 2 for that case so "the schema is broken" is distinguishable from "the data is wrong". Asserted by Task 1's verify block and by an `allOf` acceptance criterion. |
| T-1-15 | Tampering | A CI step whose failure is swallowed | high | mitigate | The step runs under `set -e` and every validator invocation is bare — no `\|\| true`, no `2>/dev/null` on a validator call. The single `\|\| true` sits on the `lint` command whose non-zero exit is expected, and its output is validated on the next line so an empty file cannot pass. |
| T-1-16 | Tampering | `bool` validating as `integer` | medium | mitigate | The `type` mapping excludes `bool` from both `integer` and `number`; asserted directly in Task 1's verify block. Python's `bool` being an `int` subclass is the standard way a hand-rolled validator passes data it should reject. |
| T-1-04 | Information Disclosure | Evidence written into the checkout during a CI run | high | mitigate | The CI step copies the fixture to `/tmp` first so `_evidence/` is created under `/tmp`, and the acceptance criteria require `git status --porcelain` to be clean afterwards. |
| T-1-SC | Tampering | npm/pip/cargo installs | low | accept | This phase installs nothing; `01-RESEARCH.md` § Package Legitimacy Audit records "Not applicable". |
