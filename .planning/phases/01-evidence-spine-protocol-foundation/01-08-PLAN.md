<objective>
Make the store answer the question it exists for. This is phase success criterion 4: a single query
answers "how am I doing on objective X over time" across every session and every subject, reading
from the unified store alone.

Purpose: D-08 says the log is the only authority and queries are served by a **disposable derived
index**, rebuilt whenever the log has grown past it and deletable at any time with no loss. That
sentence is the whole design: a `sqlite3` file is acceptable as that cache and never as the system
of record, which keeps PROJECT.md's "no database" rule intact in the sense that matters — nothing
authoritative is opaque.

Plan 01-02's `objective_history` was a linear scan of the log behind the right signature. This plan
replaces the scan with the projection behind that same signature, which is the tracer's real data
layer arriving. It also delivers EVID-08's visible half: a drill-mode correct and an exam-mode
correct are reported apart rather than averaged, because "I got it right" means something different
when the answer was revealed on request.

Output: `rebuild_index`, `ensure_index`, a staleness rule that survives truncation, a fallback that
keeps the tool working when the index cannot be built at all, and a query surface with exact,
prefix, subject, mode, session and date filters.
</objective>

    Define `rebuild_index(log, index)` doing a full rebuild into `index + ".tmp"` and then
    `os.replace(tmp, index)`:
    - `CREATE TABLE events (seq INTEGER PRIMARY KEY AUTOINCREMENT, event_id TEXT UNIQUE, ts TEXT,
      session_id TEXT, item_id TEXT, item_ref TEXT, objective TEXT, subject TEXT, mode TEXT,
      item_type TEXT, score TEXT, attempt_number INTEGER, confidence TEXT, response_time_ms
      INTEGER, review_state TEXT, retracted INTEGER DEFAULT 0)`. `seq` is what preserves log order
      for events sharing a `ts`; every query orders by `ts, seq`.
    - `CREATE INDEX idx_objective ON events(objective, ts)`, `CREATE INDEX idx_subject ON
      events(subject, ts)`, `CREATE INDEX idx_session ON events(session_id, ts)`.
    - `CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT)` holding `index_version`,
      `event_schema_version`, `log_bytes` (the byte offset of the log consumed so far) and
      `log_mtime_ns`.
    - Insert one row per response event in log order, storing `score` as the JSON encoding of the
      value so the three states `true`, `false` and `null` survive the round trip — a `short` item
      awaiting a marker is not a wrong answer, and collapsing them here would undo the distinction
      `runtime.score_response`'s docstring exists to protect.
    - After the insert pass, `UPDATE events SET retracted = 1 WHERE event_id IN (...)` for every id
      in `retracted_ids(log)`. Retracted rows are marked, never deleted, so the index mirrors the
      log's own semantics.
    - Reuse `iter_raw`'s skip-and-report handling by building on `events`, so a malformed line warns
      and is skipped rather than aborting a rebuild.

    Define `index_stale(log, index)` returning a two-tuple of `(stale, offset)`:
    - Stale with a full rebuild (`offset` 0) when the index file is missing, when it cannot be
      opened, when `index_version` or `event_schema_version` in `meta` differ from the current
      constants, or when the log's current size is **smaller** than the recorded `log_bytes` — a
      shrinking log means it was truncated or rewritten, and an incremental pass would silently
      index the wrong bytes.
    - Not stale when the size and mtime both match exactly.
    - Otherwise incremental, with `offset` set to the recorded `log_bytes`.

    Define `ensure_index(log, index)` applying that rule: full rebuild, or an incremental pass that
    seeks to `offset`, reads to the end, inserts the new response events, applies any `retracts`
    values found in the new tail as `UPDATE ... SET retracted = 1` (retraction is monotonic — an
    event is never un-retracted — so applying only the tail's retractions is correct), and updates
    `meta`. Take the same advisory lock around the index write that `append_line` takes around the
    log, so two concurrent queries cannot rebuild over each other.

    Wrap every index operation in a `try/except Exception` that, on any failure, prints
    `"warn  evidence index unavailable (%s); falling back to a full log scan"`, removes the index
    file if it exists, and returns a sentinel telling the caller to use the linear path. An index
    that cannot be built must never stop a learner from studying — that is the same
    degrade-never-block rule PROJECT.md applies to the model layer, applied here.

    Export `INDEX_VERSION`, `rebuild_index`, `ensure_index` and `index_stale` from `itembank.py`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| log → index | The projection is built from lines that may be torn or hand-edited |
| index file → query | The index is a mutable local file that may be stale, corrupt, or missing entirely |
| CLI filter arguments → SQL | `--objective`, `--subject`, `--mode`, `--session` and `--since` values reach a SQL query |
| query output → learner | What the tool chooses to display shapes what the learner optimises for |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-19 | Tampering | SQL built from CLI filter values | high | mitigate | ASVS V5.
