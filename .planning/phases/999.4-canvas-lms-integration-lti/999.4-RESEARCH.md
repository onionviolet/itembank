**Researched:** 2026-08-11
**Domain:** LTI 1.3 / LTI Advantage (OIDC third-party login, deep linking, Assignment
and Grade Services), Canvas LMS tool configuration, JWT/JWKS verification in Python
**Confidence:** MEDIUM-HIGH — the LTI 1.3 message flows, Canvas endpoints, and AGS
shape were web-verified this session against current (2026) sources; the exact
request/response bytes must be re-verified against the live Canvas instance and the

decisions (D-01..D-09), which are not re-litigated.

## Summary

Five findings:

1. **LTI 1.3 is the right protocol and the only one worth building.** LTI 1.1
   (OAuth 1 signature, XML config) is deprecated; Canvas 2026 default tool
   installs are LTI 1.3 [WEB-VERIFIED: Canvas LTI docs — "If the tool was
   installed after January 1, 2026, this configuration is already included in
   the default installation"; LTI 1.1 deprecation posts]. LTI 1.3 is plain
   OIDC + signed JWTs + HTTPS — no XML, no OAuth 1, no vendor SDK required. It
   is exactly the "authentication and identity protocol" the product constraint
   names, and the only auth surface the phase will ever need (D-02).
2. **A verified launch is a three-step browser dance plus JWT validation.** The
   platform initiates an OIDC third-party login (login initiation request), the
   tool bounces the browser to the platform's authorize endpoint with a
   nonce+state, and the platform POSTs back a signed `id_token` JWT which the
   tool must verify against the platform's **JWKS** (signature, `iss`, `aud`,
   `nonce`, `exp`, `deployment_id`, `message_type`). There is no shared
   password; the tool's own RSA keypair is registered with the platform as a
   public JWK or JWKS URL. The whole protocol surface is ~250-350 lines of
   stdlib Python plus a crypto dependency — not a framework.
3. **Grade passback is LTI Advantage's AGS, and its shape fits the product
   constraint exactly.** The launch JWT carries an `lti-ags` endpoint claim
   (lineitems URL + granted scopes) when the tool is installed with AGS
   enabled. The tool gets an OAuth2 client-credentials token (signed JWT-bearer
   assertion), creates or finds a **line item**, then POSTs a score payload
   (`userId` = launch `sub`, `scoreGiven`/`scoreMaximum`, `gradingProgress`).
   AGS is a one-way write to the LMS's own gradebook — itembank stores nothing
   and receives nothing. It is the *only* sanctioned way to get a score into
   Canvas. The `gradingProgress: PendingManual` value is the built-in refusal
   shape for "never auto-grade prose" (D-04, the `short` boundary).
4. **The crypto dependency is unavoidable and cheap.** RS256 verification and
   AGS client-credential signing need RSA. Python stdlib cannot generate or
   sign RSA. `cryptography` (Apache-2.0 OR BSD-3-Clause, dual) and `PyJWT`
   (MIT) are both permissive, wheel-bearing, and maintenance-active
   [WEB-VERIFIED: PyPI records]. Directive 4a permits them with pin + checksum +
   named license review; making them an optional import keeps the core loop
   install-free (D-08, R-03).
5. **Hosting is the real cost of this phase, and it is a config problem, not a
   code problem.** LTI mandates HTTPS and a publicly reachable launch URL.
   `server.py` binds loopback by default; the phase adds an opt-in LTI bind
   with stdlib-`ssl` TLS (user-supplied certs) or a documented reverse-proxy
   posture, plus a `public_base_url` setting so redirects and launch URLs are
   correct behind either (D-05, R-04). Nothing about the learner page, the
   scorer, or the evidence store changes.

## 1. The LTI 1.3 launch flow (OIDC third-party initiated login)

Verified against the 1EdTech spec summary and multiple implementation guides
(the `lti_1p3` Elixir docs and the Blackboard/Canvas developer docs agree on
the three steps) [WEB-VERIFIED: lti_1p3 overview; Blackboard LTI welcome].

1. **Login initiation (platform → tool, browser GET).** The learner clicks the
   tool link in Canvas; Canvas redirects the browser to the tool's **OIDC login
   initiation URL** with query params: `iss`, `login_hint` (the learner's
   opaque user id), `target_link_uri`, `client_id`, `deployment_id`, and
   `lti_message_hint` (optional).
2. **Authorization redirect (tool → platform, browser 302).** The tool
   validates `client_id` against its registration, mints a random `nonce` and
   `state`, stores them briefly, and redirects to the platform's
   **authorize endpoint** with `response_type=id_token`, `client_id`,
   `redirect_uri` (the tool's launch URL), `login_hint`, `scope=openid`,
   `state`, `nonce`, `prompt=none`, `response_mode=form_post`.
3. **Launch (platform → tool, browser form POST).** The platform POSTs a JWT
   `id_token` plus the echoed `state` to the launch URL. The tool verifies:
   the JWT signature against the platform's JWKS public key (RS256), `iss`
   matches the registered issuer, `aud` equals the tool's `client_id`, `nonce`
   matches the one it minted, `exp` has not passed, and the claims carry
   `message_type`, `deployment_id`, and `sub`. Only then does the launch
   surface open.

The `state`/`nonce` pair is the CSRF countermeasure; the tool stores it only
for the seconds of the dance (D-02's in-memory nonce store). The `id_token`
claims that matter to this phase: `sub` (learner identity), `roles`, `name`/
`email`, `deployment_id`, `message_type` (`LtiResourceLinkRequest` for the
learner launch, `LtiDeepLinkingRequest` for instructor selection), `custom`
(params the tool itself embedded at deep-link time), and the optional
`https://purl.imsglobal.org/spec/lti-ags/claim/endpoint` claim when AGS is
granted.

## 2. Registration and deployment — the one store (D-06)

- **Tool side** the phase ships: `issuer`, `client_id`, `auth_endpoint`
  (platform authorize URL), `jwks_url` (platform public keyset), `token_endpoint`
  (platform OAuth2 token URL, needed only for AGS), the tool's own RSA keypair
  (private JWK file; the public JWK is pasted into Canvas or served at the
  tool's JWKS URL), `deployment_id` (granted by the platform when the tool is
  installed), and `public_base_url`.
- **Platform side** (Canvas, manual, documented): Admin → Developer Keys →
  "+ LTI Key" → paste the tool's public JWK (or a JWKS URL) plus the OIDC
  initiation URL and target link URI; install by client id, which yields the
  `deployment_id`. [WEB-VERIFIED: Canvas developer key / LTI 1.3 install docs.]

Canvas's concrete endpoints [WEB-VERIFIED: Canvas LTI docs and API mirrors]:
issuer `https://canvas.instructure.com` (or `<canvas-host>`), authorize URL
`<host>/api/lti/authorize_redirect`, JWKS `<host>/api/lti/security/jwks`,
token endpoint `<host>/login/oauth2/token`.

## 3. Deep linking — instructor selection (D-07)

When the tool is installed with the **assignment selection** (or link
selection) placement, opening the tool from the assignment editor launches a
`LtiDeepLinkingRequest` message type. The `id_token` carries a
`deep_linking_settings` claim with `deep_link_return_url`, `accept_types`
(`ltiResourceLink`), `accept_multiple`, and `accept_line_items` (AGS). The tool
renders a small picker, and on selection POSTs an HTML auto-submitting form to
`deep_link_return_url` with a `LtiDeepLinkingResponse`: `content_items` = one
`{type: "ltiResourceLink", url: <tool resource-link launch URL>, title, custom:
{objective: <id>, mode: <mode>}}`. The learner later launches that assignment,
which arrives as a `LtiResourceLinkRequest` whose `custom` carries the chosen
objective [WEB-VERIFIED: Canvas deep linking docs; ed.link deep-linking guide].

Two facts shape the plan: (a) the deep-link **response is an unsigned form
POST**, not a signed JWT — the trust anchor is that the launch that carried
`deep_linking_settings` was itself verified; (b) `custom` values ride inside
the *signed* launch JWT on the learner side, so the objective id is platform-
attested by the time it matters. The tool must still resolve it through the
stem allowlist (D-07), because a platform is a trust boundary, not a license to
stop validating.

## 4. AGS — grade passback (D-04)

Verified flow [WEB-VERIFIED: 1EdTech AGS spec summary, Canvas grading docs,
2026 dev.to AGS walkthrough]:

1. **Endpoint claim:** a launch with AGS enabled carries
   `https://purl.imsglobal.org/spec/lti-ags/claim/endpoint` → `{lineitems:
   <url>, lineitem: <url>, scope: [<granted scopes>]}`. The scopes are
   `https://purl.imsglobal.org/spec/lti-ags/scope/lineitem` (create/read line
   items), `.../scope/score` (publish scores), `.../scope/result` (read
   results). No scope, no passback: a launch without the `score` scope is
   D-04's opt-in gate.
2. **Token:** OAuth2 client-credentials grant with a JWT-bearer client
   assertion signed by the tool's private key (RS256, `iss`/`sub` =
   `client_id`, `aud` = the platform token endpoint), exchanged at
   `token_endpoint` for a bearer token scoped to the granted AGS scopes.
3. **Line item:** if the assignment's line item does not exist, `POST
   {lineitems}` with content type `application/vnd.ims.lis.v2.lineitem+json`
   `{label, scoreMaximum, resourceId, tag}`. Canvas typically pre-creates the
   line item for external-tool assignments; the plan's task probes first
   (GET) and creates only when absent, keyed by `resourceId` = the launch's
   resource link id — that is the idempotence anchor.
4. **Score:** `POST {lineitem}/scores` with content type
   `application/vnd.ims.lis.v1.score+json` `{userId: <sub>, scoreGiven,
   scoreMaximum, activityProgress: "Completed", gradingProgress:
   "FullyGraded", timestamp}`. Canvas accepts it and the grade appears in the
   assignment. The score is a **copy** — the runtime report already recorded
   it locally (D-04/R-02).
5. **The never-auto-grade shape:** for a session with `short` items still
   `pending`, the plan's passback publishes the graded fraction with
   `gradingProgress: "PendingManual"` — AGS's own vocabulary for "a human
   must confirm," which is exactly the runtime's rule that prose is never
   auto-graded. If the deployment's line item rejects that, the fallback is
   no numeric publish + the named refusal in the report (R-02's fallback).

## 5. The crypto dependency decision (D-08, R-03)

- Python stdlib: `hashlib`/`hmac`/`base64` cover HMAC and JOSE framing;
  **RSA is absent**. `pow(a, e, n)` can *verify* RS256 signatures in pure
  Python (a few ms), but generating an RSA keypair and signing (needed for the
  tool's JWKS private key, the AGS client assertion, and any tool-signed JWT)
  cannot be done honestly in pure stdlib.
- `cryptography`: dual Apache-2.0 OR BSD-3-Clause, wheels for all supported
  platforms, the de-facto standard. `PyJWT`: MIT, small, standard JWT
  encode/decode over `cryptography`. Both permissive; no copyleft exposure.
  [WEB-VERIFIED: PyPI package metadata.]
- Posture: **optional imports**. `surfaces/lti.py` imports them inside a
  guard; with them absent, `itembank lti` and the LTI handler refuse by name
  with the install command, and every non-LTI command is byte-identical
  (degrade, never block — `CLAUDE.md:57`). The pin + checksum + named license
  review record lands in the same commit as the code (Directive 4a, the KaTeX
  precedent).
- JOSE framing (base64url, JWS header/payload/signature assembly, JWKS
  parsing) is hand-rolled stdlib over `cryptography`'s primitives — matching
  the repo's stdlib preference; `PyJWT` remains an accepted fallback if the
  hand-rolled path proves awkward, decided at implementation time.

## 6. Hosting posture (D-05, R-04)

LTI mandates HTTPS and a reachable launch URL. Options weighed:

| Option | Cost | Verdict |
|---|---|---|
| Built-in TLS via stdlib `ssl`, user certs | ~40 lines; user supplies cert/key paths in settings; `ssl.SSLContext.load_cert_chain` | **Default.** No dependency, explicit, matches "explicitly hosted" |
| Documented reverse proxy (nginx/Caddy) | docs + a `public_base_url` setting; tool stays loopback | **Shipped as the second documented posture** (Directive §3: build both, learner picks) |
| Built-in ACME/Let's Encrypt | needs an HTTP-01 handler + external dependency | Rejected — the tool never holds a domain or a CA account; that is the reverse proxy's job |
| Tunnels (ngrok/cloudflared) | third-party, auth surface, unstable URLs | Out of scope; not a hosting posture, a workaround |

The loopback default (`server.py` binding `127.0.0.1`) is **unchanged**; the
LTI bind is a separate, opt-in, config-gated server instance in the same
handler family. `public_base_url` is required when LTI is enabled and drives
every URL the platform must call (OIDC initiation, launch, JWKS, deep-link
return) — the single knob that makes both postures work.

## 7. Privacy and the "no hosted gradebook" constraint (D-04, D-09, R-02)

What leaves the machine, stated plainly:

1. **Item text** travels to the learner's browser *through the LMS* (the
   browser is Canvas's guest; the page is served by the tool over the LTI
   iframe). This is the same accepted-risk class as hosted models seeing item
   text (`CLAUDE.md`), with the LMS as the transit host. It is disclosed in the
   UI copy and `itembank lti` help (D-09).
2. **The final score** is copied to the LMS gradebook via AGS at session
   completion only. itembank stores no gradebook, hosts nothing, and receives
   no learner data back from the LMS. The evidence store remains the local
   record (D-04/R-02).
3. **Nothing else.** No telemetry, no hosted storage, no item text stored
   remotely by this tool, no learner evidence beyond the score.

The `sub` claim is used only as the AGS `userId` (the LMS's own key) — itembank
never stores or routes on LMS user identity (D-02, R-05).

## 8. What this phase refuses

- A second parser, scorer, or evidence store (§4.2) — D-01, enforced by a
  grep-style test.
- Accounts, passwords, multi-tenancy, an itembank login page — D-02.
- Any reveal before a recorded response — D-03 (the MCP note's §4 rules).
- Auto-grading `short`/pending prose into a score — D-04 (AGS
  `PendingManual`).
- Listening/public binds by default, telemetry, hosted storage — D-05/D-09.
- LTI 1.1, NRPS, QTI, per-user evidence — DEFERRED in CONTEXT.

## Validation Architecture

- **Fake-platform harness** (`tests/lti_roundtrip.py`): a stdlib test platform
  that (a) mints its own RSA keypair, (b) drives the OIDC login + launch dance
  against the tool over loopback, (c) signs valid and **invalid** launches
  (wrong key, wrong `aud`, expired, wrong nonce, unknown `client_id`,
  unregistered `issuer`) and asserts named refusals, (d) plays AGS: line-item
  probe/create and score receive, asserting the published payload. Fully
  offline; this is what makes the phase executable under R-01's default.
- **Wrap-seam fixture:** asserts the LTI handler calls the daemon's
  `handle_api_*` functions (or the same `session.do_start` seam) and that no
  scoring call exists outside `runtime.py` (D-01).
- **public_item fixture:** asserts the learner page payload equals
  `runtime.public_item()` and contains no key/why/distractor fields (D-03).
- **Manual-only:** the real-Canvas install → launch → deep-link → passback
  checklist (R-01's fallback), recorded in VALIDATION as manual-only.
