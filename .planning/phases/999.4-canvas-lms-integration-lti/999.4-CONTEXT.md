# Phase 999.4: Canvas LMS Integration via LTI — Context

**Gathered:** 2026-08-11
**Status:** Ready for planning (BACKLOG phase, user-requested plan)
**Mode:** autonomous (Directive §2), headless run with `--max-steps 0`

<domain>
## Phase Boundary

This phase makes the item player reachable inside Canvas LMS through an **explicitly
hosted, authenticated LTI 1.3 surface** — an adapter to the same local runtime and
scorer, never a second authority. It covers the four decision clusters the 06.1
research left open (`06.1-RESEARCH.md` resolved question 3): a consuming Canvas
instance, an externally reachable hosting posture, OIDC/LTI identity mapping, and
the privacy/evidence-retention, deep-link-ownership, and grade-passback policies.

It does **not** build: accounts, passwords, multi-tenancy, an itembank-hosted
gradebook, cloud sync, telemetry, a second parser, a second scorer, a second
evidence store, or any scoring path outside `runtime.py`. The learner's browser
page is the existing quiz surface; the instructor's selection page is a new thin
picker; LTI itself is the only authentication surface.

**What "BACKLOG" means here.** `ROADMAP.md` recorded a 2026-08-10 verdict of
"KEEP, and the next review should seriously consider Out of Scope instead" —
"no consumer exists. Promote when a real Canvas course requires it." Planning
this phase was requested by the user on 2026-08-11, which is the promotion
event. The verdict's three recorded objections are each answered below by a
decision (D-02 answers "no accounts, no auth", D-04/D-09 answer "no hosted
gradebook / no telemetry", and R-01 records the consumer question as an open
ruling) rather than ignored.
</domain>

<open_rulings>
## Open Rulings — for the user to ratify at plan review

These are the consequential forks that the 2026-08-10 review explicitly left
open and that planning cannot honestly close by itself. Each has a **recommended
default** the plans are built against; the default is reversible (these are
documents, not shipped code). Ratify or overturn at review.

### R-01 — The consumer reality check (the phase's gate)

The ROADMAP verdict says the honest blocker is "no consumer exists." Planning was
ordered anyway. The ruling needed: **is there a real Canvas instance/course to
verify against?**
- **Default:** no assumption of a live Canvas. Plans build a **fake-platform
  harness** (a stdlib test platform that speaks OIDC login + launch + AGS against
  the tool, offline) as the automated gate, and ship a **manual Canvas
  verification checklist** (real install + launch + passback) as a manual-only
  validation item. The phase is not blocked on Canvas availability.
- **If a Canvas sandbox exists** (free Canvas account, or a course on any
  instance): the manual checklist becomes a live verification in VALIDATION.

### R-02 — Grade passback vs "no hosted gradebook"

`.claude/CLAUDE.md` Data residency: *"No cloud sync, no hosted gradebook, no
telemetry."* AGS passback writes a score to Canvas's gradebook.
- **Default (D-04):** itembank **stores no gradebook and keeps none remotely**.
  Passback is a one-way, outbound **copy** of the runtime's own computed score to
  the LMS's gradebook — the LMS is the instructor's record, not itembank's. It
  happens only at session completion, only when the launch granted the AGS
  scopes, and never includes evidence, prose, or item text. The evidence store
  stays the local record of what was answered.
- **If the user rejects any numeric write to an LMS:** passback degrades to
  completion-status only (`gradingProgress: PendingManual`), which is
  LTI-05's fallback path.

### R-03 — The crypto dependency

RS256 verification and AGS client-credential signing require RSA. Python stdlib
has no RSA (verification can be faked with `pow()` big-int math; **key
generation and signing cannot be done well in pure stdlib**). Directive 4a:
dependencies are permitted with pin + checksum + named license review.
- **Default (D-08):** vendor **`cryptography`** (Apache-2.0 OR BSD-3-Clause,
  dual-licensed, permissive) and **`PyJWT`** (MIT) — both pinned, checksummed,
  license-reviewed — as an **optional import**: the LTI surface refuses by name
  when they are absent, and the core loop (quiz/serve/day/session/evidence)
  stays install-free and works unchanged. JOSE framing (base64url, JWS) is
  hand-rolled over `cryptography` per the repo's stdlib preference; PyJWT is
  used for claim encode/decode only if the hand-rolled path proves awkward.
- **If the user prefers zero dependencies:** verify-only `pow()`-based RS256 is
  possible but asymmetric (no keygen/sign), so AGS client credentials and
  deep-link tool signing cannot work; the phase would shrink to launch-only.
  Not recommended.

### R-04 — Hosting posture

LTI requires a publicly reachable HTTPS endpoint; `server.py` binds loopback by
default and the product is local-first.
- **Default (D-05):** the LTI mount **binds only when explicitly enabled** in
  settings. TLS termination is **stdlib `ssl`** with user-supplied cert/key
  paths (no dependency), *and* a documented reverse-proxy posture (nginx/Caddy
  in front, tool stays loopback) for users who already run one. The loopback
  default is unchanged; nothing listens publicly unless the user turns it on.
- **If the user wants zero hosting work:** the phase still ships the
  fake-platform harness and the surface can be exercised over loopback; the
  public-reachability half becomes documentation only.

### R-05 — Learner identity scope

The product is "One. No accounts, no auth, no multi-tenancy." An LMS launch
carries a Canvas `sub` per user.
- **Default (D-02):** one learner profile on this machine. Every verified
  launch maps to that profile; evidence and attempt files are keyed by
  (deployment, resource link, session), never by LMS user identity. Multi-user
  / multi-tenant routing is out of scope, and the phase says so rather than
  half-building it.
- **If the user wants per-LMS-user evidence separation:** a later phase; the
  identity seam (claims → profile) is built now so the mapping is a one-line
  change.

<decisions>
## Locked Implementation Decisions

These are the gray areas planning resolved. The plans bind to them.

### The surface, not a second authority

- **D-01 (Directive §4.2, the phase's spine):** the LTI surface is an
  **adapter over the existing JSON commands** — it calls the same handler
  functions the daemon dispatches to (`handle_api_start` / `handle_api_next` /
  `handle_api_submit` / `handle_api_hint` / `handle_api_report` in
  `surfaces/daemon.py:1361-1659`) in-process, and the embedded page posts
  through the same `runtime.score_response` path the quiz surface uses. It
  never parses a bank a second way, never decides correctness, and writes no
  second evidence store. **Adding the LTI mount changes none of `API_ROUTES`,
  `SURFACE_PARITY`, or the `check_api_route_scope` test** — LTI endpoints are a
  separate handler family on `server.py`, not new `/api/*` routes. A test
  greps for a second scoring call and fails the build if one appears.
- **D-02 (no new auth surface):** LTI 1.3's own OIDC launch is the *only*
  authentication. Identity = the verified launch claims (`sub`, `roles`,
  `deployment_id`). itembank adds no accounts, no passwords, no login page, no
  API keys for learners. The only local state LTI needs is a short-lived
  in-memory nonce/state store for the OIDC dance (CSRF), which is a protocol
  countermeasure, not an account system.

### What the learner and the instructor may see

- **D-03 (learner surface = public_item only):** the embedded player renders
  exactly what every other surface renders — `runtime.public_item()`. No key,
  why-best, distractor analysis, or higher-tier content is reachable before a
  recorded response for that item exists in the evidence store; tier gating is
  server-side and identical to the HTTP path (Directive §4.1, the MCP note's
  three rules apply unchanged). A browser that inspects the LTI page finds the
  same public payload as the quiz surface.
- **D-04 (grade passback boundary):** AGS score publish is **outbound-only,
  at session completion, opt-in per launch** (the AGS scope must be present).
  `scoreGiven`/`scoreMaximum` come from the runtime's report; `short` items
  that are `pending` are **never auto-graded** — the reported fraction is
  correct-graded / graded-items, and the refusal/copy says so. Passback
  failure is a named refusal that never blocks the learner and never rewrites
  local evidence (see R-02).

### Hosting and configuration

- **D-05 (explicit hosting, loopback default unchanged):** the LTI mount binds
  only when `settings.lti.enabled` is true. TLS is stdlib `ssl` with
  user-supplied cert/key paths; a documented reverse-proxy posture is the
  alternative; `lti.public_base_url` is a required setting when enabled (it
  drives the launch/redirect URLs). Nothing listens publicly by default (R-04).
- **D-06 (one registration store):** a `platforms` registry in settings — one
  entry per LMS platform: `issuer`, `client_id`, `auth_endpoint`, `jwks_url`,
  `token_endpoint`, `deployment_id` allowlist, plus the tool's own RSA keypair
  (private JWK path) and `public_base_url`. A launch from an unregistered
  issuer or unknown `client_id`/`deployment_id` is refused by name — the same
  named-refusal discipline as engine names (09.1 D-04) and bank stems.
- **D-07 (deep-link ownership):** the instructor's selection picks an
  **objective from the local bank registry** (the same objective ids
  `handle_api_start` resolves); the returned `ltiResourceLink` content item
  carries the objective id and mode as custom params. The learner launch opens
  exactly that objective; a resource-link launch without a resolvable
  objective is refused by name. The objective id is resolved through the
  existing stem allowlist — never treated as a path (the daemon's T-2-02
  discipline).

### Honesty

- **D-08 (supply chain, Directive 4a):** `cryptography` and `PyJWT` are
  optional, pinned, checksummed, license-reviewed dependencies (R-03). The
  pin record and license review land with the code in the same commit.
- **D-09 (network/privacy honesty):** the surface and its docs state exactly
  what leaves the machine: item text travels to the learner's browser through
  the LMS (the browser is hosted by the LMS), and the final score is copied to
  the LMS gradebook. No telemetry, no hosted storage by this tool, no
  learner-item text stored remotely by this tool. The statement lives in the
  LTI UI copy and in `itembank lti` help text, not only in planning documents
  (the 09.1 D-16 precedent).

### Claude's discretion

LTI endpoint paths, the JWKS cache TTL, the nonce store shape, the exact
settings schema field names, module factoring, and the JOSE framing details are
open. Not open: wrap-the-JSON-commands (D-01), no new auth surface (D-02),
public_item-only (D-03), the passback boundary (D-04), the loopback default
(D-05), the one registration store (D-06), named refusals everywhere (D-06/D-07),
the supply-chain pin (D-08), and the privacy statement (D-09).
</decisions>

<code_context>
## Existing Code Insights

### Reusable assets
- The daemon's `handle_api_*` functions are the exact wrap seam D-01 requires;
  calling them in-process is "wrapping the JSON commands" with no second
  dispatch.
- The quiz surface (`surfaces/quiz.py`) already renders a served, loopback-only
  page that posts through the runtime scorer — the embedded LTI player is that
  page behind a verified launch, with the frame-ancestors policy added.
- `server.py` `bind()` already takes a `host`; `ssl` is stdlib, so D-05's TLS
  needs no dependency.
- The model-backend registry idiom (Phase 8) and the 09.1 engine registry are
  the shape D-06's platform registry copies — no second idiom.

### Established patterns
- Named refusal over silent degradation, everywhere.
- One interface per swappable decision; schema defaults as the one source of
  truth.
- Optional-dependency refusal by name (the LTI surface without `cryptography`
  must say so), matching how `day` omits Anki counts when Anki is closed.

### Integration points
- Objective ids come from Phase 3.2's `[OBJ:]` registry / `handle_api_start`'s
  stem allowlist — the deep-link selection resolves through the same seam
  (D-07).
- The runtime report (`handle_api_report`) is the source of the passback score
  (D-04).
</code_context>

## Specific Ideas

- Weibao's framing: a course a learner actually sits in Canvas should be able
  to carry itembank drills without itembank becoming a hosted product — the
  LMS is the hosting, the local machine stays the authority, and LTI is the
  only bridge. The fake-platform harness makes the whole spine testable with
  zero Canvas access, which is what keeps this plan honest under R-01.
</specifics>
