# Plan 999.4-01 Summary — the LTI 1.3 protocol spine (tracer)

## What landed

The whole LTI 1.3 protocol spine with zero UI and zero Canvas access: the
platforms registration store, the optional crypto dependency with a named
refusal, the OIDC login initiation + authorize redirect, JWT verification
against a fake platform's JWKS, and the in-process wrap that calls the
daemon's JSON-command handlers. A fake Canvas can now complete the OIDC dance
and start a real itembank session over the wrapped commands.

## Task map

| Task | Outcome |
|---|---|
| 01-1 Registry + crypto guard + settings block | `lti` settings block in the schema and itembank.json (enabled=false default, platforms registry, all x-itembank-phase 999.4); `load_registration()` resolves one platform per issuer with named refusals for unknown issuer/client_id/duplicate and missing public_base_url when enabled (D-05/D-06); `crypto_available()` guards the pinned optional imports; `itembank lti status`/`doctor`/`serve` registered |
| 01-2 JWT verification vs JWKS | `verify_id_token()` verifies JOSE framing -> RS256 signature against the platform JWKS (bounded TTL cache) -> iss -> aud -> nonce (one-time spend) -> exp -> deployment_id, each failure named; the nonce store is in-memory, short-TTL, capped, one-time (D-02, T-994-02/06) |
| 01-3 OIDC login + launch + wrap seam | `OIDCLoginHandler`/`LTIHandler` on server.py's Handler base (a sibling family — API_ROUTES/ROUTE_CLI/check_api_route_scope byte-unchanged); the launch handler resolves the registration from the server-issued state and calls the daemon's `handle_api_start` in-process through the shim wrap; the opt-in bind (`itembank lti serve`) gates on lti.enabled with stdlib-ssl TLS or plain-HTTP proxy posture (D-05) |
