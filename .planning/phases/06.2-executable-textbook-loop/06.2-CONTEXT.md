# Phase 6.2: Executable Textbook Loop - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning
**Mode:** autonomous (Directive §2)

<domain>
## Phase Boundary

This phase makes a lesson gate its own continuation on an inline check: the next passage does not render until the check is cleared, clearing it is an ordinary `runtime.score_response()` verdict, and the idea returns days later through the **normal** retention queue. It is built entirely from the lesson reader (Phase 3/3.1), the hint ladder (Phase 6), and the evidence log (Phase 1).

It adds **no seventh item type**, **no second scorer**, and **no lesson-local schedule**. It does not add the `[!CHECK:]` parse path (Phase 3.1 owns it), the scheduler (Phase 10 owns it), or any authoring of gated lessons (Phase 3.2/11).
</domain>

<decisions>
## Implementation Decisions

### Open ruling

- **D-01 (ruling 9 — DEFAULT ADOPTED, shared with Phase 3.1):** `[!CHECK: <id>]` may reference an item in **its own bank only**. A cross-bank reference is a lint error naming the rule. This phase and Phase 3.1 must not diverge on this; if one widens later, both widen. — **Reversibility:** reversible — widening is additive (a reference the linter rejects starts being accepted).

### The gate

- **D-02 (Directive §3 applied — build all three):** `[GATE: required|recommended|off]`, defaulting to **`recommended`**. The reason is stronger than the mastery-learning literature: a hard gate is **theater on a plaintext file the learner owns**. It is a claim the product cannot keep, and a claim that cannot be kept is worse than an absent feature. The loop's value is the return, not the wall.
- **D-03:** `required` still ships, and it is not a lie about enforcement — it is a stronger default posture with a more deliberate skip affordance. It is not marketed or documented as making skipping impossible.
- **D-04:** A recorded skip preserves the loop's value **better** than a hard gate does: skipped-and-still-unclear is a prioritizable signal, while a hard gate learns nothing.
- **D-05:** The gate is a **presentation policy over existing item types**. A gated lesson and an ungated one differ by a declared block, not by a code path — one render path with a policy, not two renderers.
- **D-06:** Gate state is **derived from the evidence log**, never stored as per-lesson progress. A second store of "which gates are cleared" would be a second evidence store (Directive §4.2) and would go stale against retraction.

### Evidence

- **D-07:** `gate_skip` is a **new event type** appended to `KNOWN_EVENT_TYPES` (`evidence.py:43`), verified additive against `evidence.py`. It is **explicitly not a `response` carrying a null score** — conflating them would make a skip indistinguishable from an unmarked attempt in every downstream count. — **Reversibility:** one-way — the log is append-only; a shipped event shape can only be superseded, never rewritten. Fix the field set before the first write.
- **D-08:** Clearing an inline check writes **ordinary response evidence**. A lesson-embedded attempt and a quiz attempt on the same objective are indistinguishable to Phase 10's scheduler except by the `selection_mode`/context field naming where it happened.
- **D-09:** A skipped gate is visible to Phase 10 as a prioritization signal. This phase writes the event and defines its meaning; it does not implement the scheduler's response to it.

### Measure

- **D-10:** This phase's usage measure is the **gate outcome split** — cleared vs skipped, over gates encountered. **Stated denominator. No target shown to the learner. No streak.** A streak here would convert a diagnostic signal into a thing worth gaming.

### Learner-facing behavior

- **D-11:** A learner can **always** read ahead by an explicit, recorded choice. The gate is a default, not a lock, and skipping is evidence too.
- **D-12 (accessibility, `UI-SPEC.md` §8):** The skip affordance is a real focusable control with a visible label, announced through the single `role=status` region — never a hover-only or keyboard-inaccessible escape hatch. The nine gates in `UI-SPEC.md` §8 are completion requirements here, not preferences (Directive §4.5).
- **D-13:** The gate never hides content from a screen reader that a sighted learner can reach, and never reveals through a hidden label what the visual path withholds (`UI-SPEC.md` §8 item 4).
- **D-14 (compatibility floor):** A bank whose lessons declare no gates renders **exactly** as it does after Phase 3.1, proven by fixture. Directive §4.4.

### Claude's discretion

Transition/reveal presentation, the wording of the skip control, how the derived gate state is cached within one render, and module factoring are open. Not open: no seventh item type, no second scorer, no lesson-local schedule, no stored gate progress, `gate_skip` as its own event type, and the §8 gates.
</decisions>

<code_context>
## Existing Code Insights

### Reusable assets
- The lesson reader's block rendering — the gate is a policy over it, not a fork of it.
- `runtime.score_response()` — one verdict path, already covering every item type this phase gates on.
- The append-only evidence writer and its schema version — one additive event type.
- Phase 6's hint ladder — a gated check uses the same entitlement rules as any other item; this phase grants no extra hint budget.

### Established patterns
- Public/private payload separation (`public_item()` / `explain_payload()`) — an ungated passage below a gate must not be present in the public payload, or the gate is decorative.
- One store, queried, not a second store, maintained (D-06).

### Integration points
- Phase 10's scheduler consumes both the ordinary response evidence (D-08) and the `gate_skip` signal (D-09).
- Phase 3.1's `[!CHECK: <id>]` anchor is the only entry point; this phase adds no parse path.
</code_context>

<specifics>
## Specific Ideas

- The framing that decided D-02: a lesson "that will not let you skim it" is the goal, but the mechanism is the **return**, not the wall. `required` exists because some learners want the stricter default; `off` exists because some lessons are reference reading.
</specifics>
