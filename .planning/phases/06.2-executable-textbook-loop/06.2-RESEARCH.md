## The `[GATE:]`/`[!CHECK:]` interface — what 3.1 owns, what 6.2 must add itself

**`[!CHECK: <id>]` is entirely Phase 3.1's to build** (ROADMAP 3.1 criterion 3e: *"`[!CHECK: <id>]` is the single new parse path"*; 06.2-CONTEXT: *"It does not add the `[!CHECK:]` parse path (Phase 3.1 owns it)"*). As of this session `model.py` has no such grammar — `grep` for `CHECK|GATE` in `model.py` returns nothing `[VERIFIED: model.py, read in full this session — no match for either token]`. This phase's plan must therefore **read Phase 3.1's actual shipped parse output** at 6.2-plan/execute time rather than trust any prose description here, including this document's — 3.1 executes first in roadmap order (`3.1 → 3.2 → 4 → 5 → 6 → 6.1 → 6.2`), so by the time 6.2 is planned the real shape will exist in source. The one fact this phase can safely assume without re-verifying, because both CONTEXT files state it identically: the anchor "carries no key and no scoring path" and resolves to an item's identity in the **same bank**.

**`[GATE: required|recommended|off]` is *not* claimed by Phase 3.1's "single new parse path" criterion — it is 6.2's own grammar addition.** ROADMAP 3.1 criterion 3e names `[!CHECK: <id>]` as *the* (singular) new parse path 3.1 owns; ROADMAP 6.2 criterion 7 introduces `[GATE:]` as this phase's own criterion, and nothing in either CONTEXT.md assigns its parsing to 3.1. `[ASSUMED]`: this phase must add `[GATE:]` to `model.py` itself, following the exact existing single-line-directive pattern already used for `[LESSON-SRC:]` — a `grab(r"(?m)^\[GATE:\s*(.*?)\s*\]", ...)` call, additive, matching the precedent at `model.py:213` `[VERIFIED: model.py:213, read this session]` `src = grab(r"(?m)^\[LESSON-SRC:\s*(.*?)\s*\]", head)`. This is additive grammar under Directive §4.4 (a bank not using `[GATE:]` parses unchanged), not a second parser.

**Where `[GATE:]` is declared, and its precedence — recommended default, `[ASSUMED]`, no source settles this today:**

1. **Scope: lesson-level, not per-`[!CHECK:]`.** 06.2-UI-SPEC's settings table lists `[GATE:]` as "authored per lesson" (§10), and the copywriting table (§15) derives the band header text ("Check · required to continue" / "Check · recommended") from one lookup, not a per-anchor attribute. No per-anchor `[GATE:]` syntax (e.g. `[!CHECK: <id> gate=required]`) appears anywhere in either UI-SPEC or either CONTEXT. Recommend one `[GATE:]` directive in the lesson's preamble (same location class as `[LESSON-SRC:]`), applying uniformly to every `[!CHECK:]` in that lesson. This is simplest, matches "one render path with a policy" (D-05), and does not need a second grammar addition inside the anchor syntax 3.1 already owns.
2. **Precedence, derived from `06.2-UI-SPEC.md §10.1` (LOCKED there): learner `gate_policy: as-authored|off` setting → lesson's declared `[GATE:]` value → hardcoded default `recommended` if the lesson declares none.** `gate_policy: off` may only *weaken* a declared gate (render it as `off`), never strengthen one — a `recommended` lesson can never become `required` by a learner setting (§10.1, LOCKED, rejected explicitly).
3. **What `required` actually means, resolved concretely (06.2-UI-SPEC §5.2, §6.3, §5.7, all LOCKED):** `required` selects the **G1 truncate-and-reveal** render — prose past an uncleared check is not emitted in the HTTP response at all (not hidden, not `aria-hidden`, not `display:none` — genuinely absent from the bytes the server sends). The skip control is present from the first render (`gate_skip: always`, default) or after one attempt (`gate_skip: after-attempt`) — either way it is **always eventually reachable**, satisfying D-11's "always." Skipping fires exactly one `gate_skip` event, reveals the next section, and **the band stays open and answerable afterward** — `required` never becomes a wall the learner cannot pass, it becomes a wall that logs the fact it was passed around. In diagnostic and exam feedback modes, `required` **degrades to `recommended`** automatically (06 §6.5's no-feedback-until-sitting-ends rule would otherwise make a `required` gate un-clearable for the whole sitting — a dead gate, which 06.2-UI-SPEC calls "C9's dead disabled button at document scale" and forbids).

## `gate_skip` as a new event type

**What exactly must change, verified against real source this session:**

1. `evidence.py:43` — `KNOWN_EVENT_TYPES = ("response", "retraction", "mark", "day_tick")` `[VERIFIED: evidence.py:43]` becomes `("response", "retraction", "mark", "day_tick", "gate_skip")`. This is the entire mechanism that makes an unknown event type degrade rather than crash: `events()` (`evidence.py:418-436`, `[VERIFIED]`) already checks `et not in KNOWN_EVENT_TYPES` and **skips-and-warns** rather than raising, for *any* string not in the tuple — this is exactly the D-09 guarantee Phase 1 built for exactly this situation (a log written by a newer build read by an older one). Adding `"gate_skip"` to the tuple is the one-line change that makes a newer log's `gate_skip` lines start being recognized instead of skipped; nothing else in `events()` needs to change.
2. A new builder function, `gate_skip_event(...)`, following the `day_tick_event()`/`mark_event()` pattern exactly (`[VERIFIED: evidence.py:1350-1370 for day_tick_event, :1035-1080 for mark_event]`): both existing non-response builders construct their own envelope (`schema_version`, `event_id`, `event_type`, `ts`) directly rather than reusing `response_event()`, both compute their own `dedupe_key` over a small, deliberately narrow tuple of fields (not the full response `dedupe_key(session_id, item_key, attempt_num, canon)` shape), and both raise `ValueError` on a malformed required argument rather than accepting silently.
3. Proposed minimal field set for `gate_skip_event()`, satisfying 06.2-UI-SPEC §16 Open Question 1's stated minimum (*"at minimum: bank, lesson_slug, check_item_id, session_id, gate_mode, served_at — enough for §11's denominator to be derivable without a second store"*, `[CITED: 06.2-UI-SPEC.md:986]`) plus the envelope every event carries:

```python
def gate_skip_event(session_id, bank, lesson_slug, check_item_id, check_item_ref,
                     objective, gate_mode):
    """One learner-recorded choice to read past an uncleared gate without
    clearing it. NOT a response event: score stays absent from this shape
    entirely (there is no score key at all, not even null), so a `gate_skip`
    can never be confused with a not-yet-marked constructed response in any
    downstream count (ROADMAP criterion 8).
    """
    if gate_mode not in ("required", "recommended"):
        raise ValueError("gate_skip_event: gate_mode must be 'required' or "
                          "'recommended' (got %r) -- 'off' never offers a skip"
                          % (gate_mode,))
    raw = "%s|%s" % (session_id, check_item_id)
    return {
        "schema_version": EVENT_SCHEMA_VERSION,
        "event_id": new_event_id(),
        "event_type": "gate_skip",
        "ts": utc_now(),
        "session_id": session_id,
        "bank": bank,
        "lesson_slug": lesson_slug,
        "check_item_id": check_item_id,
        "check_item_ref": check_item_ref,
        "objective": objective,
        "gate_mode": gate_mode,
        "dedupe_key": hashlib.sha256(raw.encode("utf-8")).hexdigest(),
    }
```

`[ASSUMED — proposed shape, not yet locked by any CONTEXT.md or UI-SPEC.md]`. Key design choices, stated so the planner can accept or overrule them explicitly rather than inherit them silently:

- **`dedupe_key` over `(session_id, check_item_id)` alone, mirroring `day_tick_event`'s `(date, lane)`-only key** `[VERIFIED: evidence.py:1361-1364 states this exact reasoning for day_tick_event]`. A learner can click the skip control more than once on the same still-open band (06.2-UI-SPEC §6.3: "the skipped band stays answerable" — nothing removes the control), and a second click on the same check within the same session should report `already_recorded`, not append a second identical fact. `attempt_num`/`canon` do not apply — a skip has no "answer" to canonicalize.
- **No `score` key, not even `None`.** This is the concrete, testable form of ROADMAP criterion 8's *"explicitly not a `response` carrying a null score"* — a reader that naively checked `ev.get("score") is None` to mean "pending" would misclassify a `gate_skip` as a pending constructed response if the key existed at all; omitting the key entirely (rather than setting it to `None`) makes that bug structurally impossible rather than merely discouraged.
- **`check_item_id`/`check_item_ref` mirrors the `item_id`/`item_ref` duality every response event already carries** (`evidence_key()`, `[VERIFIED: evidence.py:317-325]`), so a skip on an item that has not yet had `id-assign` run against it still records a stable positional reference, exactly like a response would.

## Criterion 9 — the gate outcome split is derived, not counted

**Confirmed derivable from the evidence log alone, no new stored counter, matching D-06.** The "cleared" half of the ratio is a query over `response` events (`objective`/`bank`/`context="lesson_gate"` filtered, `score is True or score is False` — dichotomous by construction, same as every other scored item type); the "skipped" half is a query over `gate_skip` events. Both are already-shipped or newly-proposed-and-additive read paths, not a mutable counter anywhere.

**One open resolution this research surfaces that neither CONTEXT.md nor 06.2-UI-SPEC.md settles: what happens when the *same* check is both skipped and later cleared in one session** (06.2-UI-SPEC §6.3's "stays answerable" ruling makes this a real, expected case — the whole point of D-04 is that a skip is not final). If the outcome-split table (06.2-UI-SPEC §11) counts every event independently, one check could contribute one "skipped" row and one "cleared" row for what is really one encounter, inflating the denominator and double-counting. **Recommended default, `[ASSUMED]`:** compute the outcome **per distinct `(session_id, check_item_id)` pair, not per event** — a pair with any live `response` event (cleared, regardless of whether a `gate_skip` also exists for the same pair) counts as **cleared**; a pair with a live `gate_skip` event and **no** subsequent live `response` event counts as **skipped**. This gives the "skipped-and-still-unclear" signal D-04 explicitly names as the valuable case, while a skip-then-clear sequence correctly resolves to the more informative final state. This is a genuine design decision the planner should record explicitly (not silently inherit) — it is exactly the kind of thing Directive §2 says to decide and continue on rather than block for, since it is fully reversible (a read-side aggregation rule, not a stored fact).

**"Gates encountered" (the denominator) is every distinct `(session_id, check_item_id)` pair with *either* a live `response` event carrying `context="lesson_gate"` *or* a live `gate_skip` event for that pair** — this is what "the runtime served the band" collapses to when derived purely from the evidence log rather than from a render-time counter, and it is fully consistent with 06.2-UI-SPEC §11's *"gates encountered means distinct required gate bands the runtime served — a server-side fact, not an inference"*: an encounter that produced neither event (the learner merely saw the band and navigated away) is, honestly, not observable from the evidence log at all, and is correctly excluded from the denominator rather than guessed at (C8's "never fake a... result" bars inventing a count for something the runtime cannot observe).

## Common Pitfalls

### Pitfall 1: Reusing `source_ref` or `mode` instead of minting a new field
**What goes wrong:** a plan reaches for an existing-looking field (`source_ref`, since it is already `object|null`; or `mode`, since it already varies by context) to carry "served from a lesson," rather than adding a new one.
**Why it happens:** adding a new required field to a published, `additionalProperties: false` schema touches every existing call site, which reads as more invasive than repurposing a field that is already `null` most of the time.
**How to avoid:** read §2 of this document — `source_ref` is explicitly scoped to migration provenance with a closed two-value `kind` enum, and `mode` is explicitly the feedback-policy axis Phase 6's own CONTEXT forbids conflating with anything else. Mint `context` (or an equivalent explicitly-decided new name) instead.
**Warning signs:** a schema change that adds a new *enum value* to an existing field rather than a new *field* — that is almost always the reuse-instead-of-mint mistake in this codebase's established style (see how `mode`'s enum already carries the unrelated `"legacy"` value for a different reserved purpose, `[VERIFIED: schemas/response.schema.json:59-62]`, which is itself the cautionary precedent, not a pattern to repeat).

### Pitfall 2: Double-counting a skip-then-clear sequence in the outcome split
**What goes wrong:** the outcome-split query counts events rather than distinct `(session, check)` pairs, so a check skipped and later cleared contributes to both buckets, inflating the denominator past the number of gates actually encountered.
**Why it happens:** the natural first query ("count `gate_skip` events" / "count cleared-check `response` events") is a straightforward `SELECT COUNT`, and the pair-level aggregation is one join away from that natural query — easy to skip under time pressure.
**How to avoid:** see §8's resolution — aggregate by `(session_id, check_item_id)` and resolve each pair to exactly one of {cleared, skipped} before counting.
**Warning signs:** a fixture test with one session that skips a check and then clears it should assert the ratio table shows exactly one encounter, not two — write that test explicitly, it is the cheapest way to catch this class of bug.

### Pitfall 3: Building the `[GATE:]` grammar as a second parser instead of extending the existing directive-grab pattern
**What goes wrong:** a plan invents a new parsing subsystem for lesson-scoped metadata (a "lesson frontmatter" concept, a YAML-like block, etc.) rather than reusing the one-line-bracket-directive convention every other lesson-preamble field already uses.
**Why it happens:** `[GATE:]` conceptually feels like "lesson configuration," which invites a heavier mechanism than the codebase's existing style.
**How to avoid:** follow `model.py:213`'s exact `grab(r"(?m)^\[LESSON-SRC:\s*(.*?)\s*\]", head)` pattern, character for character in spirit — one more `grab()` call for `[GATE:]`, nothing structurally new. This is what keeps the change additive under Directive §4.2/§4.4 rather than becoming "a second document model" (the line Directive §4a draws between permitted grammar growth and a forbidden second parser).
**Warning signs:** any plan task that mentions a new module for lesson metadata, or a schema file for lesson-level directives, is over-building relative to the one-`grab()`-call precedent.
