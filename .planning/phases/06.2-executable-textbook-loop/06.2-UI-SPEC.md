# Phase 6.2 — UI Design Contract: the Executable Textbook Loop

> **6.2 reuses Phase 3.1's reading layout. It adds exactly three things and redesigns nothing.**
>
> That sentence is research §3's own instruction for the top of this document
> (*"That sentence should appear at the top of 6.2's UI-SPEC"*), and 3.1 §18.2 already names the
> three: a gate band, the recorded-skip control, and a truncation boundary. Everything else —
> measure, heading ramp, `[!KEY]`, `[!EXAMPLE]`, glosses, the glossary appendix, the style footer,
> the voice table, the print contract — is 3.1's, unchanged.
>
> **A second reader is the Directive §4.2-class error this entire phase exists to avoid.**
> Directive §4.2, quoted: *"Exactly **one parser, one scorer, one evidence store**."* Research §1
> states the analogy that makes it a UI rule rather than a code rule: *"If 6.2 ships a second
> reading layout the project has two readers, which is the same class of error as two parsers."*
> **If this phase's plan touches the reading CSS beyond adding the gate band, it has failed**
> (3.1 §18.1, verbatim).

## How to read this document

Consequences, stated once so no plan re-derives an invented rule:

1. **This phase needs no JavaScript at all** — every element below is a server-rendered form POST

   script loads is cheaper to test and cheaper to keep accessible), and **never** as the reason
   another option lost. A client-side smoothing of the reveal is a legal later enhancement; §5.2's
   server-side truncation is not optional, and the reason is C6, not JavaScript.
2. **Print is a first-class output and never a veto.** §8 is a real deliverable, not a footnote.
3. **The one place a real prohibition bites** is C6 answer leakage, and §5.2 states it in the exact
   terms a fixture can test.

## 4. Typography and voice

Five sizes exist project-wide and **this phase adds none** (3.1 §4; 03.1-CONTEXT D-02: *"do not
re-litigate and do not introduce a sixth type size"*). Two weights: `--weight-normal` 400 and `--weight-emphasis` 600, per the UI-SPEC §7 weight ruling of 2026-08-10 (which superseded the prior 400/700 row on measured evidence; 3.1's type table was amended to match, and this phase inherits it).

| Role | Token | Voice | Use in this phase | Status |
|---|---|---|---|---|
| Band header | `text-xs` @600, small-caps treatment | **Ledger** | `Check · required to continue` | NEW string, INHERITED treatment (3.1's `.blabel` shape) |
| Check item stem, options | `text-body` 16 / 1.5 | **Paper** | the gated item itself | **LOCKED — see the ruling below** |
| Lesson prose above and below the band | `text-lesson` 18 / 1.65 | Paper | unchanged | INHERITED |
| Truncation boundary line | `text-xs` | **Ledger** | `3 more sections below this check.` | NEW string |
| Skip control label | `text-body` | **Chrome** | `Read ahead without answering` | NEW string |
| Status announcement clause | `text-xs` | **Ledger** | `The next section is below.` | NEW string |

**The item-size ruling — LOCKED.** A check inside a lesson renders at **`text-body` 16/1.5 in Paper
voice**, exactly as the same item renders when served by the quiz surface — *not* at `text-lesson`
18/1.65. Two reasons, both real:

1. UI-SPEC §7 scopes `text-lesson` to *"Sustained authored lesson prose only (Paper voice)."* An item
   stem is Paper voice (§7.1 lists *"item stems"* under `--font-paper`) but it is not sustained lesson
   prose, and voice is a family assignment, not a size assignment.
2. Rendering the check at lesson size would make it read as a continuation of the paragraph above it,
   which is precisely the confusion the band's border exists to prevent. A gated check and a quiz
   check must be **the same object typographically**, or the learner has been handed two kinds of
   question.

This ruling also serves §5.1: 3.1 reserved *"the height of one item stem plus its response controls
plus `space-4`"*, and that reserve was measured at the item's own size. Changing the size here would
invalidate 3.1's reserve.

### 4.1 Voice assignment for every string this phase renders — LOCKED

C12: *"Voice is assigned by **who authored the string**, never by visual preference."*

| String | Voice | Reason |
|---|---|---|
| The check item's stem, options, and rationale | **Paper** | a human authored it |
| Band header, truncation boundary line, skip-recorded status, mode-degrade line, unresolvable-check line, the report denominator | **Ledger** | the runtime asserts each one; each is a claim about a gate, a file, or a count the learner can inspect |
| `Read ahead without answering` | **Chrome** | the tool speaking as a tool, exactly like 3.1's `Full entry`, `Add to review`, `Back to the question` |
| Verdict copy after a check is answered | **Ledger** | Phase 6 owns the string and the voice; this phase reproduces neither |
| Anything a model generated | **Chrome, inside a labelled container — never Ledger, never Paper** | **B7, LOCKED.** Research §0.1 B7: *"a generated hint … render[s] in **Chrome voice inside a labelled container**, never in the Ledger voice reserved for things the runtime guarantees, and never in a voice invented for them. A model that gets its own face is a model that looks like an authority."* This phase renders no model output itself; if Phase 8's generated help appears alongside an open gate it appears in the hint ladder's generated slot under Phase 6's contract, never inside the gate band and never in the reading column. |

### 5.1 ACTIVATED — the reserved slot becomes a live form, with zero reflow above it

3.1 §9.4 built the screen form of `[!CHECK: <id>]` as **D2, a reserved empty slot**, and named the
reason (C15): D2 *"pre-reserves the vertical space so that turning on 6.2's gate does not reflow the
page, which matters because reflow-on-state-change is exactly the kind of thing that makes a gate
feel like a trick."* This phase honours that by **filling the slot, not replacing it**.

**LOCKED — the same element in every state.** The inert slot, the open band, the cleared band and the
skipped band are one `<section class="gate">` with identical box metrics:

| Property | Value | Identical to |
|---|---|---|
| Measure | full `--measure-prose` 66ch — the band never escapes to `--measure-wide` | 3.1 §7.1: headings, `[!KEY]` and `[!CHECK:]` anchors *"stay at full 66ch measure"* |
| Background | `--card` | 3.1's `[!KEY]` card |
| Border | `1px solid var(--line)` | 3.1's callout container |
| Radius | `--r-3` | 3.1's `[!KEY]` card |
| Padding | `space-3` | 3.1's callout inner padding |
| Block margin | `space-4` above and below | 3.1's callout block margin |
| `min-height` | the 3.1 reserve: one item stem + its response controls + `space-4`, computed server-side at `text-body` | 3.1 §9.4 |

**LOCKED — the zero-reflow invariant, stated so a fixture can test it.** *Nothing above a gate band's
top edge changes position between the inert render, the open render, the cleared render and the
skipped render.* Every state change is contained inside the band's own box or below it.

The honest caveat, stated rather than hidden: **content below the band does move**, because content
below is exactly what the gate governs. That motion is the loop, not a trick. What C15 forbids is the
page rearranging itself *around* a state change, and the invariant above is the testable form of
that.

**LOCKED — no colour change on state change.** A cleared band keeps `--card`. A skipped band keeps
`--card`. Recolouring on clear is celebration-adjacent (C7); recolouring on skip would style the skip
as a transgression (C16). State is carried by the band's Ledger header and by Phase 6's verdict
rendering inside it, never by the container's fill.

`keyboard/SR:` the band is a `<section>` led by a real heading-level-free Ledger label plus the item's
own controls; 3.1 required the inert slot to be **non-focusable**, and the live band's focusable
elements are exactly the item's response controls, the check button, and the skip button — in that
DOM order, which is C10's keyboard path *"response/manipulation → submit/hint"*.
`print:` §8 — the band prints as 3.1's **D1 labelled rule**, never as an empty box, because *"a
printed lesson has no session, so an empty slot on paper is a lie"* (3.1 §9.4).
`degraded:` with no runtime the slot renders 3.1's inert D2 copy verbatim, which already states its
own condition; C8 is satisfied by construction and no new string is needed.

### 5.2 NEW — the gate band, and the DOM ruling that makes it honest

**6.2 does not paginate. It gates in place, and the page scrolls.** Research §3.2, quoted:
*"[Brilliant] paginates because every screen *is* an interaction. Ours is prose with checks in it, so
it scrolls. **Do not import pagination.**"* And research §1.1 rules that 3.1 *"must not paginate
lessons"* — this phase does not reverse that; it adds a check into the scroll, which is Execute
Program's actual mechanic (*"Interleave short prose with a check instead of paginating"*).

`[GATE:]` already selects the rendering, so Directive §3 lands for free (3.1 §18.2):

| `[GATE:]` | Rendering | Research option |
|---|---|---|
| `required` | **G1 truncate-and-reveal.** The server renders the lesson up to the anchor, the band, then the truncation boundary. Clearing or skipping re-renders with the next segment appended. | §3.4 G1 |
| `recommended` | **G2 inline-and-continue.** The whole lesson renders; the band sits in the flow; the sections below it are present and readable. Clearing marks the band as cleared. | §3.4 G2 |
| `off` | 3.1's reader, unchanged. The anchor renders as the inert D2 slot. | 3.1 §9.4 |

**Default `recommended`** (CONTEXT D-02), and the reason is C19 — *"a hard gate is theater on a
plaintext file the learner owns"* — not the mastery-learning literature.

#### The DOM ruling — LOCKED, and this is the B4 question the objective demands be settled

**Under `[GATE: required]`, prose past an uncleared check is NOT in the DOM.** Not hidden, not
collapsed, not `aria-hidden`, not `display:none`, not in a `<details>`, not in any JSON payload, not
in any accessible name, not in CSS-off text. The server does not emit it.

**What is withheld, exhaustively.** Every one of these belongs to a section below an uncleared
`required` gate and none of them is emitted: section headings, paragraphs, list items, tables, code
blocks, figures, `[!KEY]` cards and their ids, `[!EXAMPLE]` blocks, further `[!CHECK:]` anchors and
their ids, backlink lists, and the `reader_nav` TOC entries and glossary entries covered by §5.5 and
§5.6.

**Why, quoted.** C6: *"fixture asserts no key, unshown tier, accepted visual target, expected code
output, or diagnostic/exam verdict is present in HTML, JSON, ARIA, CSS-off text, or accessible names
before legal disclosure."* Research §3.4 G1's own defence: *"the truncation is honest — the remaining
content is **not in the DOM**, so the claim 'the next idea has not arrived yet' is true rather than a
CSS trick."*

**REJECTED — G3, collapse-and-expand (`<details>`-hidden below-gate content).** Research §3.4:
*"REJECTED (B4 answer leakage — not a JavaScript objection): the content is in the DOM. For a lesson
that is merely untidy; for a gated check whose *own* later sections may contain the discriminating
fact, it is a leak."* Recorded here as well as in 3.1 §18.2 *"because it is the cheapest-looking
option and it is wrong."* **CSS-hiding downstream prose does not satisfy C6 and no plan may
substitute it for server-side truncation.** This rejection is unchanged by research §0.1's JavaScript
correction; it never rested on a JS taboo.

#### What the learner sees above and below the gate, under `required`

```
   [ every already-revealed section, unchanged — heading ramp, prose, [!KEY], [!EXAMPLE] ]
   [ every already-cleared or already-skipped gate band, still in place, still a record  ]

 ┌───────────────────────────────────────────────────────┐   66ch, --card, 1px --line, --r-3
 │ CHECK · REQUIRED TO CONTINUE                          │   Ledger, text-xs, small caps
 │                                                       │
 │ A patient has a gag reflex. Which adjunct …           │   Paper, text-body  (public_item())
 │  ( ) A  …    ( ) B  …    ( ) C  …                      │
 │                                                       │
 │ [ Check answer ]   [ Read ahead without answering ]    │   Chrome; check is first in DOM order
 └───────────────────────────────────────────────────────┘
   ─────────────────────────────────────────────────────     1px --line, full measure
   3 more sections below this check.                         Ledger, text-xs

   Glossary                                                  3.1 §9.1, filtered per §5.6
```

**Above the band: nothing changes, ever.** Prior sections and prior bands are re-emitted byte-for-byte
across every state transition. That is the testable half of §5.1's invariant.

**Below the band: the truncation boundary (§5.3), then the glossary appendix.** The appendix follows
the boundary and that is not a contradiction — the boundary's copy names **sections**, and the
appendix is document-scope reference apparatus carrying its own `Glossary` heading, separated by
`space-7` exactly as 3.1 §9.1 requires.

#### Under `recommended`, the below-gate prose IS in the DOM — and why that is not a C6 breach

C6 forbids undisclosed content *"before legal disclosure."* Under `recommended` the whole lesson **is
the disclosure**: the mode declares that reading continues, the sections below are legally available,
and nothing about them is withheld. The protections that matter are unchanged in both modes and are
the runtime's, not the layout's:

- The item's **key, rationale, distractor analysis and unshown hint tiers are never in the page**
  before the verdict — `public_item()` / `explain_payload()`, 3.1 §9.5 and 06 §5.2, unchanged.
- `glossable()` still suppresses a term whose definition would leak the key (§5.6).
- The **objective line** is `explain_payload()` only, never `public_item()` (3.1 §9.5).

**The residual hazard, named rather than papered over.** An author can write `[GATE: recommended]` and
then state the check's answer in the very next paragraph. That is an **authoring** defect, not a
rendering one, and this phase does **not** add a lint check for it. The honest reason: deciding
whether a paragraph gives away an answer requires inference the runtime does not do, and a heuristic
that guessed would be a second, weaker judge of correctness sitting beside `runtime.score_response()`
— which is the shape C2 exists to prevent. **OPEN**, owed to Phase 3.2/11 authoring guidance; default
if unruled: document the caution in the format spec and add no gate.

`keyboard/SR:` the band's contents are in reading order; the check is an ordinary item with ordinary
controls; a screen reader receives exactly what a sighted learner receives (CONTEXT D-13). Under
`required`, an SR user reaching the boundary hears the boundary line — it is real text, not an
`aria-label`.
`print:` §8. `degraded:` §12.

### 5.3 NEW — the truncation boundary

A single full-measure `1px --line` rule, `space-5` below the band, carrying one Ledger-voice line and
nothing else.

| Case | Copy |
|---|---|
| more than one section remains | `{n} more sections below this check.` |
| exactly one section remains | `1 more section below this check.` |

Two rows, not one with a plural helper, so a plural bug cannot ship.

**Is this progress framing?** No, and the distinction is worth stating because a checker could flag
it. C7 bans *"points, badges, levels, streak-recovery prompts, countdown pressure, or celebratory
motion."* A count of unrendered sections is none of those: it is static, it names what is withheld
rather than what has been achieved, and it exists to satisfy C8's *"say exactly what is
unavailable."* It never counts *cleared* checks, never renders as a fill or a track, and never
appears beside a target.

**REJECTED — naming the next section's heading in the boundary** (`Next: Sizing an OPA`). Ground: a
heading below an uncleared check is exactly the text most likely to name the discriminating fact, so
emitting it contradicts §5.5's TOC-filtering ruling and re-opens C6 through a side door. This is not
a Directive §3 case — the two options are not both defensible, so no setting is registered. Recorded
so it is not re-proposed as an orientation improvement.

`keyboard/SR:` real text in reading order after the band; no ARIA, no live region, no hidden count.
`print:` **absent.** A printed lesson is complete and ungated (§8), so a boundary line on paper would
describe a truncation that did not happen — a lie in exactly the shape 3.1 rejected for the empty
slot.
`degraded:` server-rendered text; unaffected by script, network or model state.

### 5.4 The clear is a runtime verdict, and a model has no part in it — LOCKED

C1: *"The **runtime**, not a model, decides what reaches the learner."* Clearing a gate is an ordinary
`runtime.score_response()` verdict (ROADMAP criterion 1; CONTEXT D-08). Three consequences the UI
must make true:

1. **No model output ever appears inside the gate band.** Generated help, where Phase 8 provides it,
   appears in the hint ladder's generated slot in the support column under Phase 6's contract.
2. **The band renders `public_item()` and nothing else** before a verdict.
3. **The gate adds no scoring surface of its own** (ROADMAP criterion 10; CONTEXT D-05: *"a presentation
   policy over existing item types"*). The band is a renderer of an existing item, not a seventh item
   type.

### 5.5 ACTIVATED — the support column during a gated read, and the TOC filtering ruling

**The ordering question is settled and is not re-opened here.** C14, 3.1 §7.3, LOCKED: in a *"Sitting
or gated reading (Phase 6, 6.2 — an item is active)"*, the hint ladder occupies the support column
first and **the TOC sits below it, collapsed by default, summary `Sections in this lesson`**; narrow
viewports put it inside the existing "Help and evidence" disclosure, still after the ladder. 3.1's
stated reason: *"the ladder is tied to the active attempt; the TOC is document-scope."* This document
activates that row and changes nothing in it.

Two faithful applications, both **LOCKED**, that a plan would otherwise have to invent:

1. **The ordering rule is evaluated per render, not per surface.** The ladder outranks the TOC
   whenever the ladder is present. When no band is open — all gates cleared, `[GATE: off]`, or a mode
   in which the ladder does not run (06 §6.5) — the ladder block is *absent with a stated reason*
   (C9) and the TOC occupies the top of the support column.
2. **A gated reading is a sitting for its whole duration.** The DOM order does not flip section by
   section: the TOC never precedes content in DOM order during a gated read, even between gates.
   Reason: 3.1 §7.3 allows the standalone reader's TOC to precede content because *"a table of
   contents is navigation to the activity"*; in a gated read the activity is the check, so C13's
   *"support … begins below activity in DOM order"* applies unrelaxed. A DOM order that changed
   mid-lesson would also be its own screen-reader hazard.

**NEW ruling — the TOC is filtered under `required`. LOCKED.** With `reader_nav: column` and an
uncleared `required` gate, the `<nav>` lists **only revealed sections**, plus one Ledger line:
`More sections appear as you clear each check.`

Reason: heading text is content, and a heading below an uncleared check is content C6 forbids
emitting — *"Why an OPA is contraindicated with an intact gag reflex"* is the discriminating fact
written as a heading. A TOC that listed it would defeat the truncation completely while looking like
navigation. This is the same ruling as §5.3's rejected `Next:` line, applied to the other surface
that could leak the same string.

`keyboard/SR:` a labelled `<nav>` of real anchors, all of which resolve to elements present in the
document — filtering also removes the dead-anchor hazard structurally. The count line is real text.
`print:` the `<nav>` is `display:none`, unchanged from 3.1 §7.1, and print is ungated anyway.
`degraded:` server-rendered; only R2's optional current-section highlight is lost.

### 5.6 ACTIVATED — the gloss inside a gated read

3.1 §8.3 and §8.4 specify the in-sitting gloss completely and **6.2 is the first surface where they
actually run**. Nothing is redesigned. Three activations:

1. **The in-sitting path is the fetch-primary / navigation-degraded pair** (3.1 §8.3), because a gated
   read is a sitting. The `Back to the question` return target is the gate band's anchor.
2. **`glossable()` runs**, and its rendering is 3.1 §8.4's **silence**: a suppressed term renders as
   bare text with *"no element, no class, no `data-*` attribute, no underline, no title, no ARIA."*
   The once-per-sitting Ledger line `Some definitions are held until you answer.` is 3.1's string,
   reproduced verbatim and **not re-voiced**.
3. **The glossary appendix filters.** 3.1 §9.1 and §8.4 already require the in-sitting appendix to
   omit suppressed terms — *"a suppressed term is **absent**, not shown as an empty `<dt>`."* Under
   `[GATE: required]` **one more predicate is added, LOCKED:** the appendix renders only terms marked
   in **revealed** sections. Two reasons: a `<dt>`/`<dd>` for a term that appears only below an
   uncleared gate is below-gate content reaching the DOM through the back door (C6), and its
   backlink would point at an anchor that does not exist. No new copy is owed — the once-per-sitting
   held line already tells the learner the gate exists without disclosing where it bit.

`keyboard/SR:` unchanged from 3.1 §8.1/§8.3. `print:` unchanged — print is ungated and the appendix
prints in full (§8). `degraded:` 3.1 §11's row for the in-sitting gloss, unchanged, including
`Definitions are unavailable right now. The glossary is at the end of the lesson.`

### 5.7 NEW ruling — `required` degrades to `recommended` in diagnostic and exam modes. LOCKED.

06 §6.5 is unambiguous: in **diagnostic** and **exam** modes the learner receives *"Recording
acknowledgement, no verdict"* until the sitting ends (D-12, D-13), and 06 explicitly warns that
reaching the last item is **not** the release condition for exam mode. A `required` gate in either
mode could therefore never clear, and the rest of the lesson would be unreachable for the whole
sitting — a gate that can never open is C9's dead disabled button at document scale.

**Therefore, LOCKED:** in diagnostic and exam modes, `[GATE: required]` renders as `recommended` —
the whole lesson renders, the check is answered in the flow, no truncation boundary is emitted, no
skip control is offered and **no `gate_skip` is recorded** (there is nothing to skip). The band states
the reason in Ledger voice:

`This sitting holds feedback until it ends, so checks do not gate reading here.`

This is C8 applied exactly: *"keep the authored activity usable when possible and say exactly what is
unavailable."* Drill and practice modes run the gate as authored.

`keyboard/SR:` the line is real text inside the band, adjacent to the header, in reading order.
`print:` the line prints — a printed record of a diagnostic sitting should say why its gates did not
run. `degraded:` mode is persisted in the session file and is available before any script runs
(06 §6.5).

## 6. NEW — the recorded-skip control

### 6.1 It is never styled as a transgression — LOCKED

C16, research §3.3: *"the skip control is never styled as a transgression. No warning colour, no
confirm-you-really-want-this dialog, no `--bad` token. It is a normal button, in the same visual
register as `I'm stumped — show the next hint` — which UI-SPEC §7 already LOCKS as 'a normal button,
not a warning' for exactly this reason."*

Concretely, and each is testable:

- A real `<button type="submit">` with a visible label. Never hover-only, never keyboard-inaccessible
  (CONTEXT D-12).
- **No** `--bad`, **no** `--warn`, **no** accent fill, **no** icon, **no** `aria-describedby` warning,
  **no** confirmation dialog, **no** "are you sure", **no** second click.
- Secondary register: the check button carries the `--accent-soft`/`--accent` primary pairing already
  shipped in Phase 4; the skip button is the ordinary control style with no accent. This is hierarchy,
  not discouragement.
- It appears in the same `.actions` row as the check control, `space-3` apart, both ≥44px.
- **The check button is first in DOM order**, so Enter inside the form submits the check. That is
  deliberate and is stated here so it is not "fixed" later.

**Mechanism — RECOMMENDED.** One `<form method="post">` with two named submit buttons
(`name="action" value="check"` first, `value="skip"` second). One form, no JavaScript, both paths work
identically before any script loads.

### 6.2 When it appears — `gate_skip: always | after-attempt`, DEFAULT `always`

The one place in this phase where two treatments are both genuinely defensible, so C5 applies:
*"Implement both behind one interface and make the choice a setting."*

| Value | Renders | Default |
|---|---|---|
| `always` | the skip control is present from the first render of the band | **yes** |
| `after-attempt` | the control appears after one recorded attempt on this check; until then the band carries the Ledger line `Read ahead becomes available after one attempt.` | |

**Reason for the default.** CONTEXT D-11's word is *"always"*: *"A learner can **always** read ahead by
an explicit, recorded choice."* Hiding the control on first encounter would make the first gate feel
like a wall, which is the theater C19 rejects. **Reason `after-attempt` exists and is honest:** D-03
records that `required` is *"a stronger default posture with a more deliberate skip affordance"*, and
some learners want that. It stays honest because the band **states the condition in real Ledger-voice
text** rather than rendering a disabled control with no reason — C9, quoted: *"do not render a
disabled button with no reason."* There is never a greyed-out skip button anywhere in this phase.

This is a renderer-side read of one payload. It needs no second parser, scorer, or evidence store, so
it does not reach C5's stopping point.

### 6.3 What a skip does, and what it must never do — LOCKED

| Rule | Ground |
|---|---|
| A skip appends exactly one **`gate_skip`** event | CONTEXT D-07, ROADMAP criterion 8 |
| A skip appends **no `response` event**, and is *"explicitly not a `response` carrying a null score"* | ROADMAP criterion 8 — *"Conflating them would make a skip indistinguishable from an unmarked attempt in every downstream count"* |
| A skip **never advances the hint tier**, and **never renders in the hint ladder** — no card, no count, no skip-derived state | C17, and 06 §6.6 which defers this copy to this document |
| A skip is **not an attempt** | C17 |
| **The skipped band stays answerable** | see below |

**The stays-answerable ruling — LOCKED, and it is not obvious.** After a skip the band remains in
place with its response controls live; the sections below it are now rendered. The control is not
removed, the band is not collapsed, and the check is not marked closed.

Reason: CONTEXT D-04 — *"skipped-and-still-unclear is a prioritizable signal"*. If the control vanished
the learner could never convert a skip into a clear, and the signal this phase exists to produce
would be permanently degraded on first use. A skip moves the reading position; it does not dismiss
the question.

**Announcement copy** (one status update, §7.2): `Read ahead recorded. This check stays open.`

`keyboard/SR:` a real submit button with a visible label, reached immediately after the check button;
the outcome is announced once through the single existing `role=status` region (C11); focus behaviour
is §7.1's.
`print:` the skip control is `display:none` on paper — a printed lesson is complete and ungated so
there is nothing to skip, and a control on paper is not a control. Whether the *outcome* prints is
§8's DEFAULT row.
`degraded:` with the daemon unreachable the skip cannot be recorded, and the band says so with §12's
copy rather than skipping silently. **A skip that was not recorded must never advance the reading
position** — a reveal without its event would make the gate-outcome split (§11) count something that
never happened.

## 7. Focus, announcement, and the one place C10 does not reach

### 7.1 Focus after a `required` reveal — LOCKED, with the conflict stated honestly

C10, quoted in full: *"After submit, keep focus on submitted control unless an error needs focus;
status is announced without a focus jump."* Research §3.4 G1 says the opposite for this case: *"focus
moves to the newly revealed heading after the POST, which is the one place a focus jump is correct
because the page content changed."*

**This document rules with research, and it does not pretend C10 authorises it.**

| Case | Focus | Status |
|---|---|---|
| `required`, check cleared → a section is appended | **moves to the newly revealed section's `<h2>`** | LOCKED |
| `required`, skip recorded → a section is appended | **moves to the newly revealed section's `<h2>`** | LOCKED |
| `recommended`, check answered → the DOM does not grow | **stays on the submitted control — C10 unrelaxed** | LOCKED |
| `off` | no submission occurs in the reader | — |

**The rule in one testable sentence: focus moves only when the document grew.**

**Why C10 does not settle the first two rows.** C10 is written for a submit that leaves the page
structure intact. A cleared `required` gate is a different event: the document gains a whole section
and **the submitted control ceases to exist** — the response controls are replaced by the verdict
rendering. "Keep focus on the submitted control" is not a thing that can be done to a control that is
gone; the browser drops focus to `<body>`, which loses the keyboard user's position entirely and fails
C10's own neighbouring gate (§8 item 2, the keyboard path). C10's clause *"unless an error needs
focus"* shows the rule already admits cases where focus placement is load-bearing, but the honest
statement is that this case is one C10 does not address, and the alternative is worse for exactly the
users the gate protects. Recorded as a deliberate, reasoned extension, with §13 gate 4 as its fixture.

**Mechanism — RECOMMENDED.** POST → `303` → GET `/lesson/<stem>#<new-section-slug>`, and the served
page carries `<h2 tabindex="-1" autofocus>` on the new section. Reasons: post-redirect-get stops a
reload or a back-button press from re-submitting a check; the fragment makes the reading position
linkable; `autofocus` on a `tabindex="-1"` heading is the platform mechanism for moving focus after a
navigation with no script. A plan may improve this with a recorded reason and equal-or-better
accessibility.

### 7.2 One announcement, composed — LOCKED

C11: *"Announce state changes once, not on each visual animation frame."* A cleared gate produces two
facts — a verdict and a document change — and they must not become two announcements in two regions.

**The gate band contributes exactly one clause, appended after the verdict clause Phase 6 owns, in
the single existing `role=status` region:**

`The next section is below.`

It never replaces, re-words, or re-voices Phase 6's verdict string. On a skip there is no verdict, so
the announcement is §6.3's skip string alone.

**UNRESOLVED, and named rather than guessed.** A `role=status` region that is present in the document
at load time may not announce, because live regions announce on mutation after they are in the
accessibility tree — and every path here is a full server re-render. This document therefore makes the
**focus move the primary channel**: a screen reader reads the newly focused `<h2>`, which is the
information the learner needs. The status clause is additive. Its reliability on a fresh page load is
a **backstop** to verify against a real screen reader at plan time (§14 row), not a claim made here.
Recording it as unverified follows research §8's discipline: *"Recorded so no phase inherits a
confident wrong answer."*

### 12.1 Daemon unreachable during a gated read — LOCKED

`This check cannot be submitted while the runtime is unreachable. Run itembank daemon and reload.`
(Ledger.)

It follows 3.1's established pattern — the empty state names the one command that fills it — and C9:
the controls are not disabled with no reason; the reason is stated beside them. Never a spinner,
never a silent failure, and **never a reveal**: a reveal without a recorded event would put a section
on screen that the gate-outcome split has no event for.

### 12.2 The static offline build — LOCKED

`itembank build` produces a file with no daemon, so there is no evidence log to derive gate state from
(CONTEXT D-06) and, per 3.1 §8.5, *"Static offline build — nothing is recorded."*

**Therefore the static build renders a gated lesson ungated and complete, with every `[!CHECK:]` as
3.1's inert D2 slot carrying 3.1's existing copy** — `This check is available when you are reading with
a session.` No new string is owed and none is added.

**REJECTED — a client-side gate in the static build.** Ground: it would be a second implementation of
the gate with no evidence behind it, deriving state the log never saw. That is the shape C2 exists to
prevent, and it would make the same lesson behave differently in two surfaces for no gain.

## 13. Required verification gates for this phase

On top of UI-SPEC §11's six, every plan touching a browser surface here carries these.

1. **No-leak fixture (C6).** For a lesson with an uncleared `[GATE: required]` check, assert that
   every heading, paragraph, list item, table, code block, `[!KEY]` id, `[!EXAMPLE]` block, further
   `[!CHECK:]` id, backlink, TOC entry and glossary entry belonging to a section below the gate is
   **absent** from the HTML, the JSON payload, the ARIA tree, CSS-off text and every accessible name.
   Assert additionally that the check's own key, rationale, distractor analysis and objective line are
   absent before the verdict.
2. **Zero-reflow fixture (C15, §5.1).** Render the same lesson in four states — inert, open, cleared,
   skipped — and assert the emitted bytes preceding the band's opening tag are byte-identical across
   all four, and that the band's box metrics (padding, border, radius, block margin, computed measure)
   are identical across all four.
3. **Compatibility-floor pair (C3, D-14, ROADMAP criterion 6).** A bank whose lessons declare no gates
   renders byte-identically to Phase 3.1 output, and its parse is unchanged. The style-block exclusion
   is named in the fixture with 3.1 §12 cited, exactly as 3.1 requires.
4. **Focus fixture (§7.1).** After a clearing POST under `required`, focus is on the newly revealed
   `<h2>`; after a skip POST, likewise; after a submit under `recommended`, focus is on the submitted
   control and the DOM did not grow. Assert the reload-after-POST path does not re-submit the check.
5. **Degraded fixture (§12.1).** With the daemon stopped mid-gated-read, the copy renders verbatim,
   no control is a disabled button with no reason, no spinner persists, and **no section is revealed**.
6. **Print fixtures (§8).** `?print=1` on a lesson with an uncleared `required` gate serves the
   complete ungated document; every check prints as 3.1's D1 rule with its LOCKED string; no
   truncation boundary appears; and **the evidence log's length is unchanged across the request**.
7. **Skip fixture (C17, §6.3).** One skip appends exactly one `gate_skip`, appends **no** `response`,
   advances no hint tier, produces **no** card or count anywhere in the hint ladder, and leaves the
   band's response controls live and submittable.
8. **Mode-degrade fixture (§5.7).** `[GATE: required]` in diagnostic mode and in exam mode renders the
   complete lesson, emits no truncation boundary, offers no skip control, records no `gate_skip`, and
   renders the stated line verbatim.
9. **Responsive snapshots** at 1280 / 768 / 375px, plus 320px and 200% zoom, for `[GATE:]` all three
   values × `gate_skip` both values, with `reader_nav: column` in at least one combination. No clipped
   control, no horizontal prose scroll, band and controls operable at every width.
10. **Calm-progress fixture (C7, §9).** Assert no element in the gated reader carries a count of
    cleared checks, a percentage, a progress track, a streak, a check/cross glyph, an exclamation
    mark, or any CSS `transition`/`animation`/`scroll-behavior: smooth` on the band, the revealed
    section, or the boundary.
11. **Voice fixture.** Every string in §15 renders in the voice §4.1 assigns it, asserted by computed
    font-family **token name** rather than by literal family — 3.1 §17's rule, unchanged: *"a test that
    names Georgia has already broken the rule it is testing."*
12. **Cross-phase divergence guard (D-01 ≡ D-06).** The cross-bank `[!CHECK:]` lint code and message
    asserted here are read from the same constant Phase 3.1 asserts against, so the two phases cannot
    drift apart in the way both CONTEXT files forbid.
