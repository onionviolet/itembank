## Phase Framing — Read This First

Unlike Phase 2.1 (no new browser HTML) this phase **does** author real new HTML/CSS/JS — but as
one new branch inside an existing dispatch table, not a new page. `surfaces/quiz_page.py:TEMPLATE`
already renders six item types (`mc`, `multi`, `table`, `dnd`, `build`, `short`) through one
`{mc:asChoice, multi:asChoice, table:asAssign, dnd:asAssign, build:asBuild, short:asShort}[q.type]`
dispatch object (`quiz_page.py:217-218`) and one shared `close()` explanation renderer
(`quiz_page.py:418-460`). This phase's whole surface footprint is:

- One new dispatch entry, `check: asCheck`, following the exact shape of the five existing
  `as*(q, body, act, card)` functions — same `mkSubmit()`/`settle()`/`close()` machinery, no new
  machinery invented.
- One new `q.type === "check"` branch inside `close()`'s explanation renderer, rendering the
  per-case matrix instead of `paint()`/`blk()` prose.
- New CSS rules appended to `quiz_page.py:TEMPLATE`'s existing `<style>` block, reusing
  `THEME_CSS`'s existing custom properties (`--card`, `--line`, `--ok`, `--ok-bg`, `--bad`,
  `--bad-bg`, `--warn`, `--chip`, `--accent`, `--mut`) — **zero new colors**.
- One new `LABEL` map entry (`check: "code check"`) and one new `chips()` fallthrough (already
  free: the existing `else if(q.type!=="mc")` branch already emits the "no partial credit" chip
  for any non-`mc` type, `check` included, with no code change needed there).

**Phase 4 owns theming.** Every color, font stack, and base spacing value below is read directly
from `surfaces/theme.py:THEME_CSS` and `surfaces/quiz_page.py:TEMPLATE`'s existing values, not
invented. Where this phase introduces a genuinely new visual element (the editor gutter, the
case-result rows) it matches the *nearest existing analog* in the same file (`textarea.ans`,
`.opt.right`/`.opt.wrong`, `.trap`) rather than starting a new visual language, so Phase 4's later
palette pass touches one set of tokens, not two.

**Explicitly not built by this document's contract:** syntax highlighting, bracket matching,
auto-indent-on-Enter, multi-line block indent/dedent (select several lines, press Tab to indent
all). D-11 scopes the editor to "a `<textarea>` plus a synchronized line-number gutter... Tab
inserting a tab character and Shift-Tab dedenting" — nothing else. Adding any of the above would
be scope creep past D-11 and past CODE-03's own success criterion (monospace, working line
numbers, Tab inserts a tab). If a future phase wants them, that is a new decision, not a gap in
this one.

## Spacing Scale

Declared values (must be multiples of 4) — same 8-point scale precedent as Phase 2/2.1's
`UI-SPEC.md` for **new** elements. As in those two documents, `quiz_page.py:TEMPLATE`'s existing
CSS already carries off-grid legacy values (`18px`, `13px`, `11px`, `9px`, `7px` — see
`textarea.ans` at `TEMPLATE:84-88`), and unifying that grid is explicitly Phase 4's job
(SURF-05/07), not this phase's.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gutter-to-code internal gap |
| sm | 8px | Gap between stacked case rows (`.case + .case`) |
| md | 16px | — (not newly used this phase) |
| lg | 24px | — (not newly used this phase) |

**Exception, deliberate — matches the immediately adjacent component:** the editor's own internal
padding (`11px 12px`) and min-height baseline are copied verbatim from `textarea.ans`
(`TEMPLATE:84`), not from the 8-point scale, specifically so the code editor and the short-answer
textarea it sits beside in the same dispatch table read as one family of input, not two competing
grids. This is the same "match the neighbor, don't invent a third system" reasoning Phase 2's
`02-UI-SPEC.md` used to justify leaving `quiz_page.py` untouched — applied here in the opposite
direction (this phase touches that file, so it must match what's already there, not the abstract
8-point ideal). Phase 4 reconciles both at once, later.

## Color

Inherited unmodified from `surfaces/theme.py:THEME_CSS`. No new color, no new custom property.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg` | Page background (unchanged) |
| Secondary (30%) | `--card` | Editor background, case-row background (default/unresolved state) |
| Accent (10%) | `--accent` | Editor focus ring only (`.codewrap:focus-within`) — never a fill |
| Success | `--ok` / `--ok-bg` | A passing case: `.case.right` border/background, mirroring `.opt.right` exactly |
| Destructive | `--bad` / `--bad-bg` | A failing case (wrong output, timed out, or truncated — all three fail the case per D-08): `.case.wrong` border/background, mirroring `.opt.wrong` exactly |
| Warning | `--warn` | Two uses: (1) inside a failing case, the *status text* for a timeout or truncation reads in `--warn` rather than `--bad`, so a learner can tell "your code was stopped by a bound" apart from "your output was wrong" at a glance, even though the row itself is still styled as a fail; (2) the offline/LAN refusal banners, reusing the existing `.pend` treatment (`--warn`, `font-weight:600`) already used for "Recorded. Not marked here." |
| Muted | `--mut` | Gutter line numbers, case field labels ("Input"/"Expected"/"Your output") |
| Chip | `--chip` | Gutter background (so it reads as a rail alongside the code, matching `.chip`'s existing "recessed" treatment) |

**Accent reserved for:** the editor's own `:focus-within` outline ring — nothing else. Never a
background fill on the editor, the gutter, or any case row; those stay `--card` (default),
`--ok-bg` (pass), or `--bad-bg` (fail), matching the existing `.opt`/`.opt.right`/`.opt.wrong`
precedent exactly, so the code editor visually reads as "the same kind of thing" as every other
answer widget on the page.

## Editor Interaction Contract

*(Addendum beyond the standard template — this phase's central design risk is interaction
correctness, not visual novelty, so it is specified explicitly rather than left to the executor's
judgment on a component with no library behind it.)*

**Markup shape**, locked:

```
.codewrap                 (flex row, border, radius 9px, background var(--card), overflow hidden)
  .gutter                 (flex 0 0 auto, right-aligned line numbers, background var(--chip))
  textarea.code            (flex 1 1 auto, transparent background, white-space: pre)
```

- **Font sync is mandatory**: `.gutter` and `textarea.code` share identical `font-family`,
  `font-size` (14px), `line-height` (1.5), and top padding, so gutter row *N* sits pixel-aligned
  with textarea line *N*. This is what makes CODE-03's "line 7" citation trustworthy — a rubric
  point citing a line number is citing the line the learner visually sees only if the two columns
  cannot drift.
- **Scroll sync**: the gutter's `scrollTop` mirrors the textarea's `scrollTop` on every `scroll`
  event. Never the reverse (the gutter itself never scrolls independently or receives focus).
- **Line count**: recomputed on every `input` event by splitting the textarea's value on `\n`;
  the gutter always shows exactly as many numbers as the textarea has lines, 1-based, starting
  at 1 — not starting at 0, not padded with a phantom trailing blank line beyond what the
  textarea's own value actually contains.
- **Gutter width**: auto-grows with the digit count of the current highest line number (e.g., one
  character wide under 10 lines, two wide under 100), so a number is never clipped.
- **Tab**: `keydown` on the textarea intercepts `Tab` (no modifier), inserts a literal `\t` at the
  cursor (replacing the current selection if one exists — no block-indent of multiple lines, see
  Phase Framing's explicit exclusion), and calls `preventDefault()` so focus never leaves the
  field. This is CODE-03's literal wording ("a tab key that inserts a tab rather than moving
  focus") and the one interaction this contract cannot compromise on.
- **Shift-Tab**: dedents the current line only — removes one leading `\t` if present, else up to
  four leading space characters if present, else does nothing (never dedents past column 0, never
  touches a previous line).
- **No wrap**: `white-space: pre` and `overflow-x: auto` on the textarea. A long line scrolls
  horizontally rather than soft-wrapping, because a soft-wrapped line would visually span two
  gutter rows while remaining one logical line — breaking the "line 7 is line 7" guarantee CODE-03
  exists to provide. This is a deliberate correctness choice, not an oversight; a horizontal
  scrollbar on an 80+ column line is a smaller cost than a rubric citation that lies.
- **Starter code**: when the item authored one, it pre-fills `textarea.value` verbatim on render
  (no placeholder shown). When none was authored, the textarea shows the placeholder text `# Write
  your code here.` (locked copy, Python-specific since D-02 ships exactly one language this
  phase) and starts empty.
- **Focus ring**: `.codewrap:focus-within` gets `outline: 2px solid var(--accent); outline-offset:
  1px; border-color: var(--accent)` — matching `textarea.ans:focus`'s existing treatment exactly
  (`TEMPLATE:87`), applied to the wrapping element rather than the bare textarea so the gutter is
  visually included inside the focused field.
- **Disabled-after-submit**: on `Check`, the textarea and the Tab/Shift-Tab handlers are disabled
  (matching every other type's existing "lock the input, then reveal" sequence — `ta.disabled =
  true` for `short`, `b.disabled = true` for options). The learner's own submitted source stays
  visible, read-only, so they can compare it against the per-case explanation below it.

## Copywriting Contract

Every string below is meant to be used close to verbatim. Locked strings that must be worded
**identically** everywhere they appear are marked so explicitly.

| Element | Copy |
|---------|------|

"Hidden" is deliberate and locked: per D-12, `CASE)` input/expected pairs are key material and never reach `public_item()`; the learner cannot see them before answering, so the copy must not imply they can. |
| Check button, in-flight (server executing the code, can take up to `check.timeout_seconds`) | Button text becomes `Running…`, disabled — new state this phase adds (every other type's verdict returns effectively instantly; `check` is the first type where a real multi-second wait is possible, per D-07's timeout). |

| Case row heading | `Case %d` — 1-based, authored `CASE)` order (D-01's results vector order), no plural/singular branch (same shape at 1 case or many, per D-03's own "no special-casing" precedent). |
| Case status — pass | `Passed` — color `var(--ok)`. |
| Case status — fail, output mismatch | `Failed` — color `var(--bad)`. |
| Case status — fail, timeout | `Failed — timed out after %ss` (e.g. `Failed — timed out after 5s`, `%s` = `check.timeout_seconds`) — row still styled `.case.wrong` (D-08: a bounded run fails the case), but status text color is `var(--warn)`, not `var(--bad)`, so a learner can tell "stopped by a bound" apart from "produced wrong output" without reading the sentence. |
| Case status — fail, output truncated | `Failed — output was cut off at %d KB` (`%d` = `check.max_output_bytes / 1024`, default 64) — same `.case.wrong` row, `var(--warn)` status text, same reasoning as timeout. |
| Case field label — input | `Input` — omitted entirely (no empty `Input:` line) when the case's authored stdin is the empty string, matching the existing `blk()` helper's own `val ? … : ""` pattern (`TEMPLATE:426`). |
| Case field label — expected, `[MATCH: exact\|trimmed]` | `Expected` |
| Case field label — expected, `[MATCH: regex]` | `Expected (pattern)` — distinct label so a learner does not assume their output must match the shown text byte-for-byte when it's actually a pattern. |
| Case field label — actual | `Your output` |
| Offline / not-answerable-in-file refusal (D-06) — replaces the entire editor + Check button when the page was opened as a static `file://` build, i.e. `!SERVE` | `"This item runs code on the machine serving itembank and can't be answered from a file opened directly in a browser. Not marked here." treatment — this is a boundary, not a fault. |
| Offline skip control (D-06 continued — new interaction, scoped to this exact case only) | A single button, label `Skip — not answerable offline`, replacing `Check`. Advances to the next item directly (`i++; render();`) **without** calling `verify()`/`settle()`/`close()` — nothing is recorded, nothing is scored, and the item is excluded from `autoTotal` exactly as if it were never reached. This is deliberately a narrower behavior than a general "skip any item" feature (out of scope everywhere else in this project) — it exists solely because D-06 makes answering structurally impossible offline, not because skipping is otherwise supported. |
| LAN execution refusal (D-09 — surfaces in the action area after `Check` is pressed, when the daemon is serving with `--lan` and `check.allow_lan` is false) | `"Code execution is turned off while itembank is serving on your network (--lan). Ask whoever runs itembank to turn on check.allow_lan in settings if this device should be trusted, or answer this item from the machine itembank is running on."` Styled `.pend` (`--warn`) — this is the one refusal this project's own honest "no sandbox" claim has a matching default for (05-CONTEXT.md D-09), not a bug report. |
| Language not in allowlist (runtime — settings drifted after authoring; the lint-time version of this is `item.check_lang_unknown` and never reaches the browser) | `"This item requests the '%s' language, which isn't enabled in this itembank's settings (check.languages). Add it in settings, or ask whoever set up this bank to fix its [LANG:] value."` Styled `var(--bad)` (a misconfiguration, treated as an error) — not `.pend`, because unlike the LAN/offline cases this one has no correct default; something is actually wrong. |
| Connectivity failure (server unreachable mid-submit) | **Unchanged — reused verbatim.** `check` reuses `settle()`'s existing catch-block copy exactly: `"Could not reach the process that scores and records this sitting (<err>). This answer was not saved and was not marked. Restart itembank serve and sit it again."` No new copy needed; this failure mode is identical across every item type. |
| Empty state | Not applicable — a `check` item cannot parse with zero `CASE)` lines (the format requires at least one to be recognized as the type at all per `model.py`'s parse branch), so the per-case list's "empty" state is unreachable by construction, not merely handled. |
| Destructive confirmation | None in this phase's scope. Submitting code is not destructive (it does not overwrite anything, matching every other item type's no-confirmation precedent, itself matching `config set`'s Phase 2 resolution). |
