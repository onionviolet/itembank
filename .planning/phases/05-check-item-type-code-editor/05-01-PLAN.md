<objective>
Prove the whole `check` path end to end on one item: a bank parses it, the runner
executes the learner's source once per authored case, the per-case results reduce to a
vector, `runtime.score_response()` returns the dichotomous verdict, and the evidence log
records both the vector and the source that produced it.

This is the phase's tracer slice. It is production-quality, not a prototype: every layer
it touches gets its real shape, and the later plans widen it (bounds hardening, the
second submit path, the editor, the per-case readout) without moving any seam this plan
lays down.

Purpose: an architectural dead end in this phase — execution leaking into the pure
scorer, or the learner's source being lost from evidence — costs one commit to discover
here instead of ten commits later.
Output: `runner.py`, the `check` format contract, the `check` scoring branches, the
`check_source` evidence field, and a fixture bank plus a roundtrip test that drives all
of it through the real HTTP route.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide what content_fingerprint() covers for a check item</name>
  <reversibility rating="one-way">Every `[HASH:]` already written into a bank is
  computed from this field set; widening or narrowing it later invalidates every stored
  digest and fires content_drift on items nobody edited.</reversibility>
  <decision>Which fields of a `check` item are hashed into `model.content_fingerprint()`</decision>
  <context>
`content_fingerprint()` (model.py:142-179) digests the *tested content* of an item and
deliberately excludes rationale and metadata. It is the input to `[HASH:]`, which
`lint()` compares against to warn about content drift, and it is what keeps an item's
evidence history attached across edits.

A `check` item introduces four new fields — `cases` (the authored stdin/expected pairs),
`starter` (optional pre-filled source), `lang`, and `match`. D-05 says the stem and the
`CASE)` set are content and `[LANG:]`/`[MATCH:]` are configuration. It does not rule on
`STARTER:`, which this plan adds as the authoring surface for D-12's starter-code field.

Undo cost: no real bank carries a `check` item yet, so today the cost is zero. Once one
bank has been through `itembank id-assign`, changing this set means every `check` item's
`[HASH:]` is wrong and every one of them warns as drifted with no edit having occurred.
  </context>
  <options>
    <option id="option-a">
      <name>Stem + cases only (D-05 exactly as written)</name>
      <pros>Smallest surface. Matches the literal text of D-05. Editing starter code — a
      pure convenience for the learner — never disturbs an item's history.</pros>
      <cons>Replacing the starter code can change what an item effectively asks (a
      starter that pre-writes the parsing loop tests something different from one that
      does not), and that change would go unrecorded.</cons>
    </option>
    <option id="option-b">
      <name>Stem + cases + starter (recommended)</name>
      <pros>Consistent with how `short` already treats `model`+`rubric` as content: the
      authored scaffolding is part of what the item asks. Keeps `lang`/`match` out, which
      is D-05's actual distinction — content in, configuration out.</pros>
      <cons>Reformatting starter code (retabbing, a comment tweak) fires a drift warning
      even though the task is unchanged. `collapse()` already absorbs whitespace-only
      differences, which narrows this to real edits.</cons>
    </option>
    <option id="option-c">
      <name>Everything, including lang and match</name>
      <pros>No judgment call at all; the digest covers the whole item.</pros>
      <cons>Directly contradicts D-05. Switching `[MATCH: trimmed]` to `[MATCH: exact]`
      is a grading-strictness change, not a change to what is asked, and would orphan
      the item's fingerprint for no pedagogical reason.</cons>
    </option>
  </options>
  <acceptance_criteria>The developer names one of option-a, option-b or option-c, and the
  chosen field set is what Task 3 writes into both the fingerprint branch and the
  docstring.</acceptance_criteria>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
</task>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 2: Decide how the learner's source reaches the evidence log</name>
  <reversibility rating="one-way">The evidence log is append-only; a response written
  without the learner's source cannot gain it afterwards, and Phase 8's tutoring model
  reads that source to teach about the specific wrong answer.</reversibility>
  <decision>Where the submitted source text is stored on a `check` response event</decision>
  <context>
`evidence.response_event()` (evidence.py:355-395) takes exactly one `answer` value and
uses it for three purposes at once: it is stored as the event's `"answer"`, it is fed to
`idempotency_canon()` to build `"canonical"` and the dedupe key, and it is what
`score_response()` was called with.

For every existing item type those three are the same value. For `check` they are not:
the scorer needs the per-case results vector (D-01 keeps `canonical_response()` a pure
string reduction), and the record needs the source text (D-12 says the submitted answer
*is* the source). If the vector goes into `"answer"` and nothing else changes, the
learner's code is never written to disk anywhere.

`schemas/response.schema.json` sets `additionalProperties: false` and lists every key in
`required`, so whatever is chosen must be added to both `properties` and `required` or
every non-`check` event stops validating.

Undo cost: a migration over `_evidence/evidence.jsonl`, or permanent loss of the source
for every response written before the fix.
  </context>
  <options>
    <option id="option-a">
      <name>A reserved check_source field on the response event (D-13, recommended)</name>
      <pros>Follows the precedent already set by `error_category` and `hint_tier`
      (evidence.py:390-391): an explicitly-`None` reserved key rather than an absent one,
      so a consumer can tell "not captured" from "did not exist in that era".
      `"answer"`/`"canonical"` keep carrying what was scored, so dedupe and attempt
      counting behave identically for `check` and for every other type. One additive key
      in `properties` and `required`.</pros>
      <cons>One more always-present key on every event, `None` for five of the six
      types.</cons>
    </option>
    <option id="option-b">
      <name>Store the source as "answer" and the vector only in "canonical"</name>
      <pros>No new key.</pros>
      <cons>`idempotency_canon()` calls `canonical_response(q, answer)`, which for
      `check` would then receive source text and have to run the code to reduce it —
      exactly the purity violation D-01 exists to prevent. Rejected on architecture,
      not on taste.</cons>
    </option>
    <option id="option-c">
      <name>A separate event_type for code submissions</name>
      <pros>Keeps the response event untouched.</pros>
      <cons>Two events per submission means every reader (`report`, `evidence`, the
      attempt renderer, objective rollups) needs a join to see one answer, and the
      schema's top-level document stops describing a complete response. Far more
      invasive than a reserved field for the same information.</cons>
    </option>
  </options>

`run_cases(q, source, timeout_seconds=..., max_output_bytes=..., languages=...)` resolves
the item's `lang` against `languages` (raising `UnknownLanguage` on a miss, never falling
back to a default), writes `source` once into a `tempfile.TemporaryDirectory`, and calls
`run_one_case()` once per authored case in order. Return a list of dicts, one per case,
each carrying `case_index`, `passed`, `actual`, `timed_out` and `truncated`.

`run_one_case()` spawns one fresh subprocess per case — never one long-lived interpreter
fed several inputs — so a case that hangs does not consume the next case's budget and a
case that corrupts interpreter state cannot contaminate the one after it. Write the
case's stdin then close the stdin pipe immediately, so a program reading to EOF finishes
its own read instead of sitting out the deadline. Read stdout and stderr on two
`threading.Thread` drains via `drain_pipe()` rather than sequentially: reading one pipe
to completion while the child blocks writing to the other is the classic pipe-buffer
deadlock, and `communicate()` avoids it internally with exactly this shape. On POSIX
spawn with a new session so the child leads its own process group. Compute `passed`
through `case_passed()`.

`drain_pipe()` accumulates into a buffer until `cap_bytes`, then sets the truncated flag
and the stop event but keeps reading and discarding until EOF — stopping the read while
data remains unread leaves the child blocked on its next write, which converts an output
overrun into a hang.

`kill_tree(proc, job_handle)` is the single kill path both the deadline branch and the
output branch call; do not grow a second kill mechanism for the second trigger. On POSIX
it signals the child's process group with SIGKILL directly rather than escalating from
SIGTERM: the deadline is itself the bound, and a termination handler a runaway loop never
reaches buys nothing but a second wait window. On Windows this task ships
`taskkill /T /F /PID` — D-07's own named fallback, always present, and correct today;
plan 05-02 promotes a Job Object in front of it behind this same function signature.
Reap the direct child with `proc.wait()` afterwards or it lingers as a zombie until the
parent process exits.

`case_passed(match_mode, expected, actual)` implements D-04's `[MATCH:]` modes: `exact`
is byte equality, `trimmed` compares with trailing newlines stripped from both sides —
the default, because the overwhelmingly common failure is a missing or extra trailing
newline and failing a correct answer on that teaches nothing — and `regex` is a full match
over the whole actual output with dot-matches-newline. An unrecognized
mode returns False — lint catches it before this is ever reached. This comparison lives
here and not in `runtime.py` because it decides whether a case *passed*, which is
upstream of the scorer's pure vector comparison.

**runtime.py — the scoring branches.** `canonical_response()` gains a `check` branch that
joins an already-computed list of per-case pass flags with commas as ones and zeros, and
returns the empty string when the value is not a list — it never runs anything and never
sees source text. `canonical_key()` gains a `check` branch returning as many ones as the
item has cases. `score_response()` is not touched; the two new branches are all it needs.
`public_item()` gains a `check` branch setting `response_schema` to a string of format
source carrying the item's language, plus the item's `starter` text when one was
authored — and carrying no case input, no expected output and no key, because those are
key material under D-12. `explain_payload()` gains a `run_result=None` keyword parameter
and a `check` branch: with `reveal` it returns the per-case authored input and expected
text zipped against `run_result`'s per-case actual/timed-out/truncated flags, and without
`run_result` it returns the authored halves alone. The parameter is required, not
optional design: there is no other channel through which per-case actual output can reach
the explanation, and re-running the code to get it would double the execution cost and
risk for zero benefit.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser or agent → daemon/CLI | learner-authored source text crosses here as an ordinary request body |
| daemon/CLI → spawned interpreter | attacker-influenced code is executed here, by design; this is the phase's reason to exist |
| spawned interpreter → host OS | **no boundary is enforced here.** The executed code runs with the full rights of the user running itembank |
| LAN device → daemon | only when the daemon is bound to all interfaces; `check` execution is refused by default (plan 05-03) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-5-01 | Denial of Service | `runner.run_one_case` — code that never terminates | high | mitigate | A per-case wall-clock deadline (`timeout_seconds`, default 5) with `kill_tree()` on expiry, before the next case starts. Stops an accidental infinite loop; does not stop code that deliberately detaches from the group it was spawned in. |
| T-5-02 | Denial of Service | `runner.drain_pipe` — unbounded stdout/stderr, and the pipe-buffer deadlock a naive reader causes | high | mitigate | Two threaded incremental drains with a `max_output_bytes` accumulation cap; past the cap the drain keeps reading and discarding to EOF so the child is never left blocked on a full pipe. Plan 05-02 adds the truncation verdict and the early kill. |
| T-5-03 | Elevation of Privilege | the spawned process tree — a grandchild outliving its parent | high | mitigate | POSIX: a new session at spawn, then a group-wide SIGKILL. Windows: `taskkill /T /F /PID` here, a Job Object with kill-on-close in plan 05-02. Reaches processes that did not detach; does **not** reach one that double-forks or starts its own session. |
| T-5-05 | Information Disclosure / Tampering | filesystem reach of the executed code | high | accept | **Not restricted, and not claimed to be.** The learner's code can read, write and delete anything the user running itembank can. The interpreter's `-I` flag only stops this process's own configuration from bleeding into the run; it is not a filesystem control. Accepted because the learner already holds these rights outside this tool, and CODE-05 makes stating so a deliverable. |
| T-5-06 | Information Disclosure | network reach of the executed code | high | accept | **Not restricted.** The executed code may open sockets and reach the network; no egress control is applied. Disclosed rather than defended, on the same reasoning as T-5-05. |
| T-5-08 | Tampering | `[LANG:]` naming an arbitrary interpreter or extra argv | high | mitigate | The tag's text never reaches `argv`. It is a lookup key into the `languages` map; a miss raises `UnknownLanguage` and is a lint error, never a silent default. Only the mapped template is executed. |
| T-5-10 | Repudiation | a `check` response recorded without the source that produced it | medium | mitigate | `check_source` carries the submitted source verbatim on the response event while `answer`/`canonical` carry the vector, so a later reader can see what was written and not only whether it passed. |
| T-5-SC | Tampering | npm/pip/cargo installs | low | accept | This phase installs zero packages; `05-RESEARCH.md`'s Package Legitimacy Audit records none proposed. There is no install task to gate. |

**This model makes no safety claim beyond the bounds it names.** Every mitigation above
stops an accident. None of them stops a learner deliberately trying to do something with
local code execution they already have without this tool.
