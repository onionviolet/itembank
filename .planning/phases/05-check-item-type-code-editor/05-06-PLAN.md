<objective>
Render what happened, and refuse honestly when nothing can happen.

A `check` verdict is dichotomous, but a learner who fails needs to see which case failed
and what their program actually printed — that is the whole difference between a mark and
a lesson. And there are three situations where the field cannot be used at all: the page
was opened as a file with no process behind it, the daemon is on the network with
execution closed, or the item names a language this installation does not have. Each gets
its own sentence naming its own cause and its own next step.

Purpose: a red X with no output is a grade. A per-case matrix showing expected against
actual is the first thing that teaches.
Output: `close()`'s `check` branch, the case row styles built from the existing pass and
fail treatments, and the three refusal states with the offline skip control.

Criterion 9's no-JS floor is **SUPERSEDED** under ruling 5/11 (RESOLVED 2026-08-11): CM6
is JS-only, so the server-rendered textarea-plus-lint-list fallback does not exist and no
plan in this phase provides one — where a refusal replaces the field, it replaces the
**editor**. The external-editor `--watch` authoring path criterion 9 also named belongs to
Phase 11. See ROADMAP Phase 5 criterion 9 and the RESOLVED rulings.
</objective>

`close()` already handles the verdict header, the pending state, the trap block and the
next button for six item types; only its middle changes. Add a `check` branch that renders
the per-case matrix where the other branches render per-option prose, and leave the header,
the trap block and the next button untouched.

Treat the submitted source as the learner's executable prediction/action and the returned
ordered observations as what the bounded run observed. Use those semantics in concise UI
copy and identifiers so later diagnose → teach → learner action → bounded feedback work can
consume the data contract rather than scrape presentation strings. The renderer reads
`interaction_result.observations` from the shared runtime normalizer and never reruns code,
recomputes correctness, or turns the case mix into a grade; `runtime.score_response()`'s
top-level verdict remains the only grading authority.

**The rows.** One row per entry in `interaction_result.observations`, in the order the
payload carries them, which is the order the cases were authored, which is the order the
results vector was built in. Head each with its stable 1-based `case_index` using the
locked heading string, with no singular or plural branch — one case and many render the
same shape. Select the status copy from the stable machine-readable `reason`; do not infer
the reason from displayed actual/expected strings.

**The status line.** Derive it from the three flags the entry carries. A passing case gets
the locked pass string in the success role. A case that failed on output gets the locked
fail string in the failure role. A case that timed out gets the locked timeout string with
the deadline interpolated, and a case that was truncated gets the locked truncation string
with the cap size interpolated in kilobytes. Both bound cases keep the failure row styling —
a bounded run fails its case — but their status text takes the warning role, so a learner
can tell at a glance that their code was stopped rather than wrong, without reading the
sentence.

**The fields.** Render the case's authored input, its expected text, and the learner's
actual output, each labelled with its locked label. Omit the input label and its block
entirely when the authored stdin is empty, following the existing block helper's own
present-or-nothing pattern rather than emitting an empty labelled row. Use the distinct
expected label when the item's match mode is the pattern one, so a learner does not assume
their output has to match the shown text byte for byte when it does not.

Render all three as preformatted blocks that scroll independently, so a long expected value
or a long actual output does not stretch the card. The server-side output cap already
bounds the worst case before it reaches the page, so nothing unbounded arrives here; the
scroll is for readability, not for safety.

**The styles.** Add the case row rules to the existing style block, mirroring the existing
right and wrong option rules exactly — same border colour, same background, same shape.
This is deliberate: the case row must read as the same kind of thing as every other
answer widget on the page, and a later theming pass should touch one set of tokens rather
than two. Use only existing theme custom properties and introduce no new colour. Space
stacked rows with the small step from the spacing scale.

**What not to add.** The verdict is dichotomous and stays dichotomous no matter how the
matrix reads — per-case partial credit is a deferred idea, and the vector this renders
makes it computable later without a format change but does not make it shown now. Do not
compute or display a per-case score, a partial percentage, or a pass count in the verdict
header.

**The null-verdict case.** A killed-at-timeout run carries `verdict: null` in the
normalized result — `runtime.score_response()` returns no dichotomous verdict for it
(criterion 12), matching the None-not-False discipline `short` already follows, and the
item lands pending and human-markable. When the matrix renders a null verdict, render the
existing pending treatment where the correct/not-correct header would go and keep the case
rows beneath it: each row still shows its own stable `reason`, so the timed-out case reads
`timeout` and any completed case reads normally. The learner must be able to see the item
was *stopped*, not failed — the pending header is what makes that visible, and rendering a
pass or a fail for a null verdict would be the surface inventing a grade the runtime
refused to give. Branch on the payload's `verdict` value, never on a textual guess.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bank author → rendered page | case input, expected text and status labels reach the browser as page content |
| daemon → browser | per-case actual output — the learner's own program's stdout — crosses here after the verdict |
| browser → daemon | the learner's source text crosses here as a request body |
| spawned interpreter → host OS | **no boundary is enforced here.** Filesystem and network reach are unrestricted |
