<objective>
Give the `check` item a real code field: monospace, a gutter whose row N is the
textarea's line N, and a Tab key that inserts a tab instead of moving focus.

CODE-03 is the requirement that a rubric point citing "line 7" cites the line the learner
sees. That is not a styling nicety — it is why wrapping is off, why the gutter and the
textarea share one font declaration, and why the gutter is driven by scroll mirroring
rather than by its own scrollbar. This plan builds the field and the copy beside it, and
threads the per-case run result through to the page so plan 05-06 has something to render.

Purpose: a code field that is a plain textarea teaches the learner to count lines by hand
and makes every line citation a guess.
Output: `asCheck()` in the existing dispatch table, the editor CSS built from existing
theme properties, and the honest-limits line that reads the same constant `SPEC` does.
</objective>

  <action>
This is the interaction half of CODE-03, and it is the one part of this phase with no
library behind it, so every rule below is locked by the UI-SPEC rather than left to
judgment.

**Line count.** Recompute on every input event by splitting the textarea's value on
newlines and rendering that many 1-based numbers. Do not add a trailing row for a value
ending in a newline beyond what the split actually produces, and do not start at 0. A
rubric point citing line 7 has to land on the line the learner sees.

**Scroll sync.** Mirror the textarea's vertical scroll offset onto the gutter on every
scroll event, one direction only. The gutter has hidden overflow from Task 2, so it has no
scrollbar of its own to diverge; never wire the reverse direction and never let the gutter
take focus.

**Gutter width.** Size it from the digit count of the current highest line number so a
three-digit number is not clipped at ten lines' width. Recompute it with the line count,
not on a timer.

**Tab.** Intercept the keydown when no modifier is held, insert a literal tab at the
cursor — replacing the current selection when one exists — and prevent the default so focus
never leaves the field. This is CODE-03's literal wording and the one interaction in this
contract that cannot be compromised on.

Prefer the browser's text-insertion command over assigning to the textarea's value
directly. A direct value assignment clears the native undo and redo history entirely in
every major browser, which is a real regression against simply typing. The insertion
command is deprecated for many uses but remains the only reliable way to mutate a textarea
while keeping undo intact. Fall back to a value splice with manual cursor restoration where
the command is unavailable: losing undo on Tab is a usability regression, not a CODE-03
failure, since CODE-03 asks only that the tab character be inserted.

**Shift-Tab.** Dedent the current line only. Remove one leading tab if the line has one,
else remove up to four leading spaces, else do nothing. Never touch a previous line, never
dedent past column 0, and never operate on a multi-line selection — block indent and dedent
are explicitly outside this contract.

**After submit.** Disable the textarea and unbind or short-circuit both key handlers when
the Check button fires, matching how every other type locks its input before revealing.
Keep the submitted source visible and readable so the learner can compare it against the
per-case explanation plan 05-06 renders under it.

**Stay inside the contract.** Do not add syntax highlighting, bracket matching,
auto-indent on Enter, or multi-line block indent. Each of those is scope past D-11 and past
CODE-03's own success criterion, and each is a new decision rather than a gap in this one.

Extend `tests/check_roundtrip.py` with string-containment assertions against the rendered
page: the keydown handler is bound to the textarea, a literal tab character is what Tab
inserts, the default is prevented, the modifier branch exists, the four-space dedent bound
is present, and the scroll handler writes the gutter's scroll offset from the textarea's
and not the reverse. There is no JavaScript test harness in this project and adding one is
out of scope, so these assertions bound what the source says; the behaviours themselves are
in `05-VALIDATION.md`'s manual table and are checked at the end-of-phase pass in plan 05-07.
Say so in a comment beside the assertions rather than letting a reader mistake a string
check for a behaviour check.
