<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Run the Windows process-tree kill on the target machine</name>
  <precondition>The machine running this task reports `win32` from `python -c "import sys; print(sys.platform)"` — this verification is meaningless anywhere else.</precondition>
  <what-built>
Plan 05-02 built the Windows half of `runner.kill_tree()`: a Job Object created before
the child spawns, the child assigned to it as the statement immediately after `Popen`
returns, and the whole tree terminated by closing the job handle, with the process-tree
taskkill call kept behind it as a fallback. `fixtures/grandchild_spawner.py` and
`tests/check_kill_roundtrip.py` exercise it.

None of that has run on Windows in CI, and it never will in this phase — the workflow
pins `ubuntu-latest`. Everything below is the only real evidence this path works.
  </what-built>
  <how-to-verify>
Run all six steps on the Windows 11 machine, from the repository root, and keep the exact
output of each. Report the numbers, not a summary.

1. Confirm the platform and the interpreter:
   `python -c "import sys; print(sys.platform, sys.version)"`
   Expect `win32` and a 3.11-or-later version. If it does not say `win32`, stop.

2. Confirm the enum constant survives the real API. Run:
   `python -c "import sys; sys.path.insert(0,'.'); import runner; h=runner.new_job_object(); print('job created and configured:', bool(h))"`
   Expect it to print `True` with no traceback. A `WinError` here means
   `runner.JobObjectExtendedLimitInformation` is wrong — that value is the one
   tertiary-confidence number in the whole phase, and this is the step that settles it.
   Copy the full error text if it raises.

3. Run the kill test once and record the wall-clock time:
   `python tests/check_kill_roundtrip.py`
   Expect exit code 0 and output naming the Windows branch. Record how long it took.

4. Confirm nothing survived. Immediately after step 3 finishes, run:
   `tasklist /FI "IMAGENAME eq python.exe"`
   Expect to see only the shells you have open yourself — no leftover interpreter from
   the grandchild fixture. Paste the table.

5. Measure the accepted spawn window. Run the kill test 50 times in a row and count how
   many runs leave a surviving grandchild:
   `for /L %i in (1,1,50) do @python tests/check_kill_roundtrip.py >nul 2>&1 || echo FAILED %i`
   Then run `tasklist /FI "IMAGENAME eq python.exe"` once more. Report two numbers: how
   many of the 50 runs failed, and how many stray interpreter processes are left at the
   end. **Report the observed count even if it is zero — do not report "no escapes".**
   The record needs a measured rate over a stated sample size.

6. Force the fallback path and confirm it also kills the tree. Set the switch plan 05-02
   added for exactly this — its name is in `05-02-SUMMARY.md` — then run
   `python tests/check_kill_roundtrip.py` again and repeat step 4's `tasklist` check.
   Report whether the fallback killed the tree and how long it took relative to step 3.

If any step fails, paste the failure verbatim rather than describing it. A failure here is
a real finding, not a blocker to work around: D-07's own discretion clause allows the
fallback to become the primary path if the Job Object proves unworkable on this machine.
  </how-to-verify>
  <acceptance_criteria>
    - The developer reports, as literal values: the platform string and Python version; whether step 2 printed True or raised; the exit code and duration of step 3; the `tasklist` output from step 4; the failed-run count out of 50 and the stray-process count from step 5; and the fallback's outcome and duration from step 6.
    - A zero escape count is reported as "0 out of 50", never as an absence of escapes.
    - If step 2 raised, the full error text is reported so `runner.JobObjectExtendedLimitInformation` can be corrected against it.
  </acceptance_criteria>
  <resume-signal>Paste the six results, then type "verified" or describe what failed</resume-signal>
</task>
