## Five prioritized design inputs

| Priority | Concrete proposal | Evidence connection | Acceptance demonstration |
| --- | --- | --- | --- |
| D1 | Build one course-centered shell with an outline, primary learning stage, and optional source or notes panel. Desktop uses available width. Phone shows one stage with secondary panels opened deliberately. | OpenMAIC scene organization plus the project's source-to-course contract. | Desk, course, reading, practice, and review use the same navigation, type scale, spacing, and control language. At 390 px, no squeezed desktop rails or page-level horizontal overflow. |
| D2 | Treat question answering as stable states: unanswered, selected, submitting, feedback, next. Keep the prompt, response, and feedback in one visual region. Advance only after the learner requests it. | H5P sequence pattern plus existing Itembank runtime authority and continuity requirements. | A synthetic answer shows retained feedback, obvious next action, announced position, and predictable focus. Failed submission preserves the entered response. Scores and disclosure come from runtime in production. |
| D3 | Make rich explanations the visual centerpiece. Use one meaningful interactive representation with an adjacent plain explanation, bright but readable semantic emphasis, and a clear reset. | Desmos linked representations and LiaScript deliberate reveal. | A control change has an understandable visible consequence. Keyboard and touch can perform equivalent tasks. Reduced motion and the static source preserve meaning. |
| D4 | Give the learner one obvious resume or next action and a modest route overview. Show source, objective, and status as useful context instead of implementation labels. | Course outline and progress-separation patterns above. | A returning learner can identify where they left off and what the next step does. Unknown or pending state is named accurately. A prototype must label simulated progress. |
| D5 | Establish the new visual system independently, then integrate by measured parity. Compare the same synthetic journey in prototype and production at desktop and phone sizes. | Previous integration drift recorded in the project and the user's present concern about the old UI constraining the new one. | A screenshot matrix covers empty, populated, active, feedback, completion, and error states. Legacy global CSS cannot silently override the new components. Existing useful behavior must survive integration. |

## Disposition and boundaries

Full external runtimes and institutional workflows retain the dispositions in the September 8 absorption record. No capability was deleted from those ledgers.
